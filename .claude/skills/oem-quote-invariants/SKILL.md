# กฎเหล็ก — ระบบใบเสนอราคา/เอกสารภาษี OEM

ทุกข้อมาจากบั๊กหรือช่องโหว่ที่**เกิดขึ้นจริง**ในโปรเจกต์นี้

---

## 1. 🔴 ห้ามต้นทุน / margin / ราคารับซื้อคืน หลุดถึงลูกค้า

เอกสารที่ออกจากระบบนี้**ส่งออกนอกร้าน** สิ่งที่ห้ามโผล่:
`cost_piece` · margin ทุกตัว · `nre_cost` (ราคาค่าแบบแสดงได้ แต่**ต้นทุน**ค่าแบบห้าม) · floors/MOQ/เกณฑ์ภายใน · `approval_note` (เหตุผลที่ยอม margin ต่ำ) · `lost_reason` · `calc`/`rate_snapshot` ดิบ · ค่าแรงแยกขั้นตอน · ข้อมูลแฟลสก์ · **`buy_per_baht`/`kilo_buy` (ราคารับซื้อคืน)**

**⚠️ ต้นทุนเงินแท่ง = ราคารับซื้อคืน เป๊ะโดยนิยาม** (0079) แปลว่าตัวเลขรับซื้อคืน**อยู่ใน `cost_piece` แน่นอน** ปล่อย cost หลุด = เปิดส่วนต่างซื้อ-ขายให้ลูกค้าเห็น

**กันด้วยโครงสร้าง ไม่ใช่ด้วยวินัย:**
- หน้าพิมพ์รับเฉพาะ `PrintableQuote` / `PrintableReceipt` — **ห้ามรับ `OemQuoteRow` หรือ row ดิบจาก view**
- type พวกนี้**ประกอบทีละ field ห้าม spread** เพื่อไม่ให้ field ใหม่ในอนาคตหลุดตามมาฟรีๆ
- ห้าม import component ที่แสดงต้นทุน (เช่น `OemCalcBreakdown`) เข้าหน้าพิมพ์เด็ดขาด
- คอมเมนต์เตือนไม่ใช่ด่าน — **ด่านคือ type boundary**

**วิธีตรวจว่าหลุดไหม:** ยิงหน้า print จริงออกมา แล้วหา**ตัวเลขต้นทุนจริงจาก DB** ในผลลัพธ์ (ทั้งส่วนที่ตาเห็นและ payload ที่ streamed ไป client) ไม่ใช่แค่ grep คำว่า cost ในซอร์ส

## 2. ห้ามคำนวณเลขเงินใน client

ทุกตัวเลขมาจาก `oem_price_calc` / `oem_quote_save` / view ฝั่ง DB — หน้าจอแค่แสดงผล

เหตุผลที่ไม่ใช่แค่ความสวยงาม: การหารครึ่งของ 31,172.93 ได้ 15,586.47 + 15,586.46 (ต่างกัน 1 สตางค์)
ถ้า client คำนวณเอง เลขที่ผู้ใช้เห็นจะ**ไม่ตรงกับที่ DB บันทึก** แล้วเอกสารกับรายงานจะเถียงกันเอง

ข้อยกเว้นเดียวที่มี: `aggregateQuotePreview` ที่**บวกเลขที่ DB คำนวณมาแล้ว**เพื่อ preview สด — ไม่ได้คิดสูตรใหม่

## 3. ปัดเศษ: คำนวณตัวหนึ่ง แล้วอีกตัวเป็น "เศษที่เหลือ"

```sql
vat_base   = round(grand_total / (1 + vat_rate), 2)
vat_amount = grand_total - vat_base        -- ✅ เศษที่เหลือ
-- ❌ ห้าม: vat_amount = round(vat_base * vat_rate, 2)
```

ปัดสองตัวอิสระกันแล้วบางยอดจะคลาด 1 สตางค์ → **เอกสารที่ส่งลูกค้าบวกไม่ลง** ฝ่ายบัญชีลูกค้าตีกลับ

ใช้หลักเดียวกันกับ: มัดจำ/ยอดคงเหลือ · งวดชำระ (งวดปิดใช้ยอดคงค้าง ไม่ใช่คิด % ซ้ำ)
**invariant ที่ต้องจริงเสมอ:** ผลรวมของส่วนย่อย = ยอดเต็ม เป๊ะ ทุกยอด รวมยอดคี่

## 4. ราคาเงินแท่งไม่เป็นเส้นตรงตามน้ำหนัก

แท่ง 1 บาท 1,455 × 10 = 14,550 แต่**แท่ง 10 บาทจริง 13,718** (ต่าง 6%)
คูณราคาต่อกรัม/ต่อบาท = เสนอลูกค้าแพงเกินจริง แล้วลูกค้าเปิดเว็บร้านเทียบเจอทันที

**ต้องอ่านราคาแยกตามขนาด** จาก `silver_price_daily` (`bar_0_5_baht`/`bar_1_baht`/.../`kilo_sell_vat`)
และ **ห้ามใช้ `sell_per_baht`** — เป็น null ได้ตั้งแต่ 0074

ส่วนต่างจริงก็ไม่เท่ากันทุกขนาด: แท่งเล็ก 20-27% แต่ **1 กก. แค่ 8.4%** อย่าสมมติว่า margin เท่ากันทั้งกลุ่ม

---

## 5. ราคาไม่สด = ออกใบไม่ได้ ห้ามใช้ของเมื่อวานเงียบๆ

ราคาเงินแท่งดึงจากหน้าเว็บร้านวันละ 3 รอบ (09/13/20 เวลาไทย)
ถ้าวันนี้ยังไม่มีราคา → เข้า `missing[]` → ออกใบสถานะ quoted ไม่ได้

**ยอมให้ทำงานไม่ได้ ดีกว่าเสนอราคาผิดโดยไม่มีใครรู้** — ห้ามใส่ fallback ไปหยิบราคาวันก่อน

---

## 6. ด่านราย item กับด่านรวมทั้งใบ ทำหน้าที่ต่างกัน — อย่าสับสน

- **ด่านรายชิ้น** (`margin_charged` ต่อ item) = คุ้มครองงานผลิต **ห้ามผ่อนเด็ดขาด** (เฉพาะราคาที่มาจากสูตร margin % — รายการที่ผู้ใช้พิมพ์ราคาต่อชิ้นทับ ดูข้อ 6.1)
- **ด่านรวมทั้งใบ** = คุ้มครองจากส่วนลด ทำงานเมื่อมีส่วนลดจริง

**บทเรียนที่เจ็บมาแล้ว:** เคยผูกด่านรวมไว้กับ "ใบนี้มีงานผลิตไหม" ผลคือเติมของชิ้นละ 50 บาทเข้าไปใบเดียว
ก็ปลดล็อกใบมูลค่าเจ็ดหมื่นให้ไม่ต้องมีเหตุผลบันทึกไว้ได้
→ **เงื่อนไขต้องผูกกับคุณสมบัติที่เป็นเหตุผลจริง** (เช่น "มีรายการที่ตรวจ margin รายชิ้นไม่ได้ไหม") ไม่ใช่ตัวแทนที่หลวมกว่า
และ**อย่าผูกกับชื่อวัสดุตรงๆ** — สินค้าประเภทใหม่ในอนาคตจะถูกคุ้มครองเองโดยไม่ต้องมีใครจำมาแก้

**ด่านที่ไม่มีข้อยกเว้นเลย:** margin รวมติดลบ (ขายต่ำกว่าต้นทุนตัวเอง) — ปฏิเสธเสมอ ไม่ปลดล็อกด้วยเหตุผล

**ด่านอ่อน (มติเจ้าของ 8 ต.ค. 69, 0168):** MOQ (จำนวนชิ้น) และล็อตโลหะขั้นต่ำ (น้ำหนักทองรวม) ของงานผลิตทุกวัสดุ = "ออกใบได้เมื่อมีเหตุผลอนุมัติ (approval_note)" ไม่ใช่ห้ามออกใบ —
quoted + floor ไม่ผ่าน + ไม่มี note (หลังลบอักขระล่องหน + trim ช่องว่างทุกชนิด) = 22023 · floors ใน `oem_price_calc` ยังรายงาน pass=false ให้ UI เตือน · ด่านอื่น (is_complete · min_job_value · margin รวมติดลบ · hard floor ·
ราคาพิเศษเงินแท่งต่ำกว่าทุน) ไม่ถูกผ่อนด้วย note · approval_note ห้ามพิมพ์บนใบลูกค้า (ข้อ 1)

### 6.1 งานผลิตพิมพ์ราคาต่อชิ้นทับ (มติเจ้าของ 9 ต.ค. 69, 0169)
ต้นทุนยังคิดจากสูตร ผู้ใช้พิมพ์ `unit_price_override_thb` (+ เหตุผลบังคับ) ทับราคาจาก margin % —
- **ต่ำกว่าทุนต่อชิ้น (`floors.price_vs_cost.pass=false`) = ห้ามเสมอ** ไม่ปลดด้วยเหตุผล · ข้อความไม่ใส่ตัวเลขทุน · บันทึก draft ได้
- **ต่ำกว่า margin floor = ด่านอ่อน** ต้อง approval_note (gate `override_below_floor`) · hard floor รายชิ้น "ไม่ใช้" กับรายการที่มี override แต่ **ยังแข็งเต็มที่สำหรับรายการที่ราคามาจากสูตร** (ใบผสมไม่ผ่อนให้กัน)
- ทอง (pass-through): margin ของราคาที่พิมพ์ = 1 − (แรง+batch)/(ราคา − เนื้อทอง) ความหมายเดียวกับ margin % ในสูตร · NRE ยังคิดจาก margin % เดิม
- `breakdown.production_override` (ราคาจากสูตร/เหตุผล) เห็นเฉพาะหน้า admin — `PrintableQuote` ไม่มี field รองรับ (ข้อ 1) · `pricePerPiece` บนใบ = ราคาที่พิมพ์

### 6.2 เหตุผล/note ทุกชนิดใช้ whitelist ห้าม blacklist (security 0168 M1/L1)
"มีเหตุผล" = `analytics.oem_note_present(text)` (ต้องมีตัวอักษร/ตัวเลขจริงหลังลบอักขระล่องหน) — **ห้าม** เขียน `btrim(x) = ''` หรือ blacklist ช่องว่างเอง
(NEL · U+2800 · VS16 · tag · "." · "👍" ล้วนหลุด blacklist ได้เสมอ) · รูปร่างก่อนเก็บ = `oem_note_valid` (ห้าม control/bidi/ล่องหน ยาว ≤ 500) ·
ฝั่ง JS ใช้ `oemNotePresent`/`approvalNoteIssue` (lib/oem/display.ts) เป็น pre-check เท่านั้น · ด่านอ่อนที่ใบใช้ note ผ่านเก็บใน `oem_quote.approval_gates` (server คำนวณ ไม่ใช่ rate_snapshot)

## 7. เอกสารภาษี — ข้อบังคับตามกฎหมาย ไม่ใช่ตัวเลือกดีไซน์

- **ใบกำกับภาษีต้องแยกจำนวน VAT ออกจากมูลค่าให้ชัดแจ้ง** เขียนแค่ "ราคารวม VAT แล้ว" ไม่พอ
- **ยังไม่จดทะเบียน VAT ห้ามเขียนคำว่าภาษีมูลค่าเพิ่มบนเอกสารเด็ดขาด** — ตัดสินจาก `seller_vat_registered` ตัวเดียว กันทั้งฝั่ง DB และฝั่งจอ
- **เอกสารที่ออกแล้วห้ามแก้** แก้ได้ทางเดียวคือยกเลิกแล้วออกใหม่
- **เลขที่เอกสารห้ามข้าม** ยกเลิกแล้วเลขเดิมต้องไม่ถูกใช้ซ้ำ
- ต้องมีครบ: ชื่อ+ที่อยู่+เลขผู้เสียภาษี+สาขา **ของทั้งผู้ขายและผู้ซื้อ**
- **snapshot ข้อมูลผู้ขาย/ผู้ซื้อ/อัตราภาษี ติดไว้กับเอกสาร** — พิมพ์ซ้ำอีก 5 ปีต้องได้เหมือนเดิมเป๊ะ ห้ามให้ view ไปดึงค่าปัจจุบันมาคำนวณสด
- ข้อมูลร้านไม่ครบ = พิมพ์ไม่ได้ (กันเอกสารไม่มีเลขผู้เสียภาษีหลุดถึงลูกค้า)

**reissue (ออกใบแทน) — บทเรียน security ตีกลับ 2 รอบ:**
- reissue ต้องผูกกับใบเดิมที่ void แล้ว **ครบ 5 อย่าง: วันที่รับเงิน + ยอดเงิน + ประเภทรับเงิน + ดีล (root_quote_id) + ตัวผู้ซื้อ (buyer_tax_id ที่ snapshot ไว้)**
  ขาดตัวไหนตัวหนึ่ง = ช่องออกใบย้อนงวดภาษี (void ใบเก่าใบไหนก็ได้แล้ว "ยืมวันที่" มาออกใบยอด/ดีล/ผู้ซื้ออื่น)
- ล็อกผู้ซื้อที่ **tax_id ตัวเดียว ไม่ล็อกทั้งก้อน** — แก้ชื่อ/ที่อยู่/สาขาที่พิมพ์ผิดคือเหตุผลที่ reissue มีอยู่ ห้ามฆ่า use case นี้
- หลักที่ใช้ตัดสิน: **"ด่านที่มีข้อยกเว้น ข้อยกเว้นนั้นต้องแคบพอที่จะพิสูจน์ได้ว่าเป็นเคสที่ตั้งใจอนุญาตจริง"** — เช็คเงื่อนไขเดียว (แค่วันที่ตรง) ไม่พอ

**องค์ประกอบใบกำกับภาษีบนกระดาษ — ทั้งหมดหรือไม่มีเลย:**
- พาดหัว "ใบกำกับภาษี" + เลขผู้เสียภาษีผู้ซื้อ + สาขาผู้ซื้อ ต้องผูกกับเงื่อนไขเดียวกัน (`isFullTaxInvoice` = มีครบ tax_id+สาขา+ที่อยู่)
  ห้ามแยกผูกทีละ field — จะได้ "ใบครึ่งๆ" ที่พาดหัวว่าใบเสร็จแต่มีเลขผู้เสียภาษี ซึ่งบัญชีลูกค้าอาจเอาไปเคลม VAT ผิดๆ
- ที่อยู่ผู้ซื้อพิมพ์ได้เสมอ (ใบเสร็จธรรมดาก็มีที่อยู่ได้) · ท่อนแยก VAT แสดงทุกใบ (ร้านจด VAT แล้ว)
- การตกชั้นเอกสาร (tax invoice → ใบเสร็จธรรมดา) **ห้ามเงียบ** — ต้องมีแถบเตือนบนจอ (`print:hidden`) ให้พนักงานรู้ก่อนกดพิมพ์

**ตัวนับเลขที่เอกสาร (`oem_doc_counter`):**
- `last_no` ขึ้นได้ทีละ 1 เท่านั้น ห้าม UPDATE/DELETE/TRUNCATE ตรง (มี trigger คุมแล้ว 0087/0088)
- ตารางข้างเคียงของเอกสารภาษีต้องได้การป้องกันชุดเดียวกับตัวเอกสาร — "กันแก้ใบเสร็จแต่ลืมกันตัวนับ" คือช่องที่เคยหลุด

## 8. ตัวเลขที่บวกไม่ลง ห้ามหลุดถึงลูกค้า

ยอดคงเหลือติดลบ (มัดจำมากกว่ายอดสุทธิ) เกิดได้จริงเมื่อตั้งมัดจำเป็นยอดเงินแล้วยอดใบลดลงทีหลัง
DB **จงใจปล่อยให้ติดลบ** เพื่อไม่ซ่อนปัญหา — แต่ **หน้าพิมพ์ต้องบล็อก** ไม่ใช่แค่เตือน

และข้อความเตือนที่พูดกับพนักงาน ("ตรวจสอบก่อนส่งลูกค้า") ต้องมี `print:hidden` เสมอ
**เคยหลุดไปบนกระดาษที่ส่งลูกค้ามาแล้ว**

## 9. อย่าเดาข้อมูลที่ไม่มี

catalog 301 SKU มี `silver_weight_g` เป็น null ทั้งหมด → ตัวเลือก SKU **จึงเป็นแค่การติดป้ายชื่อ** ไม่ใช่ทางลัดกรอกราคา
เดาน้ำหนักจากชื่อ SKU = ราคาที่เสนอลูกค้าเพี้ยนโดยไม่มีใครรู้ตัว **แย่กว่าไม่เดา**

หลักเดียวกัน: ตัวเลข `unit_cost`/`list_price` ใน catalog ล้าสมัยหนัก (บางตัว "ต้นทุน" สูงกว่าราคาขายจริงวันนี้)
ใช้ได้เฉพาะ `margin_pct` ที่เป็นอัตราส่วน — **ห้ามเอาไปคิดราคางานผลิต/เงินแท่ง** (ข้อยกเว้นเดียว = รายการสินค้า ด้านล่าง)

### 9.1 ข้อยกเว้นที่เจ้าของสั่ง (8 ต.ค. 69, migration 0166): รายการสินค้า/บริการ `metal='product'`

ขายของที่ไม่ใช่งานผลิตและไม่ใช่เงินแท่ง — **ข้อยกเว้นแคบ ห้ามขยายไปคิดราคางานผลิต:**
- `list_price` ของ SKU = **ราคาตั้งต้นที่ผู้ขายแก้ได้อิสระ** (ไม่ใช่ราคาที่ระบบ "คิดให้") · ต่ำกว่า list ต้องมี `price_reason` · DB อ่านราคา/ทุนจาก `v_dim_product` **เอง** ไม่เชื่อ client
  (client ส่งได้แค่ราคาที่กรอก · ส่ง `unit_cost_thb` มากับ SKU = 22023 กันทับทุนแคตตาล็อก)
- `unit_cost` ของแคตตาล็อก = **ค่าประมาณ** (กำไรของรายการนี้เป็น estimate) · ทุน 0/null/NaN = `is_complete=false` ออกใบ quoted ไม่ได้ — **ห้ามใช้ 0 เป็นทุน** (ข้อ 13 ของ 3j-migration-traps)
- ไม่มี SKU = พิมพ์ชื่อ + ราคา + **ทุนบังคับ** · เดาน้ำหนัก/ทุนจากชื่อ SKU ยังห้ามเหมือนเดิม
- **ไม่มีด่านทุนรายชิ้น** (`floors.margin.value = null`) แต่ **ด่านรวมทั้งใบ "margin ติดลบ = ปฏิเสธ" กับ hard floor หลังส่วนลดยังอยู่ครบ ห้ามแตะ** (ข้อ 6)
- **มติ 5**: รายการสินค้า **ไม่นับ** เป็น "มูลค่างานผลิต" (min_job_value) และ **ไม่ปลุก** note-tier (`v_has_ungated_item`) —
  แยก "ไม่มีด่านรายชิ้นเพราะเป็นสินค้า" ออกจาก "ตรวจไม่ได้" ด้วย `metal` (ข้อยกเว้นเดียวของกฎ "ผูกกับคุณสมบัติ ไม่ผูกกับชื่อวัสดุ" ในข้อ 6) ·
  ใบผสมกับงานผลิตยังติดด่านเดิมของส่วนงานผลิต · `oem_quote_save` **และ** `oem_quote_renegotiate` ต้องตรรกะเดียวกัน (renegotiate คำนวณ gate ใหม่จาก item ที่เก็บไว้)
- 🔴 **ด่าน min_job_value ของใบที่มีสินค้า (0167 F1)**: ยอดงานผลิต **หลังหักส่วนลดทั้งใบ** ต้อง >= เกณฑ์ (save ใช้ p_discount_thb · renegotiate ใช้ p_new_discount_thb) —
  ไม่งั้นเติมสินค้า 0.01 บาทเข้าใบก็ข้ามด่านได้ · ใบแท่ง + งานผลิตที่ไม่มีสินค้ายังเป็นของเดิม (หนี้ช่องเดียวกันตั้งแต่ 0079 — ยังไม่แก้ เพราะเปลี่ยนพฤติกรรมเดิม)
- 🔴 **ทุนที่กรอกเอง (`cost_source='manual'`) ไม่ใช่หลักฐาน (0167 F2)**: นับเข้าด่านได้ แต่ต้องมี approval_note (renegotiate = เหตุผล) เมื่อใบมีส่วนลด > 0 หรือเมื่อ
  "นับ manual เฉพาะส่วนขาดทุน" แล้วใบขาดทุน (กำไรที่ผู้กรอกอ้างเองกลบรายการขาดทุน) · note ที่มีแต่อักขระล่องหนไม่นับ · ชื่อรายการไม่มี SKU ที่ตรงเป๊ะกับ sku/ชื่อในแคตตาล็อก = ปฏิเสธ (F3)
- แก้ราคาในใบ = **เฉพาะใบนั้น ห้ามเขียนกลับ catalog** · ใบที่ save แล้วเก็บ snapshot ใน `calc.breakdown.product` — แก้ catalog ทีหลังไม่ขยับ
- 🔴 เหตุผลส่วนลด (`discount_reason` รวมเหตุผลตอนต่อราคา) **ไม่พิมพ์บนใบลูกค้า** (มติเจ้าของ 8 ต.ค. 69) — `PrintableQuote` ไม่มี field นี้ · บนใบเหลือ "ส่วนลด X บาท"
- 🔴 ทุน / `price_reason` / ราคาแคตตาล็อก / ทุน manual **ห้ามหลุดหน้าพิมพ์** — `PrintableQuote` ไม่มี field รองรับ (ข้อ 1) · sku/ชื่อบนใบมาจาก snapshot ที่ DB ทับ ไม่ใช่ที่ client ส่ง

## เช็คลิสต์ก่อนบอกว่างานโดเมนนี้เสร็จ

- [ ] เพิ่ม field เข้าหน้าพิมพ์ไหม → เป็นราคาที่ลูกค้าควรเห็นจริงไหม · ประกอบทีละ field ไม่ spread
- [ ] มีการคำนวณเลขเงินใน client โผล่มาไหม
- [ ] ปัดเศษที่ไหน → ผลรวมส่วนย่อยเท่ายอดเต็มเป๊ะไหม (ทดสอบด้วยยอดคี่)
- [ ] แตะ gate ไหม → ผ่อนด่านรายชิ้นหรือเปล่า · เงื่อนไขผูกกับเหตุผลจริงหรือตัวแทนที่หลวม
- [ ] แตะเอกสารภาษีไหม → แก้ย้อนหลังได้ไหม · เลขข้ามไหม · snapshot ครบไหม
- [ ] ยิงหน้าพิมพ์จริงแล้วหาเลขต้นทุนจาก DB ในผลลัพธ์หรือยัง
- [ ] เพิ่ม `metal` ใหม่ไหม → ทุก gate ที่แยกตาม metal (min_job_value · ungated/note-tier · อายุใบ) ใน **save และ renegotiate** ตัดสินแล้วหรือยัง · golden replay + mutant ล้มจริงไหม
