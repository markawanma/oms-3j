### 0.2 ข้อค้นพบที่ต้องรู้ก่อนเขียนโค้ด

**(ก) ช่องโหว่ในคำสั่งและ brief — บอกตรงๆ ตามที่สั่ง**

1. **"0.1–0.15 ใน round2-request" แยกอยู่สองไฟล์:** `content-ui-round2-request.md` มีแค่ 0.1–0.4 · ข้อ 0.5–0.15 (LINE/สตอรี่ · กู้คืน · ล้างด่านเมื่อแก้เนื้อหา · ล็อกหลังอนุมัติ · แหล่งอ้างอิงข้อเท็จจริง · sheet โพสต์ · ผู้รับ LINE · สัญญาณกลับ · ไม่มีผู้ช่วย · แม่แบบคลิป · คิวเกิน 10) อยู่ใน `ui-handoff-round2/01-request-round2.md` → ผมใช้ทั้งสองไฟล์
2. **"token CAS ต้องส่งทุกครั้ง" — มีแค่ 4 RPC ที่รับ token/expected จริง** (ตรวจจาก migration): `campaign_verdict_confirm` (`p_expected_proposed` + `p_expected_token` บังคับทั้งคู่ ห้าม null) · `recommendation_respond` (`p_expected_token` บังคับ) · `content_post_metric_amend` (`p_expected` jsonb ไม่บังคับ แต่ต้องส่ง) · `content_post_verdict_confirm` (`p_expected_computed`) · RPC อื่น (`content_piece_advance` / `set_plan` / `gate_record` ฯลฯ) **ไม่มี CAS** → กันกดซ้ำ/หน้าเก่าด้วยข้อความ 55000 "อยู่สถานะนี้แล้ว" ซึ่งต้องแปลเป็นไทยว่า "ชิ้นนี้เปลี่ยนสถานะไปแล้ว — รีเฟรช" (ภาคผนวก B) ไม่ใช่ error แดงน่ากลัว
3. **เอกสาร architect §13 กับ migration 0162 จริงต่างกัน** (รอบแก้ 1–3 เปลี่ยน contract): ชื่อ column ของ view (`metric_channel_code` · `metric_affinity` · `metric_date_from/to` · `result_open_pieces` · `verdict_token` · `content_token` · `owner_response`) และ signature (`campaign_verdict_confirm` มี `p_expected_token` · `recommendation_respond` มี `p_expected_token`) → **ภาคผนวก A ลอกจากไฟล์ migration** ใช้ตัวนั้น ห้ามใช้ §13.2/13.5 ตรงๆ
4. **สิ่งที่คำสั่งไม่ได้ระบุแต่จำเป็น:** ต้องเพิ่ม dependency `react-markdown` + `remark-gfm` (ยังไม่มีใน `package.json`; Weekly Brief ใช้ตาราง markdown ~50 บรรทัด/ฉบับ) — ต้องผ่าน security ใน P3

- บรรทัดหัว: "AI เสนอ: **<ป้ายคำตัดสิน>**" · ป้ายความมั่นใจ ข้อสังเกต(เส้นประ) · "เสนอเมื่อ <result_proposed_at>" (`result_proposed_by_role`: ai→"AI" / owner→"คุณ" / system→"ระบบ")
- หลักฐานจาก AI: `result_proposed_note` (ข้อความธรรมดา `whitespace-pre-wrap` · ห้าม markdown · ≤1000)
- (ถ้า `metric_code='orders'`) **แผงข้อมูลที่ DB ใช้ตัดสิน** (ตัวเลขจาก view ตรงๆ): ช่วงนับ `orders_window_from–to` · ช่องทาง/กลุ่ม `orders_channel`/`orders_affinity` (map เป็นข้อความไทย) · ยอดจริง `orders_actual` · เกณฑ์ `pass_op` (ไม่น้อยกว่า/ไม่เกิน) `pass_threshold` · คำใบ้ `orders_threshold_met` ("ตัวเลข<ถึง/ไม่ถึง>เกณฑ์ — เป็นคำใบ้ ไม่ใช่คำตัดสิน") · **ข้อมูลร้านถึง `orders_data_through`**
  - ถ้า `orders_data_covers_window=false` → แถบเตือนอำพัน "ข้อมูลออเดอร์ยังไม่ครบช่วง — ยอดอาจอ่านต่ำกว่าจริง · นำเข้าไฟล์ออเดอร์เพิ่ม" + ปุ่ม/ลิงก์ ≥44px ไป `/crm/import` + (ถ้าระบุช่อง) "ช่อง <orders_channel> ข้อมูลล่าสุด <orders_channel_data_through>" / (ถ้า `orders_major_channels_covered=false`) "ช่องทางหลักบางช่องยังไม่มีข้อมูลหลังวันสุดท้าย"
  - ผล: ฟันธง "ได้ผล/ไม่ได้ผล" ถูก DB ปฏิเสธจนกว่าข้อมูลครบ (55000 ข้อความไทยพร้อมเหตุผล) — **ห้าม** ฝั่งจอปิดปุ่มเองจากเงื่อนไขนี้ (ไม่ซ้ำกฎ — drift) · แสดงข้อความที่ DB ตอบกลับใต้ปุ่มแทน
- (ถ้า metric เป็น `save_rate`/`share_rate`) แสดง `posts_measured_n` ชิ้นที่มีผล T+7 · ไม่คำนวณ "ครบ 4 ไหม" เอง
- **ปุ่ม:** primary "ยืนยันตามที่ AI เสนอ" (ต้องมีกล่องยืนยัน สรุป: คำตัดสิน · บทเรียน · ชิ้นค้าง) · secondary "เลือกคำตัดสินเอง" → แสดงตัวเลือก 4 ข้อ (`<input type="radio">` จริง ในกลุ่ม `fieldset`/`legend` "คำตัดสิน"): ได้ผล · ไม่ได้ผล · ยังสรุปไม่ได้ · วัดไม่ได้ + คำอธิบายสั้นใต้แต่ละข้อ
- ช่อง: "บทเรียน (ไม่บังคับ)" `textarea` ≤ **300 ตัวอักษร** (ไม่ใช่ 500 — migration ตัดเหลือ 300 เพราะส่งต่อเป็นสัญญาณ) พร้อมตัวนับ · "หมายเหตุ (ไม่บังคับ)" ≤1000 · placeholder = คำอธิบายช่อง ไม่ใช่ตัวอย่างข้อความที่ดูเหมือนบทเรียนจริง
- **กล่องยืนยัน** (Modal): ข้อความ "ปิดแคมเปญนี้ด้วยคำตัดสิน: <ป้าย>" · ถ้า `result_open_pieces`/ชิ้น `pieces_open` > 0: **"ยังมีชิ้นงานค้าง <n> ชิ้น — ปิดได้ แต่ชิ้นที่ค้างจะไม่นับในผล"** (Q12 ปิดได้ทุกเมื่อ แต่เตือน) · ถ้ากรอกบทเรียน: "บทเรียนจะถูกส่งเข้า Research เป็นสัญญาณชนิด 'บทเรียน'" · ปุ่ม "ยืนยันและปิดแคมเปญ" / "ยกเลิก"
- **CAS:** submit ส่ง `p_expected_proposed` = `result_verdict_proposed` ที่หน้านี้เห็น (ไม่มี → ส่ง `'none'`) และ `p_expected_token` = `verdict_token` ที่โหลดมา · ได้ 55000 "ข้อเสนอเปลี่ยนไปแล้ว / ข้อมูลแคมเปญเปลี่ยนแล้ว" → แถบ "ข้อมูลเปลี่ยนระหว่างที่เปิดหน้า" + ปุ่ม "โหลดใหม่" ที่ **คงข้อความบทเรียน/หมายเหตุที่พิมพ์ไว้** (ห้ามให้หายตอนรีเฟรช) แล้วให้กดยืนยันใหม่

*(ข) ไม่มีข้อเสนอ และยังไม่ปิด* — การ์ดสงบ: "ยังไม่มีคำตัดสิน" + ข้อมูลที่มี (ชิ้นโพสต์แล้ว/วัดผลแล้ว) + ปุ่ม secondary "ตัดสินเอง…" (เจ้าของเลือกคำตัดสินได้เลยโดยไม่รอ AI — `p_expected_proposed='none'`) · ข้อความ "AI จะเสนอคำตัดสินเมื่อมีผลพอ" **ห้ามสัญญาเวลา**

*(ค) ปิดแล้ว (`result_verdict_confirmed_at` ไม่ null)* — แสดง `result_verdict` (ป้ายใหญ่ + ข้อความ) · "ยืนยันเมื่อ <…> โดยเจ้าของ" · `result_note` · ถ้าต่างจากที่ AI เสนอ แสดง "AI เสนอ: <x> · คุณยืนยัน: <y>" (เก็บทั้งสองค่าไว้ — ไว้ให้เจ้าของเห็นว่าตัวเองกลับคำเสนอ) · `result_open_pieces` > 0 → "ปิดทั้งที่ยังมีชิ้นค้าง <n> ชิ้น (ไม่นับในผล)" · ปุ่ม secondary "เปลี่ยนคำตัดสิน" (DB อนุญาตยืนยันซ้ำ) เปิดกล่องเดียวกับ (ก) + คำเตือนว่าเป็นการทับ

**ส่วน 2 — แผนและเกณฑ์** แสดง: สมมติฐาน (`hypothesis`) · ตัวชี้วัด (map `metric_code` → อัตราบันทึก/อัตราแชร์/คนดูสูงสุดไลฟ์/คนทักกลับ LINE/จำนวนออเดอร์/ไม่วัดผล) · ค่าฐาน `baseline_value` "ณ `baseline_as_of`" + `baseline_note` · เกณฑ์ผ่าน (ถ้อยคำ "ไม่น้อยกว่า/ไม่เกิน" + ตัวเลข) · ช่วงแกว่ง `baseline_spread` · ขอบเขตออเดอร์ (ถ้า orders) ช่วงวัน/ช่อง/กลุ่ม · **คำเตือน `threshold_too_narrow`:** แถบอำพัน + ไอคอน "เกณฑ์นี้แคบกว่าช่วงแกว่งปกติของค่าฐาน — แยกผลจากความบังเอิญไม่ได้" (ข้อความคงที่จาก brief E ข้อ "ถ้าเกณฑ์ผ่านแคบกว่า…")
- ปุ่ม "แก้แผน" → Modal ฟอร์ม (ฟิลด์ตรง `campaign_plan_set`: hypothesis · metric_code · baseline_value · baseline_as_of · baseline_note · pass_op · pass_threshold · baseline_spread · metric_channel_code · metric_affinity · metric_date_from/to) · ส่งเฉพาะ key ที่เปลี่ยน · ล้างค่า = ส่ง JSON `null` · ผลลัพธ์ 42501 ("AI ทับแผนที่เจ้าของตั้งไม่ได้" ไม่เกี่ยวฝั่งเรา) / 55000 "ปิดแล้วแก้ไม่ได้" แสดงตรงๆ · **หน่วยของตัวเลข save_rate/share_rate ยังไม่ยืนยัน (§8.A-Q1)** → ฟอร์มใน P2 รับ "ตัวเลขดิบ" พร้อมคำอธิบายหน่วยหลังได้คำตอบ
- ถ้า `hypothesis` null และ `pieces_total>0` → ข้อความ "ยังไม่ได้ตั้งสมมติฐาน — ตั้งก่อนจึงจะอ่านผลได้" + ปุ่มแก้แผนเป็น primary ของการ์ดนี้

**ส่วน 3 — ชิ้นงานในแคมเปญ (timeline):** `v_content_piece` where `campaign_id` (+shop) เรียง `resolved_start` · แต่ละแถว: วัน · [ContentTypeChip] · ชื่อ · ช่องทาง · [PieceStatusBadge: `effective_piece_status`] · ลิงก์ไปหน้าชิ้นงาน · หัวสรุป "โพสต์แล้ว <posted>/<total> · ยกเลิก <n> · ค้าง <open>" · >20 ชิ้น → "ดูทั้งหมด" ไป `/marketing/pieces?campaign=<id>`

**ส่วน 4 — ผลล่าสุด:** `posts_active_n` · `posts_measured_n` · เหนือปกติ/ปกติ/ต่ำ (`posts_above_n/normal_n/below_n` — เป็นข้อความ+ตัวเลข) · "ณ `latest_t7_on`" · ถ้า `posts_measured_n=0` → ข้อความสงบ "ยังไม่มีผล T+7" (ไม่ใช่ error) · ลิงก์ "ดูผลต่อโพสต์" ไป `/marketing/results?campaign=<id>` (P3 — ก่อน P3 ซ่อนลิงก์)

**ส่วน 5 — บทเรียน:** `lesson` (ถ้ามี · `pre-wrap` ≤300) · ลิงก์ไปสัญญาณ (หลัง P4) · "AI เคยเสนอ" ดูข้างบน

**State 4 แบบ:** *loading* skeleton ตามโครงการ์ด (`CampaignDetailSkeleton`) · *error* `ErrorState` + ลองใหม่ · *empty*: ไม่พบแคมเปญ → `EmptyState` "ไม่พบแคมเปญนี้" + กลับรายการ · *success*: ข้างบน · *forbidden* (staff): `EmptyState icon=Lock` เหมือนหน้าอื่น · **สภาพพิเศษ:** แคมเปญเก่า (ไม่มีชิ้นในระบบใหม่) → ซ่อนส่วน 3 ใส่ข้อความ "แคมเปญนี้ไม่ได้อยู่ในระบบชิ้นงานใหม่" + คงส่วน 1, 2, 4 ถ้ามี metric

### 2.3 กอง 4 "คำถามและข้อเสนอจาก AI" — การ์ด + หน้า `/marketing/questions`

**ที่ใช้:** (1) กองที่ 4 ใน `/marketing` (แสดง ≤3 ใบที่ `effective_action='pending'` เรียง `respond_by` ใกล้สุดก่อน แล้ว `created_at` ใหม่สุด + "ดูทั้งหมด <n>") (2) หน้าเต็มมี 2 แท็บ: **รอตอบ** | **ตอบแล้ว/หมดเวลา** · (3) ใน Weekly Brief เฉพาะข้อเสนอที่ `summary_id` ตรง

**`AiQuestionCard` — แสดงตาม `item_kind`:**

| item_kind | หัวการ์ด | ปุ่ม | เขียนผ่าน |
|---|---|---|---|
| `reco` kind=`question` | "คำถามจาก AI" · `title` · ~`effort_minutes_est` นาที | primary **ตอบ** (เปิดช่องข้อความ ≤1000) · secondary **ปฏิเสธ…** (เหตุผล ≥3) | `recommendation_respond(done\|rejected, response, token)` |
| `reco` kind=`proposal` | "ข้อเสนอ" | primary **ตกลงทำ** (ช่องหมายเหตุไม่บังคับ) · secondary **ไม่ทำ…** (เหตุผล ≥3) | เหมือนกัน |
| `risk_gate` | "ด่านความเสี่ยง" + ชื่อชิ้น | primary **ใช้ได้ (ผ่านด่านนี้)** · secondary **ไปแก้ข้อความที่ชิ้นงาน** (ลิงก์) | `content_gate_record(risk_owner, passed, detail{question,answer})` — ต้องส่ง `question` เดิมกลับ (RPC เขียนทับ detail ทั้งก้อน) |
| `campaign_verdict` | "ยืนยันคำตัดสินแคมเปญ" + `detail` | primary **ไปยืนยันที่หน้าแคมเปญ** (ลิงก์ — ต้องใช้บทเรียน+token) | หน้า P2 (ก่อน P2 แสดงการ์ดอ่านอย่างเดียว ไม่มีปุ่มหลอก: "ยืนยันได้ในหน้าแคมเปญ — เปิดใช้เร็วๆ นี้" **ห้ามทำปุ่มที่ไม่ทำงาน** → ใช้ข้อความ ไม่ใช่ปุ่ม) |

- เนื้อหา: `detail` เป็น **ข้อความธรรมดา** `whitespace-pre-wrap break-words` (D24: ไม่ render markdown) · ตัดที่ 6 บรรทัดมี "ดูเพิ่ม"
- **กล่องค่าเริ่มต้น:** ถ้ามี `respond_by` → "ถ้าไม่ตอบภายใน <respond_by> → <default_action>" + `days_left` ("เหลือ <n> วัน"/"วันนี้เป็นวันสุดท้าย") · `effective_action='expired'` → ป้าย "หมดเวลา · ใช้ค่าเริ่มต้น: <default_action>" (เทา) และยัง **ตอบย้อนหลังได้** (ปุ่ม "ตอบย้อนหลัง" — DB รับ pending หรือ expired+system) · `is_late` ในประวัติ = "ตอบช้ากว่ากำหนด"
- **ช่องตอบ:** `textarea` + ตัวนับ ≤1000 · ห้ามพิมพ์ `[ต้องยืนยัน` (DB ปฏิเสธ — แสดงข้อความตามรหัส) · **ไม่มีอัปโหลดภาพ** (B5) · ข้อความคำแนะนำใต้ช่อง: "วางตัวเลข/ข้อความที่อ่านได้จากภาพ"
- **CAS:** ส่ง `content_token` ของแถวที่เห็น · 55000 "ข้อมูลข้อเสนอเปลี่ยนแล้ว" → การ์ดโหลดใหม่ คงข้อความที่พิมพ์ · 55000 "ตอบแล้ว" → การ์ดย้ายไปแท็บตอบแล้ว + toast สงบ
- หลังตอบสำเร็จ: การ์ดยุบเป็นบรรทัดสรุป "ตอบแล้ว · <ผล> · <เวลา>" (ไม่หายทันทีจนผู้ใช้ไม่มั่นใจ) แล้วออกจากรายการเมื่อรีเฟรช
- **State:** *empty (กอง 4)* ซ่อนทั้งกอง (ไม่ต้องมี "ไม่มีคำถาม" ในหน้าแรกถ้ากองอื่นมีของ) · *empty (หน้า `/questions` แท็บรอตอบ)* `EmptyState` "ไม่มีคำถามรอตอบ" + บรรทัด "ข้อเสนอชุดถัดไปมากับสรุปรายสัปดาห์" (ห้ามระบุวัน) · *error/loading* ตามมาตรฐาน

### 2.4 หน้าชิ้นงาน (F) — สเปกเต็มครบทุกสถานะ

> board มีแต่ PC และวาดสถานะ "รอตรวจ" อย่างเดียว · หน้านี้คือหัวใจ P1a · responsive จริง (ไม่ใช่ 2 ชุด)

**ลำดับ section** (มือถือบนลงล่าง · PC: คอลัมน์หลัก = 1–8, คอลัมน์ข้าง sticky = "ตรวจและอนุมัติ" + "แผน")

1. **หัว:** แถวชิป [ContentTypeChip] [PieceStatusBadge] [ป้ายผู้เขียน "ร่างโดย AI" ถ้า `drafted_by_ai`] [ป้าย "แก้โดยคน" ถ้า `human_edited`] · H1 ชื่อ (`break-words`, ไม่ตัด) · meta: ชนิด · ช่องทาง · วัน + ช่วงเวลา · กลุ่มลูกค้า · แคมเปญ (ลิงก์ P2; ก่อน P2 เป็นข้อความ) · ปุ่มย้อนกลับไปหน้าที่มา (`?from=` → inbox/calendar/pieces)
   - **ป้ายผู้เขียน ≠ สถานะ (5.3):** ป้าย "ร่างโดย AI" = outline เส้นบาง + ไอคอน Bot (ไม่ใช่สีฟ้าทึบแบบสถานะ "AI ร่าง") · "แก้โดยคน" = outline + ไอคอน Pencil
2. **แถบแจ้ง (สูงสุด 3 แถบ เรียงตามความสำคัญ):** (ก) ยกเลิกแล้ว/รอเงื่อนไข (เหตุผลจาก `hold_reason` / event `cancel`) (ข) **"ต้องอนุมัติใหม่"** — ชิ้นเพิ่งกู้คืนจาก approved/produced (อ่าน event `restore.payload.forced_review`) (ค) **"ผลตรวจถูกล้างเพราะเนื้อหาเปลี่ยน: <ด่าน>"** — event `gate` ล่าสุดที่ `payload.reset=true` หลังการ approve/ส่งตรวจครั้งล่าสุด (แสดง `payload.gate_kinds` เป็นชื่อด่านไทย + เวลา)

### 5.2 Accessibility (พื้นฐาน ไม่ใช่ของแถม)

### 5.7 ข้อความ error เป็นไทย

- ใช้ `humanizeRpcError()` ตามภาคผนวก B ทุกที่ (action เดียวกันทั้งแอป) · ตัดชื่อฟังก์ชันนำหน้า (`xxx: `) · แปลง enum ดิบ (`in_review` → "รอตรวจ") · ตัด identifier ในวงเล็บ · ถ้ายังมี identifier เหลือ → ข้อความตามรหัส
- **55000** = เปลี่ยนสถานะไม่ได้/ด่านไม่ผ่าน → ข้อความในกล่องเหนือปุ่ม (inline) ไม่ใช่ toast หาย · **22023** = ข้อมูลไม่ถูกต้อง → ใต้ช่องที่เกี่ยวข้องถ้าระบุได้ · **42501** = "เฉพาะเจ้าของทำรายการนี้ได้" · **23505** = ซ้ำ (บริบทเฉพาะ)
- error ที่แก้ได้เองแสดงวิธีแก้ ("ใส่เหตุผลอย่างน้อย 3 ตัวอักษร") ไม่ใช่ "เกิดข้อผิดพลาด"

### 5.8 ชื่อจริงโฮสต์ · ค่าภายนอก · placeholder

- ชื่อจริงโฮสต์ (`live_host.display_name`) **ห้ามขึ้นจอ ห้ามอยู่ใน payload ที่ส่ง client** — ใช้ `public_label` ("โฮสต์ A/B") · QA ตรวจ `__next_f`/Network หาชื่อจริงที่ seed ไว้ใน DB (grep ค่าจริงจาก DB ไม่ใช่แค่ชื่อคอลัมน์)
- ค่าภายนอกที่ผู้ใช้เห็น/กด (LINE/URL/เบอร์/แฮนเดิล/ราคา) **ไม่มีในแผนนี้ — ถ้าจะใส่ ต้องมีที่มา** · placeholder ใช้คำอธิบาย ("วางลิงก์โพสต์") ไม่ใช่ตัวอย่างที่ดูจริง · `[ต้องยืนยัน]` ในข้อความ = ของ AI ที่ต้องให้เจ้าของกรอก — **UI ห้ามแต่งคำตอบแทน**
- ไม่มีตัวเลขภายใน (ต้นทุน/margin/ค่ากำเหน็จ) ในหน้าเหล่านี้ — view ที่ใช้ไม่มีอยู่แล้ว · ห้าม join ตารางต้นทุนเพื่ออธิบายผล

### 5.9 ทดสอบ

- vitest: ฟังก์ชัน pure (label map ครบ enum · `humanizeRpcError` · parse ตัวเลขย่อ · mask host name · markdown sanitizer · derive `external_id`/platform) · ไม่มี browser automation (กติกา QA ของโปรเจกต์) · อ่านโค้ดแบบ "คนกดจริง" ตามสถานะ
- ก่อนเรียก UAT: `npm run typecheck` + `npm test` + **`npx next build`** · รายงานแยก "ตรวจแล้ว / ยังไม่ได้ตรวจ / จุดที่อยากให้เจ้าของดู" ตาม CLAUDE.md
