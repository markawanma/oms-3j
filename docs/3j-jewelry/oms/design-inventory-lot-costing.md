## มติ: ใช้ FIFO (ของเก่าออกก่อน) ไม่ใช่เฉลี่ยถ่วงน้ำหนัก

**เหตุผลที่ชี้ขาด (เฉพาะธุรกิจนี้ ไม่ใช่ตามตำรา):**

1. **คำเจ้าของคือ FIFO ตรงตัว** — "ยังถือของแพงจาก lot เก่ากี่ชิ้น" คือ state ของ FIFO เอง
   ถ้าเลือกเฉลี่ยก็ยังต้องเขียน FIFO เพิ่มเพื่อตอบคำถามนี้อยู่ดี = งานมากกว่า ไม่ใช่น้อยกว่า
2. 🔴 **ยอดขายเข้าเป็นแบตช์รายเดือน** ⇒ ตอนกด done lot ใหม่ `qty_on_hand` ยังไม่ถูกหัก
   ยอดขายของเดือนนั้น ⇒ เฉลี่ยถ่วงน้ำหนักจะถ่วงด้วยของที่ "ขายไปแล้วแต่ยังไม่ได้นำเข้า"
   **เพี้ยนทุกครั้ง แก้ที่ logic ไม่ได้** ส่วน FIFO ไม่สนจังหวะ reconcile
3. ยกเลิก/ลดจำนวน → คืนเข้า lot เดิมได้เป๊ะ เพราะจดว่าออเดอร์ไหนกินจาก lot ไหน

**Trade-off ที่ยอมรับ**: lot เก่าจะโชว์ขาดทุนจริงเมื่อราคาเงินลง — *นั่นคือสิ่งที่เจ้าของอยากเห็น* ·
หน้าจอโชว์ "ต้นทุนของในมือ" เป็นเลขเดียว (เฉลี่ยถ่วงน้ำหนักของชั้นที่เหลือ) + รายการ lot แยกด้านล่าง
สำหรับคนที่ไม่ใช่นักบัญชี

## โครงสร้าง

- **`analytics.stock_lot`** — 1 แถว = ของเข้า 1 ครั้ง (`source`: production / opening / purchase ·
  `unit_cost` · `qty_in` · `qty_remaining` · `received_on` · `production_order_item_id` unique)
- **`analytics.stock_lot_consumption`** — 1 แถว = (ออเดอร์ × SKU × lot) ใช้คืนของเข้า lot เดิมได้เป๊ะ
- **ใครลด**: `stock_sync_sales` ใน loop iteration เดียวกับ `adjust_stock` (sub-transaction เดียวกัน)
  - `delta > 0` → กินจาก lot เก่าสุดที่ `qty_remaining > 0` ตาม `(received_on, created_at)`
  - `delta < 0` → คืนจาก consumption rows ย้อนจาก lot ใหม่สุด
  - assert ท้ายทุกคู่: `sum(consumption.qty) = qty_applied` ใหม่ ไม่ตรง = raise ตกที่ `last_error`
- **กำแพงชั้น 2**: `constraint trigger … deferrable initially deferred` — SKU ที่ `track_stock`
  ต้องมี `sum(qty_remaining) = qty_on_hand` ตอน commit ⇒ ทางลัดใดๆ ที่แตะ `on_hand`
  โดยไม่แตะ lot จะล้มทั้ง transaction **ไม่เงียบ**

### `cost_type` เปลี่ยนความหมาย

`cost_type` = **วิธีคิดต้นทุนตอนรับของเข้า** เท่านั้น (spot = น้ำหนัก×ราคาเงินวันนั้น · fixed = เลขที่กรอก)
ส่วนต้นทุนที่ใช้รายงาน = ของที่ถืออยู่จริง (lot)

- `production_order_done`: เลิก `set cost_type/unit_cost` บน product → insert `stock_lot` แทน
- `production_cost_calc` / `production_order_preview`: **ไม่แตะ** (คำนวณ "ต้นทุน lot ใหม่" ถูกอยู่แล้ว)
- `v_dim_product`: **ต่อท้าย**คอลัมน์ `lot_qty_on_hand`, `lot_cost_avg`, `lot_next_unit_cost`, `lot_count`
  (`effective_unit_cost` คงความหมายเดิม — `transform` ใช้อยู่ ยังไม่สลับ) · ระวังกับดัก 42P16
- `/catalog`: SKU ที่ track โชว์ 2 เลข — "ต้นทุนของที่มีในมือ" + "ต้นทุนถ้าผลิตวันนี้"
- ป้าย "โหมดต้นทุน" → "วิธีคิดต้นทุนตอนผลิต"

⚠️ นี่เปลี่ยน **กลไก** ของมติ Q1 (17 ก.ย. "ล๊อค ตามนี้เลย") แต่ **เจตนาคงเดิมและแน่นกว่า** —
เหตุที่ Q1 ปฏิเสธ "คง spot" คือกลัว re-import ทำกำไรลอย ซึ่ง lot ปิดช่องนั้นเอง ⇒ **รอเจ้าของยืนยัน (D1)**

### D6 — น้ำหนักแท่ง 1 บาท = **15.244 กรัม** (ยืนยันแล้ว)

ด้วย แต่ตรงนี้ไม่ต้องไปคิด คิดแค่ 15.244 เลย"*

⇒ **ค่าที่ 0134 ตั้งไว้ถูกอยู่แล้ว ไม่ต้องแก้** (`silver_weight_g = 15.244`, `silver_purity = 0.999`)
⇒ ชีตคิดเนื้อเงินที่ ~15.2 ระบบคิดที่ 15.244×0.999 = 15.229 ⇒ **ระบบสูงกว่าชีต ~0.2%**

**อคติที่รู้ตัวและยอมรับแล้ว**: ของผลิตจริงหนักเกิน 15.244 เสมอ (บางครั้งถึง 15.3)
⇒ ต้นทุนจริงสูงกว่าที่ระบบคิดเล็กน้อยเสมอ — **กำไรที่ระบบรายงานจะสูงกว่าความจริงนิดหน่อยตลอด**
เจ้าของสั่งไม่ต้องโมเดลส่วนเกินนี้ ⇒ ห้ามมีใครมา "แก้ให้แม่นขึ้น" โดยไม่ถามเจ้าของก่อน

## ✅ D1 + D3 เจ้าของอนุมัติแล้ว 19 ก.ย. 69 ("เอาเลยทั้ง 2 ข้อ")

### D1 — ย้ายที่ล็อกต้นทุนไปที่ **รอบผลิต**

เจ้าของถามก่อนตัดสิน: *"มันจะงงไหม จะมองว่าไม่ได้เป็น SKU เดียวกับที่ขายหรือเปล่า
หรือว่ามีตัว track ได้ว่าเป็นคนละล๊อทอีกทีนึง แต่อยู่ภายใต้ SKU เดียวกัน"*

คำตอบที่ให้ไป และเป็นสิ่งที่ต้องยึดตอน implement:

| | เปลี่ยนไหม |
|---|---|
| ขายของ | **ไม่เปลี่ยน** — ยังขาย SKU เดิมตัวเดียว ลูกค้า/หน้าร้านไม่เห็นอะไรต่าง |
| ยอดสต็อกหน้าจอ | **ไม่เปลี่ยน** — เลขเดียวต่อ SKU |
| ต้นทุนที่เห็นปกติ | **ไม่เปลี่ยน** — เลขเดียว (เฉลี่ยถ่วงน้ำหนักของชั้นที่เหลือ) |
| สิ่งที่เพิ่มมา | กดดูได้ว่า "60 ชิ้นที่มี = รอบ ม.ค. 10 + รอบ ก.ย. 50" |

🔴 **lot เป็นชั้นข้างล่างของ SKU เดียวกัน ไม่ใช่ SKU ใหม่** — ถ้า implement แล้วหน้าจอทำให้รู้สึกว่า
เป็นคนละสินค้า แปลว่าทำผิดเจตนา

เหตุผลที่ต้องย้าย (จาก F2): ตอนนี้ต้นทุนมี**ช่องเดียวต่อ SKU** ⇒ ผลิตรอบใหม่ทับรอบเก่าหาย และใคร
แก้แคตตาล็อกก็ทับได้ — **เกิดขึ้นจริงแล้ว 18 ก.ย.**: PO-0002 ล็อกต้นทุนตอน 15:23 แล้ว 0134 ทับหาย
ในวันเดียวกัน

### D3 — กำไรเงินแท่งเลิกใช้ ÷1.2

เจ้าของถามก่อนตัดสิน: *"อันนี้คือค่าประมาณหรอ"* — **ไม่ใช่** และนี่คือคำตอบที่ทำให้ตัดสินใจ:

- ค่าประมาณจะแกว่งตามความจริงบ้าง แต่ตัวนี้ออกมา **16.67% เป๊ะทุกบรรทัด 1,605/1,605** ไม่เคยขยับเลยใน 9 เดือน

  ⇒ ระบบไม่เคยบอกว่าเป็นตัวเลขสมมติ

- และมัน **ไม่รู้จักราคาเงินเลย** — เงินขึ้นลง ถือของแพงค้าง ตัวเลขก็ยัง 16.67% เท่าเดิม

**ทำใน 0138 (L2) ไม่ใช่ 0137** — ต้องมี lot ก่อนถึงจะมีต้นทุนจริงให้ใช้
