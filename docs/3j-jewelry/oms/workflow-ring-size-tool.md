## 0. บอกตรงๆ ก่อนเริ่ม (ข้อที่เจ้าของควรรู้ก่อนวาด)

1. **บัตรทับจอ = ปุ่ม/ตัวเลขใต้บัตรกดและมองไม่ได้** บัตรขนาด 85.60 x 53.98 มม. เป็นวัตถุทึบ ถ้าวางโซนควบคุมไว้ใต้บัตร ผู้ใช้จะติดทันที ⇒ จอเทียบขนาดต้องออกแบบให้ "บัตรค้างขอบบนของจอ + ปุ่มอยู่ล่าง" (§3 R2) และจอวัดแหวน/กระดาษก็ต้องแบ่ง "เวทีวัดอยู่บน – ปุ่มอยู่ล่าง" เหมือนกัน
2. **ด้านที่ใช้เทียบคือ "ด้านสั้นของบัตร" (53.98 มม.) เท่านั้น** เพราะด้านยาว 85.60 มม. กว้างกว่าจอมือถือแนวตั้ง (จอกว้างราว 58–72 มม.) — จึงเทียบแค่เส้นซ้าย-ขวา ไม่ต้องวาดกรอบบัตรเต็มใบ
3. **เครื่องมือนี้ตรวจไม่ได้ว่าผู้ใช้ทำถูกไหม** (วางแหวนเอียง ใช้บัตรผิดขนาด) กันได้แค่ด้วยการเช็กช่วงค่าที่สมเหตุสมผล + บอกความแม่นตรงๆ + ทางส่งให้แอดมินเช็กซ้ำทาง LINE — จึงไม่ควรเขียนว่า "แม่นยำ" ที่ใดเลย
4. **ปุ่มเดิม "ส่งไซส์ให้แอดมินทาง LINE" กับ "ดูแหวน/สั่งแหวนไซส์นี้ → LINE" ซ้ำกัน** (ปลายทางเดียวกัน) — เสนอรวมเป็นปุ่มหลักปุ่มเดียว (§3 R6, คำถาม Q3) และเว้นช่อง "ดูแหวนในร้าน (TikTok Shop/Shopee)" ไว้ซ่อนอยู่จนกว่าจะมีลิงก์จริง
5. **ยังไม่มีปลายทางไหนกรองตามไซส์ได้จริง** (SKU แหวนหลายไซส์ยังไม่เสร็จ — ตรงกับที่เจ้าของบอกว่า "ไซส์มันทำยาก") ห้ามตั้งชื่อปุ่มว่า "ดูแหวนที่มีไซส์นี้" เพราะสัญญาเกินที่ระบบทำได้ → ดู §9 ข้อเสนอฝั่งร้าน
6. **ต้องแก้ด่าน auth ของกลาง** — `/ring-size` เป็นหน้าสาธารณะ ต้อง exempt แบบ "path เป๊ะ" ใน `middleware.ts` matcher + `lib/auth/exempt-path.ts` + test (บทเรียน gem-quiz M3: ห้าม exempt ทั้ง subtree · ห้าม look-alike เช่น `/ring-sizes` หลุด) ไม่งั้นลูกค้าโดนเด้งไป `/login`
7. **LINE OA ID ในรีโปไม่ตรงกัน**: `lib/shop/category.ts` ใช้ `3jsilver` (ตัวเองเขียนไว้ว่ายังไม่ยืนยัน) และ `app/(public)/layout.tsx` ลิงก์ `@3jjewelry` — แต่เจ้าของให้ค่าจริงคือ `@3jjewelry` / `https://lin.ee/PzIJl6j` (gem quiz ใช้ค่านี้แล้ว) — เครื่องมือนี้ใช้ค่าจริงของเจ้าของเท่านั้น · ส่วนที่ผิดอยู่นอกขอบเขตงานนี้ แจ้ง Tech Lead แล้ว

## 1. หลักการ user-friendly (ใช้ตัดสินทุกจอ)

| หลัก | วิธีทำในเครื่องมือนี้ |
|---|---|
| ทำทีละขั้น | 1 จอ = 1 งาน = 1 ปุ่มหลัก · ไม่มีฟอร์มยาว · ไม่ถามชื่อ/เบอร์/อีเมล |
| บอกความคืบหน้า | ตัวนับ "1/3 · 2/3 · 3/3" (เทียบจอ → วัด → ผล) · ถ้าเครื่องนี้เคยเทียบจอแล้ว ข้ามขั้น 1 และตัวนับเป็น "1/2 · 2/2" (ใช้ `QuizHeader` ที่มีอยู่ — รับ `current/total` อยู่แล้ว) |
| ภาพประกอบแทนข้อความยาว | ทุกจอสอนมี 1 ภาพ + ไม่เกิน 3 ข้อสั้น (ภาพที่ต้องมี: ดู §5) · ภาพ "ขอบด้านใน ✓ / ขอบนอก ✗" สำคัญที่สุด |
| ปุ่มใหญ่ | ทุกปุ่ม ≥ 48 px (ปุ่มปรับละเอียด −/+ แนะนำ 56 px เพราะกดบ่อย) · ระยะห่างระหว่างปุ่ม ≥ 8 px กันกดพลาด |
| ย้อนกลับได้เสมอ | ปุ่มย้อนบนหน้าจอ **และ** ปุ่ม Back ของเครื่อง/เบราว์เซอร์ (ทุกจอ = 1 history entry — ใน webview Android ปุ่ม Back ที่ไม่ผูก history จะ "ปิดทั้งหน้า" ทำให้ผู้ใช้เสียงานวัด) · ค่าที่วัดแล้วไม่หายเมื่อย้อน |
| ไม่ปล่อยให้ติดทางตัน | ทุก error มีทางไปต่อ 1 ทาง (ลองใหม่) + ทางหนี 1 ทาง (ทัก LINE) |
| น้ำเสียง 3J | ตรงไปตรงมา ไม่ขายฝัน · บอกข้อจำกัดเอง ("คลาดเคลื่อนได้ ±ครึ่งเบอร์") · ไม่ใช้คำว่า "แม่นยำ 100%" |
| ไม่เก็บอะไรที่ระบุตัวคน | ค่าที่จำในเครื่อง = ตัวเลข ไม่มีรูป/ชื่อ/IP · การนับเหตุการณ์ใช้ bucket ไม่ใช่ค่าดิบ (§10) |

## 3. ลำดับจอ (ต่อจอ: เป้าหมาย · องค์ประกอบ · ข้อความ · state · จุดที่คนติด)

> รูปแบบ state ต่อจอ: **โหลด / ว่าง / ผิดพลาด / สำเร็จ** (+ webview ถ้าเกี่ยว) · ข้อความในเครื่องหมาย "..." คือข้อความจริงที่ใส่ได้เลย (ภาษาไทย)

### R0 หน้าแรก

- **เป้าหมาย**: ให้คนรู้ว่าทำอะไร ใช้เวลาเท่าไร ต้องเตรียมอะไร แล้วกดเริ่ม
- **องค์ประกอบ**: โลโก้ 3J (`components/brand/Logo`) · หัวเรื่อง · คำอธิบาย 1 บรรทัด · รายการ "สิ่งที่ต้องเตรียม" 2 ข้อ · ปุ่มหลัก · บรรทัดความเป็นส่วนตัว · (เงื่อนไข) การ์ดเล็ก "ผลล่าสุด" · (เงื่อนไข) บรรทัด "เทียบจอไว้แล้ว"
- **ข้อความ**
  - หัวเรื่อง: "วัดไซส์แหวนด้วยมือถือ"
  - คำอธิบาย: "รู้เบอร์แหวนใน 1 นาที ไม่ต้องไปร้าน ไม่ต้องมีอุปกรณ์พิเศษ"
  - หัวข้อรายการ: "สิ่งที่ต้องเตรียม"
  - ข้อ 1: "บัตร 1 ใบ (บัตร ATM บัตรสมาชิก ใบขับขี่) ไว้เทียบขนาดหน้าจอ"
  - ข้อ 2: "แหวนวงที่ใส่พอดีอยู่แล้ว หรือกระดาษแถบเล็กๆ กับดินสอ"
  - ปุ่มหลัก: "เริ่มวัดไซส์"
  - ความเป็นส่วนตัว: "ไม่ถ่ายรูป ไม่เก็บข้อมูลบัตร ไม่ต้องกรอกชื่อหรือเบอร์โทร"
  - ผลล่าสุด (มีค่าในเครื่อง): "ผลล่าสุดของคุณ: เบอร์ 54" + ปุ่มข้อความ "ดูผลอีกครั้ง"
  - เทียบจอไว้แล้ว: "เครื่องนี้เทียบหน้าจอไว้แล้ว ข้ามขั้นที่ 1 ได้" + ปุ่มข้อความ "เทียบใหม่"
- **state**
  - โหลด: ก่อนอ่านค่าในเครื่องเสร็จ แสดงโครงจอเปล่าที่ไม่มีการ์ด "ผลล่าสุด/เทียบจอไว้แล้ว" (กัน hydration mismatch และกันภาพกระพริบ — อ่าน localStorage ใน `useEffect` เท่านั้น เหมือน `GemQuizClient`)
  - ว่าง (ไม่มีค่าในเครื่อง): แสดงแบบพื้นฐาน ไม่มีการ์ดเงื่อนไข
  - ผิดพลาด: อ่านค่าในเครื่องไม่ได้ (webview บล็อก) = ทำเหมือนไม่มีค่า ไม่แสดงข้อความผิดพลาด
  - สำเร็จ: ไม่เกี่ยว
  - webview: ต้องกดเริ่มได้ทันทีโดยไม่ต้อง login/ขอสิทธิ์ใดๆ
- **จุดที่คนติด / ช่วย**: คนไม่มีบัตรอยู่ข้างตัว (กำลังดูไลฟ์) → หน้านี้บอกล่วงหน้าว่าต้องมีบัตร ไม่ใช่ไปเจอตอนกลางทาง · คนคิดว่าต้องถ่ายรูปมือ → บรรทัดความเป็นส่วนตัวตอบเลย

### R1 สอนเทียบขนาดหน้าจอ (ขั้น 1/3)

- **เป้าหมาย**: เข้าใจว่าทำไมต้องเทียบ + เตรียมท่าวางบัตรที่ถูกก่อนเข้าจอปรับ
- **องค์ประกอบ**: ตัวนับขั้น · ปุ่มย้อน · **ภาพประกอบหลัก 1 ภาพ** (มือถือวางราบบนโต๊ะ มีบัตรวางทับจอแนวตั้ง ปลายบัตรเลยขอบบนจอออกไป เส้นแดง 2 เส้นชิดขอบซ้าย-ขวาของบัตร) · ขั้นตอน 3 ข้อ · กล่องเคล็ดลับ 1 กล่อง · ปุ่มหลัก
- **ข้อความ**
  - หัวเรื่อง: "ขั้นที่ 1 เทียบขนาดหน้าจอ"
  - อธิบาย: "มือถือแต่ละรุ่นแสดงขนาดไม่เท่ากัน เราจึงต้องเทียบกับของจริงก่อน เพื่อให้ 1 มม. บนจอ เท่ากับ 1 มม. จริง"
  - ข้อ 1: "วางมือถือบนโต๊ะเรียบๆ แล้วเร่งความสว่างหน้าจอให้สุด"
  - ข้อ 2: "วางบัตรทับบนจอ แนวตั้ง ให้ปลายบัตรเลยขอบบนของจอออกไปได้"
  - ข้อ 3: "เลื่อนเส้นแดงให้ชิดขอบซ้าย-ขวาของบัตรพอดี"
  - เคล็ดลับ: "คว่ำด้านที่มีตัวเลขบัตรลงได้ เราไม่ถ่ายรูปและไม่เก็บข้อมูลบัตร · ใช้ได้กับบัตรขนาดมาตรฐานทุกใบ (ATM เครดิต บัตรประชาชน ใบขับขี่) · ไม่ควรใช้บัตรที่งอ ขอบบิ่น หรือเล็กกว่าปกติ"
  - ปุ่มหลัก: "เข้าใจแล้ว เริ่มเทียบ"
- **state**: โหลด = ไม่มี (จอคงที่) · ว่าง = ไม่เกี่ยว · ผิดพลาด = ไม่เกี่ยว · สำเร็จ = กดต่อไป R2 · webview: ภาพต้องโหลดได้โดยไม่พึ่ง CDN นอก (ใช้ไฟล์ในโปรเจกต์/inline SVG)
- **จุดที่คนติด / ช่วย**: คนไม่เข้าใจว่า "เลยขอบบนจอ" คือยังไง → ภาพต้องวาดบัตรยื่นพ้นขอบจอจริงๆ · คนกลัวบัตรเสีย/ข้อมูลรั่ว → ประโยคคว่ำบัตร + ไม่เก็บข้อมูล

### R2 ปรับเส้นให้ชิดขอบบัตร (ขั้น 1/3)

- **เป้าหมาย**: ได้ค่า "กี่ px ต่อ 1 มม." ของเครื่องนี้ ภายใน ~20 วินาที
- **ข้อจำกัดกายภาพที่ผู้วาดต้องรู้ (ไม่ใช่เรื่องหน้าตา)**
  1. เวทีเทียบ = พื้นที่ครึ่งบนของจอ มีเส้นแนวตั้ง 2 เส้น (ซ้าย/ขวา) วิ่งเต็มความสูงเวที ระหว่างเส้นเป็นโซนว่าง · **โซนควบคุมทั้งหมดอยู่ล่างเวที** (บัตรไม่ควรบังปุ่ม)
  2. ระยะระหว่างเส้นในสุด = ความกว้างบัตรที่ผู้ใช้ปรับ — เส้นต้องวาด "ด้านนอก" ของระยะนี้ (ขอบในของเส้น = ตำแหน่งที่ตีความว่าเป็นขอบบัตร) → เมื่อพอดี เส้นจะ **โผล่เต็มติดขอบบัตรพอดี**; แคบไป = เส้นถูกบัตรทับ/หาย; กว้างไป = มีช่องว่างสีพื้นระหว่างเส้นกับบัตร ทั้งสองทิศมองเห็นได้ ไม่ต้องเดา
  3. เส้นหนา ~2–3 px สีเข้มตัดกับพื้นขาว (≥ 3:1) ห่างขอบจอ ≥ 12 px (กันจอโค้ง/ขอบเคส) · พื้นเวทีสีอ่อนเรียบ ห้ามมีลายรบกวนขอบ
  4. งานนี้อาศัยการมองด้วยตาล้วน — ต้องมีทางหนีสำหรับคนที่ทำไม่ได้ (ลิงก์ "ให้แอดมินช่วยวัด" → LINE ที่ท้ายจอ)
- **องค์ประกอบ**: ตัวนับขั้น + ย้อน · เวที (เส้น 2 เส้น) · ข้อความสั้น 1 บรรทัดใต้เวที · **แถบเลื่อนหยาบ** (ปรับความกว้าง) · **ปุ่มปรับละเอียด − / +** (ทีละ ≈ 0.1 มม. ของความกว้างบัตร, กดค้างเลื่อนต่อเนื่องและเร็วขึ้น) · ลิงก์ "ดูตัวอย่างพอดี / แคบไป / กว้างไป" (เปิดภาพ 3 ช่อง) · ปุ่มหลักยืนยัน · ลิงก์ช่วยเหลือ "ให้แอดมินช่วยวัดทาง LINE"
- **ข้อความ**
  - คำสั่ง: "เลื่อนจนเส้นแดงชิดขอบบัตรทั้ง 2 ข้างพอดี"
  - คำใบ้ใต้ปุ่ม: "เส้นถูกบัตรทับ = แคบไป · มีช่องว่าง = กว้างไป"
  - ป้ายแถบเลื่อน (สำหรับ screen reader): "ปรับความกว้างเส้นเทียบบัตร"
  - ปุ่ม − : "ลดทีละนิด" · ปุ่ม + : "เพิ่มทีละนิด" · ข้อความกำกับ: "ปรับทีละ ~0.1 มม. กดค้างเพื่อเลื่อนเร็วขึ้น"
  - ปุ่มหลัก: "เส้นชิดขอบบัตรแล้ว"
  - ลิงก์ช่วย: "ปรับไม่ได้? ให้แอดมินช่วยวัดทาง LINE"
  - สำเร็จ (ข้อความสั้นก่อนเข้า R3, ~1 วินาที): "เทียบหน้าจอเรียบร้อย"
- **ค่าเริ่มต้น/ช่วงที่ยอมรับ** (ตัวเลขนี้ให้ frontend ใส่ใน `config` ตั้งต้นจากเหตุผลด้านล่าง ปรับได้หลังทดสอบเครื่องจริง)
  - เริ่มที่ ≈ 6.0 px/มม. (ค่ากลางของมือถือ)
  - ขอบเขตแถบเลื่อน: 3.0 – 9.0 px/มม. และไม่เกินความกว้างจอที่มองเห็นลบขอบ ~15 px ต่อข้าง
  - ช่วง "ปกติของมือถือ" ที่ไม่เตือน: 4.5 – 7.5 px/มม.
- **state**
  - โหลด: ไม่มี (คำนวณฝั่ง client ทันที) · ระหว่างรอ `visualViewport` ให้ปิดปุ่มยืนยันไม่เกิน ~200 ms
  - ว่าง (ยังไม่เคยเทียบ): ค่าเริ่ม 6.0
  - ว่าง (เคยเทียบแต่เครื่องเปลี่ยน — G5): ค่าเริ่ม = ค่าเก่า × (DPR เก่า ÷ DPR ใหม่) + แถบแจ้งข้างบน (ดู §4)
  - ผิดพลาด: **G1 จอถูกซูม** (บล็อก) · **G3 ค่าผิดปกติ** (เตือนหลังกดยืนยัน) · แถบเลื่อนสุดปลายแต่ยังมีช่องว่าง → ข้อความ "จอนี้เล็กเกินกว่าจะเทียบด้านนี้ — ให้แอดมินช่วยวัดทาง LINE แทน"
  - สำเร็จ: บันทึกค่า (ถ้า storage ใช้ได้) → R3 ตัวนับขยับเป็น 2/3
  - webview TikTok/LINE: ห้ามพึ่ง pinch-zoom/สกรอลล์ของหน้า · เวทีใช้ `touch-action: none` เฉพาะเวที (ไม่ปิด zoom ทั้งหน้า — ดู §4)
- **จุดที่คนติด / ช่วย**

### R3 เลือกวิธีวัด (ขั้น 2/3)

- **เป้าหมาย**: ให้ผู้ใช้เลือกวิธีที่ทำได้ "ตอนนี้ ตรงนี้" ในการแตะเดียว
- **องค์ประกอบ**: ตัวนับ · แถบ "เทียบหน้าจอเรียบร้อย" (เล็ก + ลิงก์ "เทียบใหม่") · การ์ดเลือก 2 ใบ (แต่ละใบ: ภาพเล็ก ชื่อวิธี 1 บรรทัด ข้อดี/ข้อจำกัด 1 บรรทัด) · บรรทัดช่วยตัดสินใจ
- **ข้อความ**
  - หัวเรื่อง: "ขั้นที่ 2 เลือกวิธีวัด"
  - การ์ด A ชื่อ: "วางแหวนวงเดิมบนจอ" · รอง: "มีแหวนที่ใส่พอดีอยู่แล้ว · ใช้เวลาราว 30 วินาที · คลาดเคลื่อนราว ±ครึ่งเบอร์"
  - การ์ด B ชื่อ: "พันกระดาษรอบนิ้ว" · รอง: "ไม่มีแหวนก็วัดได้ · ต้องมีกระดาษแถบกับดินสอ · คลาดเคลื่อนมากกว่า (ราว ±1 เบอร์)"
  - ช่วยตัดสินใจ: "ไม่แน่ใจ? ถ้ามีแหวนที่ใส่นิ้วเดียวกับที่จะสวมแล้วพอดี เลือกวิธีแรก"
- **state**: โหลด = ไม่มี · ว่าง = ไม่เกี่ยว · ผิดพลาด = ถ้าเข้ามาตรงนี้โดยไม่มีค่าเทียบจอ (เช่น ลบข้อมูลเบราว์เซอร์กลางทาง) → กลับ R1 พร้อมข้อความ "ยังไม่ได้เทียบหน้าจอ ต้องเทียบก่อนวัด" · สำเร็จ = เลือกแล้วไป R4A/R4B
- **จุดที่คนติด**: ไม่รู้ว่าแหวนวงเดิมต้องเป็นนิ้วไหน → ข้อความรองย้ำ "นิ้วเดียวกับที่จะสวม" ใน R4A

### R4A สอนวัดด้วยแหวนวงเดิม (ขั้น 2/3)

- **เป้าหมาย**: ผู้ใช้เข้าใจ "ขอบด้านใน" ก่อนวัด (จุดผิดที่เจอบ่อยที่สุดของวิธีนี้)
- **องค์ประกอบ**: ภาพหลัก = มองจากด้านบน แหวนวางราบ ลูกศรชี้ "ขอบด้านใน ✓" และ "ขอบด้านนอก ✗" (+ภาพข้างเล็ก: แหวนนอนราบบนจอ) · ขั้นตอน 3 ข้อ · ข้อควรระวัง 1 ข้อ · ปุ่มหลัก
- **ข้อความ**
  - หัวเรื่อง: "วัดด้วยแหวนวงเดิม"
  - ข้อ 1: "เลือกแหวนที่ใส่พอดี และเป็นนิ้วเดียวกับที่จะใส่แหวนใหม่"
  - ข้อ 2: "วางแหวนนอนราบบนจอ ให้รูแหวนอยู่ตรงวงกลมสีแดง"
  - ข้อ 3: "ขยายวงกลมจนเต็มรูแหวน ให้ชิด 'ขอบด้านใน' ของแหวน"
  - ข้อควรระวัง: "วัดที่ขอบด้านใน (ฝั่งที่สัมผัสนิ้ว) ไม่ใช่ขอบนอก · ถ้าแหวนมีหัวสูงจนวางไม่ราบ ให้ใช้วิธีกระดาษแทน"
  - ปุ่มหลัก: "พร้อมแล้ว เริ่มวัด" · ลิงก์รอง: "ไม่มีแหวน? ใช้วิธีกระดาษแทน" (→ R4B)
- **state**: ไม่มี loading/error · สำเร็จ = ไป R5A
- **จุดที่คนติด**: วัดขอบนอกแทนขอบใน → ภาพ ✓/✗ ตัวใหญ่ + ข้อควรระวังตัวหนา · ใช้แหวนที่ปรับหลวม/บิดเบี้ยว → (ใน R5A มีบรรทัดเตือน)

### R5A ปรับวงกลมให้เต็มรูแหวน (ขั้น 2/3)

- **เป้าหมาย**: ได้เส้นผ่านศูนย์กลางด้านใน (มม.) → เส้นรอบวง → เบอร์ พร้อมเห็นตัวเลขเปลี่ยนสดๆ
- **ข้อจำกัดกายภาพ**
  1. วงกลมสีแดงทึบอยู่กลางเวที ตำแหน่งคงที่ — **ผู้ใช้เลื่อนแหวนเข้าหาวงกลม ไม่ใช่ลากวงกลมหนีแหวน** (แหวน+มือบังวงกลม ลากโดยตรงไม่ได้ผลจริง → "ลาก" ทำที่แถบเลื่อนแทน — ปรับจากบรีฟเดิมที่ให้ลากบนวง)
  2. มี **เส้นเล็งกากบาทบางๆ** ผ่านศูนย์กลาง (ช่วยจัดแหวนให้อยู่กึ่งกลาง ช่องว่างรอบวงเท่ากัน) — "ขยาย" ในบรีฟเดิมไม่ทำเป็นแว่นขยายบนจอ เพราะภาพแหวนจริงไม่อยู่ในจอ แว่นขยายจึงไม่ช่วย
  3. เริ่มจากวงเล็ก (ราว 14 มม.) แล้วขยาย → ผู้ใช้เห็น "ช่องว่างหายไป" = จุดพอดี (ทิศเดียวกันตลอด ตีความง่ายกว่าไปๆ มาๆ)
  4. วงกลมทึบ + ขอบเส้นคม: ถ้าเล็กกว่ารู จะเห็นช่องว่างสีพื้นรอบวง · ถ้าพอดี ช่องว่างหมดพอดี
  5. เวทีสูงพอให้แหวนที่เส้นผ่านศูนย์กลางนอก ~27 มม. วางทับได้ โดยปุ่มทั้งหมดอยู่ล่างเวที
- **องค์ประกอบ**: ตัวนับ + ย้อน · เวที (วงกลม + กากบาท) · คำสั่ง 1 บรรทัด · **แถบเลื่อนขนาดวงกลม** (ช่วง 12.0–24.0 มม. ของเส้นผ่านศูนย์กลาง ละเอียด 0.1 มม.) · **ปุ่ม −/+** (0.1 มม./ครั้ง กดค้างเร็วขึ้น) · **ตัวเลขสด** (เส้นผ่านศูนย์กลาง → เส้นรอบวง → เบอร์) · ปุ่มหลัก · ลิงก์ "ต้องทำยังไง" (กลับดูภาพ R4A)
- **ข้อความ**
  - คำสั่ง: "ขยายวงกลมจนไม่เหลือช่องว่างระหว่างวงสีแดงกับขอบด้านในของแหวน"
  - คำใบ้: "ขยับแหวนให้ช่องว่างเท่ากันทุกด้านก่อน แล้วค่อยปรับขนาด"
  - ตัวเลขสด: "ผ่านศูนย์กลาง 17.2 มม. · เส้นรอบวง 54.0 มม. · เบอร์ 54"
  - ปุ่มหลัก: "ใช้ค่านี้"
  - เตือนใต้ปุ่ม: "แหวนต้องนอนราบสนิทกับจอ และไม่บิดงอ"
- **state**
  - โหลด: ไม่มี
  - ว่าง: ค่าเริ่ม 14.0 มม. (ยังไม่แตะ → ปุ่ม "ใช้ค่านี้" ปิดจนกว่าจะปรับอย่างน้อย 1 ครั้ง กันกดผ่านโดยไม่วัด)
  - ผิดพลาด: แถบเลื่อนสุดปลายเล็ก/ใหญ่ → "สุดช่วงที่วัดได้แล้ว — ถ้าวงเล็ก/ใหญ่กว่านี้ ทักแอดมินให้ช่วยดู" + ลิงก์ LINE · **G1 จอถูกซูม** บล็อก · **G4 ค่าผิดปกติ** (เส้นรอบวงนอก 40–75 มม.)
  - สำเร็จ: ไป R6
  - webview: ตัวเลขสดประกาศให้ screen reader แบบหน่วงเวลา (ไม่อ่านทุกการขยับ) · เวทีไม่ให้ scroll หน้า

### R4B สอนวัดด้วยกระดาษพันนิ้ว (ขั้น 2/3)

### R5B ไม้บรรทัดบนจอ วัดความยาวกระดาษ (ขั้น 2/3)

- **เป้าหมาย**: อ่านความยาวแถบกระดาษ (= เส้นรอบวงด้านใน) ได้ละเอียด ~0.5 มม.
- **ข้อจำกัดกายภาพ**
  1. ไม้บรรทัดตั้งแนวตั้งชิดขอบซ้ายของจอ เลข 0 อยู่บนสุด ขีดทุก 1 มม. เลขทุก 5 และ 10 มม. · ต้องยาวถึง ≥ 80 มม. (จอสูงน้อยกว่านี้ → G2 ให้หมุนจอตั้ง)

  3. **เส้นอ่านค่าสีแดง** ยาวข้ามจอ (เลยความกว้างแถบกระดาษ) เพื่อให้เห็นเส้นทั้งสองข้างของแถบ ใช้เทียบรอยดินสอด้วยตา · **ที่จับ (ปุ่มกลมใหญ่ ≥ 48 px) อยู่บนไม้บรรทัดด้านซ้าย** (นิ้วอยู่ห่างรอยดินสอ ไม่บัง) ลากขึ้น-ลงได้ + ปุ่ม −/+ ทีละ 0.5 มม.
  4. ปุ่ม −/+ และปุ่มหลักอยู่มุมล่างที่ไม่ทับแนวไม้บรรทัดใช้งาน (ไม้บรรทัดใช้ 0–80 มม. ≈ 480 px; ที่เหลือล่างต้องพอสำหรับปุ่ม — ถ้าเหลือไม่พอให้ไม้บรรทัดเลื่อนชิดบนขึ้นไปใต้ header)

- **ข้อความ**

  - ตัวเลขสด: "ความยาว 57.5 มม. = เส้นรอบวงด้านใน · เบอร์ 58"
  - ปุ่ม −/+ : "ลด 0.5 มม." / "เพิ่ม 0.5 มม."
  - ปุ่มหลัก: "ใช้ค่านี้"
  - เตือน: "ให้กระดาษแบนราบกับจอ ไม่งอหรือม้วน"

### กติกา "ค่าเทียบจอ" (จำในเครื่อง)

- เก็บ: `{ pxPerMm, dpr, screenShort, screenLong, savedAt, version }` ใน localStorage (try/catch เหมือน `readRetakeFlag`) · ไม่เก็บอย่างอื่น
- **หมุนจอ = ค่ายังใช้ได้** (ใช้ขนาดจอแบบเรียงน้อย/มากเป็นส่วนของ fingerprint; ค่า px/มม. ของ CSS ไม่เปลี่ยนตามการหมุน) · **เปลี่ยนเครื่อง = localStorage คนละใบ** จึงเริ่มใหม่เอง · **ซูมเบราว์เซอร์/เปลี่ยนขนาดจอในตั้งค่าเครื่อง = DPR เปลี่ยน → G5**
- เก็บค่าวัดทุกอย่าง (กรอบบัตร/เส้นผ่านศูนย์กลาง/ความยาว) เป็น **มม.** ใน state แล้วแปลงเป็น px ตอนวาดเท่านั้น → ไม่เพี้ยนเมื่อหมุนจอ/ย่อ-ขยายหน้าต่าง
- **ห้ามปิด pinch-zoom ทั้งหน้า** (`maximum-scale=1`/`user-scalable=no`) — ขัดการเข้าถึง (ผู้สายตาไม่ดี) และ iOS Safari ไม่ทำตามอยู่แล้ว · ทำแทน: (1) `touch-action: none` เฉพาะเวทีวัด (2) ตรวจ `visualViewport.scale` แล้วขึ้น G1 · เหตุผล: ซูมเปลี่ยน px/มม. จริง ค่าเทียบเสียทันที แต่การปิดซูมทั้งหน้าแลกกับคนที่อ่านตัวหนังสือไม่ออก

## 7. เคสที่ "ต้องผ่าน" ก่อนส่งเจ้าของ (ให้ QA)

**ต้องถูกปฏิเสธ/ตักเตือน**
1. ซูมหน้า (scale ≠ 1) ที่จอวัด → ปุ่มยืนยันถูกบล็อกแสดง G1
2. ค่าเทียบ < 4.5 หรือ > 7.5 px/มม. → G3 (ไม่ใช่บล็อกเงียบ ไม่ใช่ผ่านเงียบ)
3. เส้นรอบวง < 40 หรือ > 75 มม. → G4 ไม่ขึ้นผล
4. ค่า localStorage เสีย/แก้เป็นข้อความ/ตัวเลขนอกช่วง → ทิ้งค่านั้น ทำเหมือนไม่มี (ไม่ crash ไม่ใช้ค่าเพี้ยน)
5. DPR เปลี่ยนจากตอนเทียบ → G5 ไม่ใช้ค่าเก่าเงียบๆ
6. ตัวเลขในข้อความ LINE มีเฉพาะเบอร์/มม./วิธี — ห้ามมีข้อมูลอื่น (grep ใน diff)
7. การ์ดแชร์/ข้อความ/หน้าผล ไม่มีตัวเลขราคา ไม่มีคำอ้างสรรพคุณ

**ต้องไม่พัง**
1. หมุนจอกลางจอวัด → ค่ามม.คงเดิม เวทีวาดใหม่ถูกขนาด
2. storage ถูกบล็อก → ทำจบ วัดได้ ได้ผล (แค่ไม่จำค่า)
3. Back ของเครื่องย้อนทีละจอ ไม่ปิดหน้า และค่าที่วัดแล้วไม่หาย
4. ตรวจเกณฑ์ปัดเศษด้วยตารางใน R6 (รวมค่าขอบ 54.25/54.26/54.75 และ −0.01 รอบทศนิยม)
5. ไม่มี `"use server"`/`lib/actions` ใต้ `app/(quiz)/ring-size/**` (กฎเดียวกับ gem quiz §1.2) · และ `/ring-sizes`, `/ring-size-admin` ยังโดน gate
6. เปิดใน Safari/Chrome ปกติ + TikTok + LINE (iOS/Android) → วัด คัดลอก เปิด LINE ได้ทุกชุด
7. ผู้ใช้ที่ login อยู่เปิด `/ring-size` ได้ ไม่ถูกเด้ง `/dashboard` (N-5)

## 8. ระบบเบอร์ + ความแม่น + เหตุผลที่ไม่ใช้ครึ่งเบอร์

- **ระบบเบอร์ = เส้นรอบวงด้านใน (มม.)** ตามมติเจ้าของ · ตรงกับตารางภายในรีโป `docs/3j-jewelry/design-system/05_Ring_Workflow.md` (เบอร์ 54 = เส้นผ่านศูนย์กลางใน 17.20 มม. → 17.20 x π ≈ 54.0) ✓ · เป็นระบบเดียวกับที่ใช้ผลิต จึงส่งแชทให้แอดมินแล้วใช้ต่อได้ทันที `[ต้องยืนยัน: ระบบนี้ตรงกับมาตรฐานสากล (ISO 8653) หรือไม่ — ให้ docs-researcher ยืนยันก่อนเขียนอ้างในหน้า]`
- **วิธี A**: เส้นผ่านศูนย์กลาง d → เส้นรอบวง c = π x d · d ละเอียด 0.1 มม. = c ละเอียด ~0.31 มม. · ความคลาดเคลื่อนรวมประมาณ ±0.5 มม. (≈ ±ครึ่งเบอร์) จาก: ตัดสินช่องว่าง + ขอบในโค้งมน + มุมมอง + ค่าเทียบจอ
- **วิธี B**: c = ความยาวกระดาษ · คลาดเคลื่อนประมาณ ±1 มม. (≈ ±1 เบอร์) จาก: ตำแหน่งขีดดินสอ + กระดาษแนบนิ้วแน่นต่างกัน
- **เหตุผลที่ไม่แสดงครึ่งเบอร์**: ความแม่นจริง ±0.5–1 มม. ทำให้ครึ่งเบอร์เป็นความละเอียดปลอม · ร้านน่าจะทำเป็นเบอร์เต็มเป็นหลัก `[ต้องยืนยัน Q2]` · แสดงค่ามม.ที่วัดได้เป็นบรรทัดรองให้แอดมินตัดสินเองแทน
- **กฎ "ระหว่างเบอร์ → ใหญ่กว่า"** อยู่ที่สูตร `ceil(c − 0.25)` ดู R6 · ผลคือเอนไปทางใหญ่เฉลี่ย ~0.25 เบอร์ ตั้งใจให้ตรงมติ ("อยู่ระหว่างเบอร์ → ใหญ่กว่า")
- **ทางเลือกอื่น (ไม่เลือก)**: ปัดขึ้นเสมอ (ceil ตรงๆ) — ค่า 54.05 กลายเป็น 55 หลวมเกินจากค่าคลาดเคลื่อนเพียงนิดเดียว · ปัดใกล้สุดธรรมดา — ค่า 54.4 เป็น 54 ขัดมติ "ใหญ่กว่า" · ครึ่งเบอร์ — ดูข้างบน

## 9. ข้อเสนอ: เครื่องมือนี้ช่วยปัญหา "SKU แหวนหลายไซส์ทำยาก" อย่างไร (ไม่ออกแบบระบบสต็อก)

บริบท: เจ้าของกำลังสร้างแบบ + SKU แหวนจะปักตะกร้า TikTok Shop / Shopee · ตัวเลือก สี x ไซส์ ทำให้ SKU ระเบิด (แบบ x สี x เบอร์) · เอกสาร `docs/3j-jewelry/oms/system-flow-2026-09.md` §6.3 ระบุว่า TikTok ไทยรองรับตัวเลือก 2 ชั้นพอดี และแถวลูก "สี x ไซส์" ในระบบเรายังไม่เสร็จ

| ข้อเสนอ | เครื่องมือช่วยตรงไหน | ผลต่อร้าน | หมายเหตุ |
|---|---|---|---|
| **S1 ส่งเบอร์มาในแชท แอดมินเลือก SKU ให้** | ข้อความ LINE ฟอร์แมตตายตัว มี "เบอร์ XX" + มม.ที่วัดได้ + วิธีวัด | แอดมินไม่ต้องถามกลับ "นิ้วขนาดเท่าไหร่" · ค้นไซส์ได้ทันที | ทำได้ตั้งแต่ phase 1 ไม่ต้องมี SKU ต่อไซส์ในตะกร้า |
| **S2 ตั้งช่วงเบอร์ที่ร้านมีจริงใน config** | ผลลัพธ์แสดง "ร้านมีเบอร์ {ต่ำสุด}–{สูงสุด}" และกล่อง "นอกช่วง → ถามแอดมิน" | ลูกค้าไม่ถามไซส์ที่ไม่มี · ลดแชทเสียเปล่า | **ช่วงจริง = เบอร์ 45–68 (เจ้าของ 24 ต.ค. 69)** · วัดได้ < 45 หรือ > 68 → กล่อง "เบอร์นี้ร้านยังไม่มี — ทักแอดมิน" ห้ามเดา — ค่าเดียวที่เห็นในรีโปคือแหวนฟรีไซส์ 52–58 ของแบบ Ganesha ซึ่งเป็นสินค้าเดียวไม่ใช่ช่วงทั้งร้าน |
| **S3 เบอร์ที่ไม่มี → แนะนำแหวนปรับไซส์ได้** | กล่องนอกช่วงมีที่ใส่ข้อความ "มีแบบปรับไซส์" | ไม่เสียลูกค้าเบอร์พิเศษ | ใช้ได้เฉพาะเมื่อมีสินค้าปรับไซส์จริง `[ต้องยืนยัน: สินค้า/นโยบายปรับไซส์ — แบบ Ganesha บันทึกว่าช่างปรับก่อนส่ง แต่เป็นแบบเดียว ห้ามเหมาไปทั้งร้าน]` |
| **S4 ลดจำนวน SKU: 1 SKU ต่อแบบ + ไซส์เป็นข้อความตอนสั่ง** | ปุ่ม "คัดลอกเบอร์" + ข้อความกำกับ "ตอนสั่งพิมพ์ในโน้ตว่า ไซส์ 54" | SKU ไม่ระเบิด · สต็อกนับต่อแบบ | แลกกับ: นับสต็อกรายไซส์ไม่ได้ · ต้องมีช่างปรับ/ผลิตตามสั่ง → เป็นการตัดสินใจเชิงธุรกิจของเจ้าของ (Q8) ไม่ใช่ของเครื่องมือ |
| **S5 (ภายหลัง) ลิงก์จากสินค้ามาพร้อมรหัสแบบ** | `/ring-size?item=<รหัสแบบ>` แล้วข้อความ LINE ใส่รหัสแบบให้ด้วย → แอดมินรู้ทั้ง "แบบ + เบอร์" | ตัดคำถามโต้ตอบเหลือศูนย์ | ไม่อยู่ใน phase 1 · ถ้าทำ ต้อง whitelist รูปแบบรหัสแบบ (`[A-Z0-9-]` สั้นๆ) ฝั่ง client เท่านั้น ไม่เชื่อค่าจาก URL เกินที่ validate |

**ข้อแนะนำ**: phase 1 ทำ S1 (+S2 เมื่อมีช่วงจริง) เท่านั้น — ได้ประโยชน์ทันทีโดยไม่ผูกกับการตัดสินใจเรื่อง SKU · S4/S5 รอเจ้าของเคาะโมเดลขายแหวนก่อน เพื่อไม่ออกแบบทับการตัดสินใจธุรกิจ

## 12. Design decision + trade-off + จุดที่ต้อง validate กับผู้ใช้จริง

| การตัดสินใจ | เลือก | ไม่เลือก | เหตุผล |
|---|---|---|---|
| เทียบจอด้วยอะไร | เส้นซ้าย-ขวาเทียบด้านสั้นบัตร ปรับด้วยแถบเลื่อน + ปุ่มละเอียด | วาดกรอบบัตรเต็มใบ / เทียบด้านยาว | ด้านยาว 85.6 มม. กว้างกว่าจอมือถือแนวตั้ง · กรอบเต็มใบกินความสูงจนบังปุ่มควบคุม |
| หลักตัดสิน "พอดี" | เส้นโผล่เต็มชิดขอบบัตร (ผิดทั้งสองทิศมองเห็น) | ให้เล็งกรอบซ้อนบัตร | บัตรทึบ บังกรอบที่เล็กกว่า — ต้องออกแบบให้เส้นอยู่นอกขอบ |
| ซูมหน้า | ตรวจ `visualViewport.scale` + บล็อก (G1) | ปิดซูมด้วย viewport meta | ปิดซูม = ขัดการเข้าถึง และ iOS ไม่ทำตาม |
| วัดแหวน | ลากแถบเลื่อน ไม่ลากบนวง | ลากวงกลมโดยตรง | แหวนและมือบังวงกลม |
| ขยาย | กากบาทเล็ง + เริ่มจากวงเล็ก | แว่นขยายบนจอ | ภาพแหวนจริงไม่อยู่ในจอ แว่นขยายไม่มีข้อมูลให้ขยาย |
| เบอร์ | เต็มเบอร์ + กฎ `ceil(c−0.25)` + แสดง มม. รอง | ครึ่งเบอร์ | ความแม่นจริง ±0.5–1 มม. |
| ปุ่มปลายทาง | LINE เป็นปุ่มหลักเดียว + ช่องร้านซ่อนไว้ใน config | ปุ่ม LINE สองปุ่ม / ลิงก์ร้านที่ยังไม่มี | ไม่แย่งความสนใจ · เปลี่ยนปลายทางภายหลังไม่รื้อ flow |
| เก็บอะไร | ค่า (มม./px) ในเครื่องเท่านั้น | บัญชี/ฟอร์มข้อมูล | ตรงมติไม่เก็บตัวตน · ลดแรงเสียดทาน |

**จุดที่ต้องลองกับคนจริง** (design จับไม่ได้)
1. คนวางบัตร "ค้างขอบบนจอ" ได้ถูกต้องไหม หรือวางกลางจอแล้วบังปุ่ม (ดูว่า I1 ชัดพอไหม)
2. คนเห็น "เส้นโผล่เต็ม/ถูกทับ/ช่องว่าง" ตรงกับที่ออกแบบไหม โดยเฉพาะบัตรสีเข้มและหน้าจอสว่างน้อย
3. สัดส่วนที่เทียบจอสำเร็จภายใน 30 วินาที และสัดส่วนที่เจอ G3
4. คนเลือกขอบ "ใน" ถูกไหม (ถ้าผิดบ่อย เพิ่มภาพ/ข้อความที่ R5A เอง ไม่ใช่แค่ R4A)
5. ข้อความ LINE ที่เตรียมไว้ขึ้นในแชทจริงไหม ในแต่ละชุดเครื่อง/เบราว์เซอร์/webview
6. เบอร์ที่เครื่องมือให้ vs เบอร์ที่ช่างวัดจริงของคนกลุ่มเดียวกัน (ลอง 10–20 คนกับ ring sizer ของร้าน) เพื่อรู้ความคลาดเคลื่อนจริง ก่อนจะเขียนค่า ±ครึ่งเบอร์ในหน้าสาธารณะอย่างมั่นใจ
