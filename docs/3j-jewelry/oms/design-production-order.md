## 🔴 Q1 — คำถามเดียวที่ต้องให้เจ้าของตอบก่อนเริ่ม

**"หลังผลิตเสร็จ ต้นทุน SKU ใน `/catalog` ล็อกตามใบผลิต (ไม่ลอยตามราคาเงินรายวัน) ใช่ไหม"**

- **ใช่** (แนะนำ · design นี้ยึดทางนี้) ⇒ done เซ็ต `cost_type='fixed'` + `unit_cost` = ต้นทุนที่คำนวณวันนั้น
  ⇒ ราคาเงินขึ้นวันหลังไม่กระทบกำไรของล็อตที่ผลิตไปแล้ว ตรงกับกฎเหล็ก
  *"stamp ราคาทุนตามนี้ไปเลย อนาคตถ้ามาปรับราคาไม่ต้องไปแก้กำไรย้อนหลัง"*
- **ไม่ใช่** ⇒ คง `spot` ตามที่ §6.1 เขียนไว้เดิม แต่ต้องรับว่ากำไรย้อนหลังขยับทุกครั้งที่ re-import เดือนเก่า
  — **ไม่แนะนำ** เพราะขัดกฎเหล็กโดยตรง

ถ้าเปลี่ยนใจภายหลัง แก้แค่ ~6 บรรทัดใน RPC `done` ไม่ต้องรื้อโครง

## มติที่ Tech Lead ตัดสินแล้ว (ไม่ต้องถามเจ้าของ)

**1. ลำดับงานเปลี่ยนเป็น P1 → P1.5 → P2** (เดิม P1 → P2 → P1.5)
เหตุผล: ทุกวันที่ P1 อยู่โดยไม่มี P1.5 คือวันที่สต็อก **บวกอย่างเดียวไม่มีวันลด** เจ้าของจะเห็นตัวเลขที่ดูเหมือนจริงแต่ผิด ซึ่งแย่กว่าไม่มีตัวเลข · และ P1.5 หดลงแล้วเพราะคอลัมน์ `track_stock` ย้ายมาอยู่ใน P1

**2. `track_stock` — ย้าย *คอลัมน์* มา P1 แต่ไม่ย้าย RPC toggle**
P1 เพิ่ม `product.track_stock` + `track_stock_since` และให้ RPC done เป็นผู้เปิด · ส่วน toggle บน `/catalog` + ยอดตั้งต้น + guard แม่/ลูก ยังเป็นงานของ P1.5
เหตุผลที่ไม่ปล่อยให้ P1.5 ทำทั้งก้อน: ถ้า P1 ไม่จดวันเริ่มนับ ยอดขายช่วง PO→P1.5 จะถูกตัดซ้ำหรือไม่ถูกตัดเลย

**3. "บวกอย่างเดียว" ชั่วคราว — ยอมรับได้ ภายใต้ 3 เงื่อนไขที่ design บังคับ**
(ก) ตัวเลข **self-heal** — `track_stock_since` + `fact_order_item` ครบ ⇒ reconcile รอบแรกของ P1.5 หักย้อนหลังให้เองโดยไม่ต้องนับของใหม่
(ข) **UI ของ P1 ห้ามมีคำว่า "คงเหลือ" ที่ไหนเลย** — แสดงเฉพาะข้อเท็จจริงของใบ ("ผลิตเข้าแล้ว N ชิ้น เมื่อ …") + ป้ายบน `/stock` ว่ายังไม่หักยอดขาย
(ค) ตอน UAT บอกเจ้าของตรงๆ ว่ารอบนี้ให้ **ต้นทุน + ประวัติผลิต + จุดเริ่มนับ** ยังไม่ให้ยอดคงเหลือ

**4. ข้อครหาว่าขัดกฎ "ห้ามเขียนกลับ catalog" — ไม่ขัด**
กฎนั้น ([[sku-autofill-decisions]] 26 ส.ค.) พูดถึง **ใบเสนอราคา OEM** ซึ่งเป็น snapshot ของดีล · ใบผลิตคือ *เหตุการณ์ที่ทำให้เกิดต้นทุน* และเจ้าของสั่งเองเมื่อ 17 ก.ย. ว่า done ⇒ cost + stock
**บันทึกไว้ที่นี่เพื่อไม่ให้มีใครมาเถียงซ้ำอีกรอบ**

## โครงสร้างที่ตกลงแล้ว

**ตาราง** `analytics.production_order` + `analytics.production_order_item`
- เลขใบ `PO-0001` เป็น generated column จาก `seq` (unique ต่อร้าน) — **ไม่ใช้ `oem_doc_counter`** เพราะไม่ใช่เอกสารทางกฎหมาย เลขข้ามได้
- สถานะ `open → done` / `open → cancelled` · **done และ cancelled เป็นปลายทาง แก้/ลบไม่ได้** บังคับด้วย trigger ไม่ใช่แค่ UI
- `unique (production_order_id, product_id)` — กัน SKU เดิมสองบรรทัดในใบเดียวที่ระดับ schema
- เก็บ `prev_cost_type` / `prev_unit_cost` / `prev_*` ไว้บนใบ ⇒ ตรวจย้อนได้ว่า stamp ทับอะไร โดยไม่ต้องพึ่ง audit log

**RPC 8 ตัว** (service_role เท่านั้น · `search_path` ตรึง · revoke anon/authenticated)
`save` · `item_set` · `item_remove` · `cost_calc` · `spot_resolve` · `preview` · **`done` 💰** · `cancel`
- `preview` ใช้โค้ดเส้นเดียวกับ `done` ลบส่วนเขียน ⇒ **ที่เห็นก่อนกด = ที่จะถูก stamp**
- `done` ทำทั้งหมดใน **1 transaction**: validate ทุกบรรทัดก่อนแตะสต็อกบรรทัดแรก → ensure `central_stock` → `adjust_stock` → เขียนต้นทุนกลับ → พลิกสถานะเป็นบรรทัดสุดท้าย · ล้มตรงไหน rollback หมด ⇒ "ต้นทุน + สต็อก ในจังหวะเดียว" เป็นจริงตามตัวอักษร
- `spot_resolve` — override > ราคาวันนี้ > **raise** · **ห้าม fallback ราคาเมื่อวาน**

**idempotency** `po:<item_id>` เพียงพอ เพราะมี state machine + unique constraint หนุน
กด done ซ้ำ → รอ row lock → เห็น done → คืนผลเดิม ไม่ raise · cancel แล้ว done ใหม่ **เป็นไปไม่ได้** (cancelled เป็นปลายทาง)

**หน้าจอ** section ใหม่ `/production` แยก layout + เมนูจาก OEM ทั้งหมด
`/production` (รายการ) · `/production/new` · `/production/[id]` (แก้ได้ขณะ open · dialog กรอกจำนวนที่ผลิตได้จริง + โชว์ต้นทุนใหม่เทียบเดิมก่อนกดยืนยัน)

## หนี้ที่รู้ตัวตั้งแต่ design

1. **P1.6** — re-import เดือนเก่าหลังมีใบผลิตใบที่ 2 ของ SKU เดิม จะ re-cost ออเดอร์เก่าของ SKU นั้น (transform ลบแล้ว insert ใหม่) · วันนี้ผลกระทบ ≈ 0 เพราะ "เอาเฉพาะของใหม่" (ขายก่อนผลิตไม่ได้) และ **ก่อนมี P1 ช่องนี้เปิดกว้างกว่า** เพราะ spot ลอยทุกวัน ⇒ P1 ทำให้แคบลง ไม่ใช่กว้างขึ้น
2. `stock_ledger.move_type` ยังเป็น `adjustment` — แยกที่มาด้วย prefix `po:` ไปก่อน (ไม่เพิ่ม enum เพราะต้อง replace `adjust_stock` ที่ผ่าน security แล้ว)
3. ไม่มี "ยกเลิกหลัง done" — สต็อกผิดแก้ที่ `/stock` · ต้นทุนผิดแก้ที่ `/catalog` · ต้องผลิตเพิ่มเปิดใบใหม่
4. `/catalog` ยังไม่มีป้ายว่า "ต้นทุนมาจากใบ PO-xxxx"

## เคสที่ต้องไม่ผ่าน (ส่ง security/QA ต่อได้เลย)

20 เคส ครอบคลุม: จำนวนติดลบ/NaN/เกินเพดาน · SKU คนละร้าน · **SKU `^live` (เช็คทั้งตอนใส่ในใบและตอน done เผื่อถูก rename ทีหลัง)** · SKU ปิดใช้งาน · SKU ซ้ำในใบ · done ซ้ำ/done+cancel ชนกัน · แก้ใบที่ปิดแล้วผ่าน service key ตรงๆ · ใบว่าง/ทุกบรรทัดเป็น 0 · spot แต่ไม่มีน้ำหนัก · **ราคาเงินวันนี้ไม่มีและไม่มี override** · override นอกช่วง 5–500 · staff เรียก action ตรง · anon/authenticated เรียก RPC ผ่าน REST

**เคสที่ต้อง "ไม่พัง" ด้วย**: done บน SKU ที่ยังไม่มีแถว `central_stock` (คือ SKU ทุกตัวจาก generator) ต้องผ่าน · done บน SKU ที่เปิดนับสต็อกอยู่แล้ว `track_stock_since` ต้องไม่ถูกเลื่อน · หน้า OEM ทั้งหมดต้องทำงานเหมือนเดิม
