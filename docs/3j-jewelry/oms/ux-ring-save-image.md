> คำสั่งเจ้าของ (คำต่อคำ): "เพิ่มปุ่ม save รูปลงเครื่องให้ลูกค้าด้วยก็ดีเพราะว่าเผื่อยังไม่อยากส่งแต่อยาก save ไว้เลือกดูก่อน"
> ขอบเขต: `/ring-builder` (tools.3jthailand.com · มือถือเป็นหลัก · เข้าจาก LINE/FB/IG/Wix = in-app browser เยอะ) · **client-only: ไม่อัปโหลด ไม่มี endpoint ไม่มี storage ไม่มี track**
> อ่านคู่: `design-ring-line-snapshot.md` §2.1 (`captureFront`) · `ux-tools-navigation.md` (P1d · §16)

## 0. พูดตรงๆ ก่อน

1. **สิ่งที่ผมไม่รู้และห้ามถือเป็นข้อเท็จจริง**: พฤติกรรม Web Share (ไฟล์) / `<a download>` / กดค้างรูปบันทึก ใน LINE in-app, FB/IG in-app, iOS Safari, Android Chrome — ทีมยังไม่เคยทดสอบเครื่องจริง · §3 จึงเป็น **ลำดับ fallback ที่ออกแบบให้ล้มได้ทุกขั้น + ตารางที่ต้องทดสอบ (§3.4)** ไม่ใช่คำสัญญา
2. **"success" ของปุ่มนี้พิสูจน์ไม่ได้ในบางทาง**: `navigator.share()` resolve = ผู้ใช้ปิดเมนูแชร์ ไม่ได้แปลว่ารูปลงอัลบั้ม → **ห้ามขึ้นข้อความ "บันทึกแล้ว ✓"** ในทางนี้ (§4)
3. **ใช้ plumbing ร่วมกับงานแนบรูป LINE**: ต้องมี `captureFront()` ใน gl-renderer + `onCaptureReady(fn|null)` ผ่าน RingViewer → RingStage → RingShowcaseClient (design-ring-line-snapshot §2.1) — ทั้งสองงานแตะ 3 ไฟล์เดียวกัน · **TL ต้องกำหนดว่าใครเพิ่มก่อน ใช้ชื่อเดียวกัน** (ห้ามเขียน 2 ชุด)
4. **ช่องที่ต้องระวังตอน implement (ไม่ใช่การออกแบบ แต่พลาดแล้วภาพเพี้ยนทุกเครื่อง)**: `readPixels` ได้ alpha แบบ premultiplied · ถ้าเอาไป `putImageData` ตรงๆ ขอบแหวนจะมีขอบดำ/halo → ต้อง un-premultiply หรือให้ capture วาดบนพื้นทึบสีเดียวกับเวที แล้วเทสต์ตาที่ขอบแหวนทุกแบบ
5. requirement ไม่ผิด แต่เจ้าของไม่ได้บอกว่าอยากได้ **มุมหน้า** หรือ **มุมที่ลูกค้าหมุนไว้** — brief จาก TL ระบุมุมหน้า ผมใช้เป็นค่าเริ่มต้น (Q1)

## 2. ปุ่ม — ตำแหน่ง และถ้อยคำ

### 2.1 ตำแหน่ง
ในกล่องสรุป ใต้ปุ่ม LINE (หลัก) — **แถวเดียวสองคอลัมน์ของปุ่มรอง: `คัดลอกข้อความ` | `บันทึกรูป`**

| ทาง | ผล | ตัดสิน |
|---|---|---|
| ปุ่มเต็มความกว้างอันที่ 3 ต่อท้าย | ชัด แต่ 3 ปุ่มสูง 56 เรียงกันยาว ดันข้อควรทราบลงไป · ดูเป็น 3 ทางเลือกเท่าๆ กัน | ตัด |
| ไอคอนบนเวที 3D (มุมภาพ) | ใกล้ภาพที่จะ save · แต่เวทีมีป้าย "ภาพจำลอง" + "ลากเพื่อหมุน" + จุดแล้ว แน่นแล้ว · ไอคอนเปล่าเสี่ยงไม่เข้าใจ · ปุ่มแตะชนกับการลาก | ตัด |
| **แถวรองคู่ (เลือก)** | จัดกลุ่มตามงาน: "ส่ง" (LINE) ชัดเป็นหลัก · "เก็บไว้ดูเอง" (คัดลอก/บันทึก) เป็นรองคู่กัน · primary มีอันเดียว ตรง principle | **เลือก** |

- ปุ่มรอง 2 อัน `min-h-14` (เท่าปุ่มคัดลอกเดิม) · ขอบ/สีเท่า `คัดลอกข้อความ` เดิมทุกประการ (outline) — **ไม่ใช้สีแดง burgundy ทึบ** ไม่แย่งปุ่ม LINE
- ที่ฟอนต์ใหญ่ (≥150%) / จอแคบ: grid `grid-cols-2` → ตกเป็น 1 คอลัมน์เมื่อข้อความตัดบรรทัด (`grid-cols-[repeat(auto-fit,minmax(9.5rem,1fr))]`) ไม่ truncate
- ลำดับ DOM = ลำดับตา: LINE → คัดลอก → บันทึกรูป
- ปุ่มมีไอคอนถาดลูกศรลง 20px (`aria-hidden`) นำหน้าข้อความ — ไอคอนช่วยแยกจาก "คัดลอก" เมื่อสแกนเร็ว ไม่ใช่ตัวสื่อความหมายเดียว

## 3. กลไกบันทึก — ลำดับ fallback

### 3.1 ลำดับ (ออกแบบให้ล้มได้ทุกขั้น ไม่มีทางตัน)
```
กด [บันทึกรูป]
 │ ปุ่มเป็น busy → captureFront(1080,810) → compose 1080×H → toBlob(jpeg .92) → File
 │ (ผิดอะไรก่อนถึงขั้นนี้ = ขั้น E)
 ▼
A. navigator.canShare?.({files:[file]}) เป็นจริง?
   ├─ ใช่ → await navigator.share({files:[file]})   ← ไม่ส่ง title/text/url (ไม่พาลิงก์ไปกับรูป)
   │         ├─ resolve            → จบ เงียบ (ห้ามอ้างว่าบันทึกแล้ว)
   │         ├─ AbortError          → ผู้ใช้ยกเลิก = จบ เงียบ (ไม่ใช่ error)
   │         └─ NotAllowedError / อื่นๆ → ไป C  (เช่น gesture หมดอายุหลัง await)
   └─ ไม่ → C
C. เปิด PreviewSheet: รูป <img src=objectURL> + คำแนะนำ "กดค้างที่รูปเพื่อบันทึกลงเครื่อง"
   + ปุ่มใน sheet `บันทึกรูป` (gesture ใหม่ + ไฟล์พร้อมแล้ว → ลอง A ซ้ำแบบ sync) + ปิด
E. ล้ม (capture null / พิกเซลว่าง / toBlob null / เกิน 8 วิ) → ข้อความ saveFailed ใต้แถวปุ่ม · ปุ่มกลับมากดซ้ำได้
```

### 3.2 ทำไมลำดับนี้ (trade-off)
| ทาง | ข้อดี | ข้อเสีย/ความเสี่ยง | ตัดสิน |
|---|---|---|---|
| **A Web Share พร้อมไฟล์** | ทางที่ใกล้ "กดทีเดียว → เลือกบันทึกรูปภาพ" ที่สุด บน iOS | ไม่รู้ว่า in-app browser ส่วนไหนรองรับ · บน Android เมนูแชร์อาจไม่มี "บันทึกลงแกลเลอรี" โดยตรง · gesture ต้องไม่หมดอายุระหว่างสร้างภาพ (~ร้อยมิลลิวินาที) | **ขั้น 1** |
| **C เปิดรูปให้กดค้าง** | ไม่พึ่ง API ใหม่ ใช้ได้ในเกือบทุก webview ที่ให้กดค้างรูป (ไม่ยืนยัน) · ผู้ใช้เห็นภาพก่อนบันทึกด้วย | ต้องรู้ว่า "กดค้าง" · เพิ่ม 1 จอ · iOS กดค้างรูปที่มาจาก blob URL ใช้ได้ไหมใน LINE in-app `[ต้องทดสอบ]` | **ขั้น 2 (ตาข่ายนิรภัย)** |
| `<a download>` | ง่าย | iOS Safari ลงโฟลเดอร์ Files ไม่ใช่อัลบั้ม (ลูกค้าหาไม่เจอ) · in-app browser ส่วนใหญ่เมิน/เปิดรูปในหน้าเดียวกัน = ผู้ใช้หลุดจากหน้าแหวนเสียงานค้าง · ปุ่มที่ "ไม่เกิดอะไรขึ้น" แย่กว่าไม่มี | **ไม่ใส่ใน v1** — เพิ่มเป็นขั้นเสริมเฉพาะถ้าผลทดสอบ Android ชี้ว่า A+C ไม่พอ |
| เปิดแท็บใหม่ด้วยรูปเต็มจอ | | ออกจากหน้า · popup blocker · in-app ค้างแท็บ | ตัด (ใช้ sheet ในหน้าแทน) |

เงื่อนไขกัน gesture หมดอายุ: ไม่ทำงานหนักก่อน `share()` เกิน capture+compose+toBlob · ถ้าทดสอบพบว่าเครื่องกลางๆ ล้มที่ A บ่อย → เปลี่ยนเป็น **"สร้างภาพรอไว้เมื่อกล่องสรุปเข้าจอ (idle)" แล้วกดแล้ว share ทันที** (ยังเป็น client-only) — ตัดสินหลังทดสอบ ไม่ทำล่วงหน้า (YAGNI + กินแบตเมื่อไม่ได้ใช้)

PreviewSheet: `role="dialog"` `aria-modal` · หัว `saveSheetTitle` · `<img alt>` = รายละเอียดทั้งหมดเป็นข้อความ (แบบ · พลอย · ไซซ์ · ราคา — จาก helper เดียวกัน) · ปุ่มปิด ≥44px · Esc ปิด · focus trap · คืนโฟกัสไปปุ่ม `บันทึกรูป` · `URL.revokeObjectURL` ตอนปิด/unmount · โครงยกจาก `LeaveSheet` ถ้า P1c merge แล้ว ไม่งั้นยกจาก `G3Sheet` (ring-size) ไม่เขียนใหม่ (ผมไม่ได้เปิด G3Sheet — ให้ frontend ตรวจ)

### 3.3 ทำไมสร้างตอนกด ไม่ใช่ล่วงหน้า
ไม่ต้องมี timer/observer/หน่วยความจำค้าง · ไม่มี state ใหม่ถาวร · แลก: รอ ~0.3–1 วิ ตอนกด (แสดง busy) — ความเสี่ยงของ gesture ดูข้อบน

## 4. State ครบ 4 ของปุ่ม + เคสเครื่องไม่รองรับ 3D

| สถานะเวที (RingStage) | ปุ่ม `บันทึกรูป` |
|---|---|
| `ready` และ `href !== null` (ไซซ์ถูก) | **ปกติ กดได้** |
| `checking` / `loading` (ชั่วคราว) | แสดง แต่ `disabled` + ข้อความใต้แถว `saveWaitStage` |
| `lost` (กู้เองได้) | `disabled` + `saveWaitStage` · กลับมา ready เองแล้วปุ่มเปิด |
| `designFailed` (มีปุ่มลองอีกครั้งบนเวที) | `disabled` + `saveWaitStage` (เวทีมีปุ่ม "ลองอีกครั้ง" อยู่แล้ว) |
| **`unsupported` (ไม่มี WebGL / โหลด chunk ไม่ได้) — ถาวร** | **ซ่อนปุ่ม** (แถวรองเหลือ `คัดลอกข้อความ` เต็มความกว้าง) |
| `href === null` (ไซซ์ผิด) | ซ่อนเหมือนปุ่ม LINE (ข้อความเตือนเดิมโชว์อยู่) |

ทำไม unsupported = ซ่อน ไม่ใช่ disabled: ไม่มีทางออกให้ผู้ใช้ (รูปถ่ายจริงใช้แทนไม่ได้ — สีพลอยไม่ตรง Z6; ภาพที่มีแต่ข้อความซ้ำกับ "คัดลอกข้อความ") ปุ่มที่กดไม่ได้ถาวรสร้างความสงสัย · แลก: คนไม่รู้ว่าฟีเจอร์มี — ยอมรับ

| State | สิ่งที่เห็น / ได้ยิน |
|---|---|
| **Loading** | ข้อความปุ่ม = `saveBusy` · `disabled` + `aria-busy="true"` · กดซ้ำไม่ได้ · `role="status"` ประกาศ "กำลังสร้างรูป" · เกิน 8 วิ → ไป Error |
| **Empty** | = เวทียังไม่พร้อม/ไม่รองรับ (ตารางบน) — ไม่มี "ข้อมูลว่าง" แบบอื่น (ทุกแบบมีค่าเริ่มต้น CZ ขาว) |
| **Error** | `saveFailed` ใต้แถวปุ่ม (`role="alert"` · ไอคอน+ข้อความ ไม่พึ่งสี · ปรับสไตล์เหมือนแถบเตือนไซซ์ เฉดกลาง ไม่แดงตกใจ) · ปุ่มกลับมากดซ้ำได้ · เหตุ: capture คืน null / พิกเซลว่างทั้งภาพ / `toBlob` null / เกินเวลา · **ไม่ใช่ error**: ผู้ใช้ยกเลิกเมนูแชร์ |
| **Success** | A → เมนูระบบเปิด/ปิดแล้วปุ่มกลับปกติ **ไม่มีข้อความยืนยัน** (พิสูจน์ไม่ได้) · C → PreviewSheet คือผลลัพธ์ · ไม่มี toast "บันทึกแล้ว" |

เหตุการณ์ที่ต้องไม่พังระหว่าง busy: ผู้ใช้ลากหมุนแหวน/เปลี่ยนแบบ/เปลี่ยนพลอย → ภาพที่ได้ = ค่าตอนเริ่มจับ (สร้างจาก snapshot ของ input ตอนกด ไม่ใช่ state ที่เปลี่ยนทีหลัง) · unmount ระหว่างทำ → ไม่ setState/ไม่เปิด sheet

## 5. ตรวจ P1d ปุ่ม "แก้" กับหน้าปัจจุบัน — ผล: **เข้ากันได้ ปรับ 4 จุด**

ตรวจกับโค้ดปัจจุบัน (`RingShowcaseClient` / `OrderSummary`):
- ลำดับการ์ดจริง: เวทีติดบน → header → **DesignPicker → ModeSwitch → (Intention+GemSet | OwnGem) → SizePicker → PhotoGallery → OrderSummary** — ลำดับ design → gems → size ที่ P1d วางไว้ยังตรง ✅ (PhotoGallery คั่นระหว่าง size กับสรุป ไม่กระทบ)
- scroller มี `scroll-pt-[46dvh]` (มือถือ) อยู่แล้ว → หัวข้อที่เลื่อนไปไม่ถูกเวทีติดบนบัง (N14) ✅ แต่ต้องตรวจตา 375×667
- ราคาต่อแบบ (790 / 890): แถวราคายังไม่มี "แก้" ✅ · เปลี่ยนแบบแล้วราคาในสรุปเปลี่ยนตาม (`formatPriceThb(design.id)`) — ประกาศ `designAnnounce` เดิมมีราคาอยู่แล้ว
- drag hint จุดขาว: อยู่ที่ RingStage state `hintDone` (ไม่ remount ตอนเปลี่ยนแบบ) · กด "แก้" ไม่ทำให้เล่นซ้ำ ✅ · ไม่อยู่ใน GL → ไม่ติดภาพบันทึก ✅
- แบบเม็ดเดี่ยว: ไม่มีหัวข้อพลอยรายเม็ด/หลัก-เสริม — แถว "พลอยเม็ดเดี่ยว" ยังแก้ได้ (target = OwnGemPicker เดิม) ✅

**ปรับ spec P1d (เขียนทับของเดิมเฉพาะข้อเหล่านี้):**
1. **"แก้" ปรากฏแถวเดียวต่อกลุ่ม**: แถว `แบบแหวน` · แถว `พลอย` (แถวแรกของกลุ่มพลอย) · แถว `ไซซ์` — **ไม่ใส่ในแถวย่อย** (พลอยหลัก/เสริม · แถวช่วงสีรายเม็ด · CZ เล็ก) เพราะแถวเหล่านี้เพิ่มลดตามแบบ ทำให้ปุ่มซ้ำ 3–7 อัน
2. **ไซซ์ที่ยังไม่เลือก**: ปุ่มเปลี่ยนคำเป็น `เลือก` (`aria-label="เลือกไซซ์"`) แทน `แก้` — "แก้" บนค่า "รอแอดมินช่วยเช็ก" ไม่บอกว่าทำอะไรได้
3. **target ของแถวพลอย**: โหมดแนะนำ → หัว `อยากเสริมเรื่องไหน` · โหมดเลือกเอง → หัว `พลอยที่คุณเลือกได้` · ถ้าหา element ไม่เจอ (เช่นหัวถูกยุบหลังเลือกเรื่อง) = ไม่ทำอะไร ไม่ throw (state table เดิม) — **frontend ต้องเปิดดูว่าหัวยังอยู่ใน DOM หลังเลือกเรื่องหรือไม่ (ผมไม่ได้เปิด IntentionPicker)**
4. **dl ที่มีปุ่ม**: แถวยืดตามปุ่ม `min-h-11` (44) · ค่าทางขวา `min-w-0` ตัดบรรทัดได้ ไม่ truncate · ปุ่ม "แก้" ชิดขวาสุดเป็นคอลัมน์เดียวกันทุกแถว ไม่แตะแถวราคา

ความสัมพันธ์กับปุ่ม `บันทึกรูป`: **ไม่ชนกัน** — "แก้" อยู่ใน `dl` ด้านบน · ปุ่มบันทึกอยู่ใต้ LINE · หลังกด "แก้" เวทีติดบนแสดงผลแหวนที่เปลี่ยนทันที ผู้ใช้กลับลงมากดบันทึกได้เลย · ภาพที่บันทึก **ไม่มี** ปุ่ม "แก้" (วาดจาก helper ไม่ใช่จาก DOM)
props ที่ OrderSummary รับเพิ่ม (additive ทั้งหมด): `onEdit?` (P1d) · `capture?: (() => …) | null` หรือ callback ที่ให้ภาพ (บันทึกรูป) — ไม่มี prop = ไม่แสดงปุ่ม/ไม่แสดง "แก้" (เทสต์เดิมไม่ต้องแก้)

## 9. Trade-off หลัก + ที่ต้อง validate กับผู้ใช้จริง

1. **ปุ่มรองคู่ แทนปุ่มที่ 3 เต็มความกว้าง** — ได้ primary ชัดอันเดียว แลกกับปุ่มกว้างครึ่งเดียว (ที่ฟอนต์ใหญ่ตกเป็นแถวเดี่ยว)
2. **ลำดับ share → sheet (ไม่มี download)** — ล้มได้ทุกขั้น แต่ขั้น A บน Android อาจไม่นำไปสู่แกลเลอรี (ต้องทดสอบก่อนปล่อย)
3. **ไม่ยืนยัน "บันทึกแล้ว"** — ซื่อตรง แต่ลูกค้าบางคนอาจไม่แน่ใจว่าสำเร็จ → ถ้า validate แล้วพบว่างง ให้เพิ่มคำแนะนำหลังปิดเมนู (ข้อความกลาง ไม่อ้างผล)
4. **มุมหน้าเสมอ** — เปรียบเทียบง่าย แลกกับลูกค้าที่หมุนไปมุมโปรด
5. **ภาพยืดความสูงตามแถว** — ไม่ตัดข้อมูล แลกกับขนาดไม่เท่ากัน
6. **ราคาในภาพ** — ใช้เทียบได้จริง แลกกับราคาค้างเมื่อเปลี่ยน (ลดด้วยวันที่)

validate กับผู้ใช้จริง: (ก) ลูกค้ากดแล้วได้ภาพในอัลบั้มจริงไหม ใน LINE/FB/IG in-app (ข) คนเห็นปุ่ม `บันทึกรูป` ไหม/เข้าใจว่าต่างจาก `คัดลอกข้อความ` ไหม (ค) ลูกค้าใช้ภาพนั้นต่ออย่างไร (ส่งให้คนอื่น? โพสต์?) — ถ้าส่งต่อบ่อย อาจต้องทบทวนเรื่อง QR/ทางกลับ ภายใต้ข้อจำกัดนโยบายแพลตฟอร์ม

## 10. คำถามเจ้าของ (ไม่รู้ = `[ต้องยืนยัน]` ห้ามเดา)

- **Q1** [ต้องยืนยัน] ภาพที่บันทึก = **มุมหน้าเสมอ** (ค่าเริ่มต้น) หรือ **มุมที่ลูกค้าหมุนไว้**?
- **Q2** [ต้องยืนยัน] ใส่ **ราคา + "ราคา ณ วันที่บันทึก"** ในภาพ (ค่าเริ่มต้น: ใส่) — หรืออยากให้ภาพไม่มีราคา?
- **Q3** [ต้องยืนยัน] ภาพ **ไม่มีลิงก์/QR/LINE ID** (ค่าเริ่มต้น เพราะนโยบาย TikTok/Shopee) ใช่ไหม — ใส่แค่ชื่อแบรนด์ `3J · JEWELRY`
- **Q4** [ต้องยืนยัน] ไม่วัดคลิกปุ่มนี้ (ค่าเริ่มต้นตามมติ Q7 เดิม · ถ้าอยากวัดต้อง migration allowlist `cta` แยกงาน)
- **Q5** [ต้องยืนยัน] ถ้อยคำปุ่ม: `บันทึกรูป` (ค่าเริ่มต้น) หรือ `เซฟรูป`?

## 11. ข้อจำกัดของ spec นี้

- ไม่ได้เปิด `IntentionPicker` · `OwnGemPicker` · `G3Sheet` · `LeaveSheet` · `RingViewer` ทีละไฟล์ — target ของ "แก้" และโครง sheet ให้ frontend ตรวจกับของจริง
- `captureFront()` และ `buildShowcaseDetailRows()` **ยังไม่มีใน worktree นี้** (ตรวจแล้ว) — spec ตั้งอยู่บนว่า TL จะให้เพิ่ม
- ไม่ได้ทดสอบ Web Share / กดค้างรูป / ฟอนต์ canvas บนเครื่องจริงใดๆ — §3.4 เป็นรายการทดสอบ ไม่ใช่ผล
- ขนาดไฟล์ JPEG, เวลาสร้างภาพบน Android ระดับกลาง ยังไม่วัด
