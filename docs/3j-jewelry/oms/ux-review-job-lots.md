## 1. สรุป

1. **23 แถว (21 ไฟล์): ✅ 4 · ⚠️ 16 · ❌ 3** — โครง flow ของเจ้าของ (หน้างานเปิดใบ 8 ขั้น · ส่งต่อ n จาก N · QR เดียว · ใบแม่ · เสร็จแล้วรอส่ง) ตรง workflow และมติเกือบทั้งหมด ไม่ต้องวาดใหม่ · ❌ 3 จุด = ปุ่มข้อความหมายเหตุขัดมติ ค6 · จอ L-6 ตัวเลขผิด (66 ควรเป็น 65 + เสีย 1) และไม่มีสถานะปิดปุ่ม · ใบย่อย "QR ตัวเดิม" ทำซ้ำไม่ได้ในระบบ token ปัจจุบัน
2. **เรื่องเงินบนหน้าช่าง/หน้างาน: ผ่านทุกจอ** (ไม่มีตัวเลขเงิน · ใบส่งของไม่มีราคา/ชื่อลูกค้า · L-6 ไม่มีเงิน) — ข้อควรระวังตอน implement มี 4 ข้อ (ส่วน 2.3) โดยเฉพาะข้อความ error ของ L-6 และ payload แคตตาล็อกพลอย/สินค้าที่เปิดให้ช่องทางสาธารณะ
3. **ปัญหาโครงสร้าง 3 ข้อที่กระทบหลายจอ**: (X1) ไม่มีทางเข้าหน้าช่างระดับร้าน — คิวงาน L-1 เข้าจากไหนไม่มี เพราะ `/w/[token]` ของจริงผูกกับ QR ต่อใบ · (X2) QR ใบงานของจริงออกครั้งเดียวตอนพิมพ์ + พิมพ์ใหม่เพิกถอนของเก่าเป็นค่าเริ่ม → ชนกับใบย่อย/ใบส่งของหลายใบถือ QR พร้อมกัน · (X3) บอร์ดของจริงมีคอลัมน์ตามขั้น + ป้ายหลัก/รอง — mock ทำเป็น grid ต่อใบ ต้องบอกว่าใบแม่ที่ของกระจายหลายขั้นไปอยู่คอลัมน์ไหน
4. **ผลรวมจำนวนบวกไม่ลง 3 จุด** (ส่วน 2.2): L-6 "เหลือ 66 เดินต่อ" · ตัวนับ "เสร็จแล้ว รอส่ง" 34 vs 45 คนละจอ · ตัวกรอง "ยังไม่รับทราบ 3" แต่การ์ดบนบอร์ดโชว์ป้ายนั้นแค่ 1 ใบ
5. **ต้องถามเจ้าของ 7 ข้อ** (ส่วน 6) + ประเด็นเทคนิค 10 ข้อส่ง architect/security (ส่วน 6.2 — ไม่ใช่คำถามเจ้าของ) · ลำดับทำ 6 ชุด UAT (ส่วน 7) · **มติใหม่ "เผื่อเสียไม่บังคับ" ตรงกับ W-3 แล้ว** ส่วนที่ต้องแก้คือฟอร์ม M1 ฝั่งออฟฟิศ (ส่วน 3)

**สถานะปัจจุบัน (อ่านจาก `wt-job-m1-ui`):** `JobCreateDialog` ตั้ง `qtyText = qty` (จำนวนสั่ง) แล้วมี `useEffect` ที่ **ทับช่อง "เริ่มผลิต" ด้วย `planData.qtyPlannedEff` อัตโนมัติ** เมื่อผู้ใช้ยังไม่แตะ (ค่านั้น = จำนวนแนะนำจาก reject rate เมื่อ rate ครบ) แล้วส่งเป็น `qtyPlanned` ถ้าต่างจากจำนวนสั่ง · `QtyFields` มีกล่องคำแนะนำสีฟ้า "แนะนำ N ชิ้น (เผื่อ b) … [ใช้ค่าแนะนำ]" อยู่แล้ว — **ชิ้นส่วนที่ต้องการมีเกือบครบ ขาดแค่ "สวิตช์" กับ "เลิกเติมให้เอง"**

### 3.1 หน้าตา

ปิด (ค่าเริ่มทุกครั้งที่เปิดกล่อง):
```
จำนวนที่ต้องการเข้าสต็อก        100 ชิ้น        (อ่านอย่างเดียว — OEM: "จำนวนที่สั่ง")
[ ปิด ○ ]  เผื่อของเสีย (ไม่บังคับ)
           ปิดอยู่ = เริ่มผลิตเท่าที่ต้องการ (100 ชิ้น)
```
เปิด:
```
[ ● เปิด ]  เผื่อของเสีย
เผื่อเพิ่ม (ชิ้น)   [ − ] [  5  ] [ + ]            → เริ่มผลิต 105 ชิ้น  · ป้าย "เผื่อ +5"
┌ กล่องฟ้า (คำแนะนำ — ไม่เติมให้เอง) ───────────────────────────────┐
│ ระบบแนะนำเผื่อ +5 (เริ่มผลิต 105 ชิ้น): หล่อเสีย a% · ขัด b%  [ใช้ค่าแนะนำ] │
└────────────────────────────────────────────────────────────────┘
```
ใช้ชิ้นส่วนเดิม: `Field` · `FIELD` · กล่องฟ้า/เหลืองใน `QtyFields` · `Button` · โทนสีจาก `StatusChip` (ไม่เพิ่มสีใหม่) · สวิตช์ใหม่ `QtyBufferToggle` = `<button role="switch" aria-checked>` สูง ≥ 44px มี label ผูกข้อความ (ไม่ใช้ checkbox พรางตัว)

### 3.2 กติกา

| # | กติกา |
|---|---|
| R1 | เปิดกล่องใหม่ = **ปิดเสมอ** (ไม่จำค่าครั้งก่อน) · `qtyText` เริ่ม = จำนวนสั่ง |
| R2 | **ปิด**: ช่อง "เริ่มผลิต" ไม่แสดง (ซ่อน ไม่ใช่ปิดใช้งาน) · ตอนสร้างไม่ส่ง `qtyPlanned` (DB ใช้ค่าเริ่ม = จำนวนสั่ง ตามคอมเมนต์ใน `JobCreateDialog`) · **เรียก preview ด้วย `qtyPlanned = qtyOrder` ชัดๆ** ไม่ใช่ `null` เพื่อให้แผนโลหะคิดจากจำนวนสั่ง ไม่ใช่จำนวนแนะนำ · dev ต้องตรวจว่า `job_plan_suggest` คืน `qty_planned_eff` เป็นอะไรเมื่อรับ `null` (ปัจจุบันคือจุดที่ทำให้เติมเอง) |
| R3 | **เปิด**: `b` เริ่ม 0 · ห้าม prefill ด้วยค่าแนะนำ · กล่องฟ้าแสดงเสมอเมื่อ DB ตอบแนะนำได้ · ปุ่ม "ใช้ค่าแนะนำ" ตั้ง `b = แนะนำ − จำนวนสั่ง` · ซ่อนปุ่มเมื่อ `b` เท่าค่าแนะนำแล้ว (พฤติกรรมเดิมของ `qtyValue !== suggest`) |
| R4 | `b` เป็นจำนวนเต็ม ≥ 0 ผ่าน `parseQtyText`-style strict ("1,5" "3.5" = error ไม่ตัดเงียบ) · เพดานตามที่ DB ตอบ (แสดงข้อความ DB) — ไม่เดาตัวเลขเพดานใน UI |
| R5 | เปิดแล้วอัตรา reject ยังไม่ครบ → ใช้กล่องเหลืองเดิม "ยังไม่มีอัตราเสียของ […] จึงไม่แนะนำเผื่อ — ตั้งที่ จัดการต้นทุน" · พิมพ์ `b` เองได้ตามปกติ · preview error (กล่องเหลือง "คำนวณจำนวนแนะนำไม่ได้") แสดง **เฉพาะตอนเปิดสวิตช์** · ตอนปิดไม่ขวางการสร้าง |
| R6 | ปิดสวิตช์ขณะ `b > 0` → รีเซ็ต `b = 0` ทันที ไม่ถามยืนยัน + `aria-live="polite"` อ่าน "เริ่มผลิต 100 ชิ้น" |
| R7 | ใช้ทั้ง `kind = production` และ `oem` (ป้ายจำนวนเปลี่ยนตามเดิม) |
| R8 | อัตรา reject % และตัวเลขแนะนำ **ไม่ไหลไป `/w/` หรือใบพิมพ์** (กติกาเดิมใน `QtyFields`) · หน้างาน W-3 จึงไม่มีกล่องแนะนำ — ถูกแล้ว |
| R9 | "ผลิตบางส่วน" (เริ่มผลิต < จำนวนสั่ง) ตอนสร้างทำไม่ได้อีก (b ≥ 0) · ยังทำได้ผ่าน `QtyPlannedDialog` "แก้จำนวน" ตามเดิม ตราบที่ขั้นแรกยังไม่ถูกรับ `[ตรวจกับเจ้าของใน UAT M1 ว่ามีใช้ตอนสร้างไหม]` |

### 3.3 ใบที่มีอยู่แล้ว / ป้าย

| ที่ | แสดงยังไง |
|---|---|
| ใบเดิมที่ `qty_planned = qty_order` | เหมือนวันนี้ทุกประการ ("30 ชิ้น" ตัวเลขเดียว · ไม่มีป้าย) |
| ใบที่ `qty_planned > qty_order` (เผื่อไว้แล้ว) | ไม่ต้อง migrate/backfill · `PlanCard` แถว "เริ่มผลิต 105 ชิ้น" + ป้าย "เผื่อ +5" · ข้อความรวมใช้ `qtyOrderPlannedText` เดิม ("สั่ง 100 · เริ่มผลิต 105 ชิ้น") |
| บอร์ด `JobCard` | ป้ายรอง key ใหม่ `buffer` "เผื่อ +n" โทน sky (คู่กับ `underPlanned`) · rank หลัง 10.1 · ไม่ขึ้นเมื่อ `qty_planned ≤ qty_order` |
| `QtyPlannedDialog` (แก้จำนวนภายหลัง) | ใช้ `QtyBufferToggle` ตัวเดียวกัน สถานะเริ่ม = เปิดถ้า `planned > order` · กติกา "แก้ได้จนขั้นแรกถูกรับ" ของเดิมไม่เปลี่ยน (การแก้หลังเริ่ม = มติ ข4 ให้ architect) |
| หน้าช่าง `/w/` | หัวใบแสดง "N ชิ้น" = `qty_planned` อย่างเดียว (ช่างผลิตเท่านี้) ไม่มีป้ายเผื่อ ไม่มี % |
| A5 / ใบย่อย | `qtyOrderPlannedText` ที่มีอยู่แล้ว ไม่ต้องเขียนใหม่ |

### 3.4 ทดสอบ

- **ต้องไม่พัง:** (1) เปิดกล่อง → ช่องเริ่มผลิตไม่ถูกเปลี่ยนเองหลัง preview ตอบ (ถอด `useEffect` ที่ทับ) · (2) ปิด → ใบที่สร้าง `qty_planned = qty_order` ทั้งเมื่อ rate ครบ/ไม่ครบ · (3) เปิด `b=5` → 105 + โลหะที่ต้องเตรียมคิดจาก 105 (จาก DB ไม่ใช่ client) · (4) "ใช้ค่าแนะนำ" ตั้ง b ถูก · (5) rate ไม่ครบ + เปิด → กล่องเหลือง + พิมพ์ b ได้ · (6) preview error + ปิด → สร้างได้ · (7) ใบเดิมที่ `planned > order` แสดงป้าย ใบที่เท่ากันไม่แสดง
- **ต้องปฏิเสธ:** `b` ติดลบ · "1,5" · "3.5" · ค่าว่าง/ตัวอักษรขณะเปิด · เกินเพดาน DB
- **ผลข้างเคียงที่ต้องรู้:** เมื่อปิดเป็นค่าเริ่ม ของเสียทุกชิ้นกลายเป็น "ขาด" ตอนปิดใบ (ดี < สั่ง) → ออฟฟิศต้องใส่เหตุผลบ่อยขึ้น (ฉ3) → Q2

## 6. คำถามถึงเจ้าของ (เฉพาะที่ตัดสินเองไม่ได้จริง) — ✅ ตอบแล้ว ดู 6.0

> ตอบเป็นข้อ เช่น "Q1 = C" · ข้อไหนไม่ตอบ = ใช้ข้อแนะนำ (ตัวหนา)

**Q1. ใครกด "ส่งเข้าสต็อก" บนมือถือได้ — ช่าง QC หรือช่างแพ็ก?** มติ ฉ1 เขียน "ช่างแพ็ก" แต่ ฉ2 บอก "เสร็จ = ผ่าน QC (แพ็กไม่ใช่การผลิต)" และจอที่ออกแบบ (L-6) เป็นช่าง QC · ขั้น QC กับแพ็กเป็นคนละขั้นต่อกัน
- A. เฉพาะช่างขั้น QC (ตรงจอที่วาด · ของผ่าน QC = พร้อมเข้า)
- B. เฉพาะช่างขั้นแพ็ก (ตรงตัวอักษร ฉ1 · ของถึงมือแพ็กก่อนเข้าสต็อก)
- **C. ทั้งสองขั้น กดได้ — เพดาน = จำนวนที่ผ่าน QC แล้วและยังไม่เข้าสต็อก** (แนะนำ: ทั้งสองกรณีไม่มีใครติด · ด่านจริงอยู่ที่จำนวน ไม่ใช่ชื่อขั้น)
- ผลต่อระบบ: กำหนดสิทธิ์ของ RPC ส่งเข้าสต็อก (ต้อง security ผ่านก่อน merge)

**Q2. ขาดจากของเสียล้วนๆ — ออฟฟิศต้องพิมพ์เหตุผลทุกใบไหม?** เมื่อ "เผื่อของเสีย" ปิดเป็นค่าเริ่ม ชิ้นเสียทุกชิ้นทำให้ดี < สั่ง ⇒ ทุกใบที่มีของเสียต้องกดปิดเอง (มติ ฉ3)
- A. พิมพ์เหตุผลทุกครั้ง (ตรงมติตัวอักษร)
- **B. ถ้า ดี + เสียที่บันทึก = เริ่มผลิต (ของเสียอธิบายส่วนขาดครบ) ระบบเติมเหตุผล "ของเสียระหว่างผลิต n ชิ้น" ให้ ออฟฟิศกดปิดได้เลย · ถ้ายังขาดมากกว่าของเสียที่บันทึก (ของหาย) ต้องพิมพ์เหตุผลเอง** (แนะนำ: ลดงานซ้ำ แต่ยังบังคับตัดสินใจเมื่อมีของหายจริง)
- C. ปิดเองเงียบทุกกรณี (ขัด ฉ3 — ไม่แนะนำ)
- ถ้าตอบ B = แก้มติ ฉ3 บางส่วน ต้องเขียนทับ §9.1

**Q3. ช่างยกเลิกการ "ส่งออกนอกร้าน" เองได้นานแค่ไหน?** มติ ข3 = ยกเลิกเองได้ถ้ายังไม่มีใครกดรับ แต่ผู้รับจ้างไม่ได้กดรับในระบบ ⇒ "ยังไม่มีใครรับ" จะเป็นจริงตลอดจนรับกลับ ทั้งที่ของออกจากร้านไปแล้ว
- A. ตามตัวอักษร: ยกเลิกได้จนกว่าจะรับกลับ (เสี่ยงข้อมูลไม่ตรงของจริง)
- B. ยกเลิกได้ภายใน `[ต้องยืนยัน: กี่นาที]` หลังกดส่ง
- **C. ส่งนอกร้านแล้ว ช่างยกเลิกเองไม่ได้ ต้องออฟฟิศยกเลิก + เหตุผล (ส่งในร้านยังยกเลิกเองได้จนกว่าคนรับจะกดรับ ตามมติ)** (แนะนำ: ของนอกร้านผ่านกระดาษเซ็นแล้ว ไม่ควรให้กดย้อนจากมือถือ)

**Q4. ช่างส่งของออกนอกร้านตอนเย็น/กลางคืน (ออฟฟิศปิด) ใบส่งของ 2 ฉบับ (เซ็น) จะมาจากไหน?** มติ ง6 = พิมพ์ 2 ฉบับเซ็น 2 ฝ่าย · ฌ2 = ออฟฟิศพิมพ์เช้าถัดไป · ฉ1 workflow = ไม่มีเครื่องพิมพ์ที่หน้างาน (ถ้าไม่ตอบ)
- A. ห้ามของออกก่อนมีใบส่งของ — ช่างกดส่งออกได้เฉพาะตอนออฟฟิศพิมพ์ใบให้ได้
- **B. ช่างกดส่งออกได้ตลอด · ออฟฟิศพิมพ์ใบส่งของเช้าถัดไป · ผู้รับจ้างเซ็นย้อนหลังรอบถัดไป (ของที่ออกคืนนั้นไม่มีลายเซ็นจนกว่าจะถึงเช้า)** (แนะนำ: ตรงมติ ฌ2 · ไม่ขวางงานกลางคืน)
- C. มีเครื่องพิมพ์ที่หน้างาน `[ค่าจริง: รุ่น/ที่ตั้ง]` ช่างพิมพ์เอง
- ถ้าตอบ B ร้านต้องยอมรับความเสี่ยงของที่ออกก่อนมีลายเซ็น

**Q5. ช่างรับของแล้วจำนวนไม่ตรงกับที่คนส่งบอก (ปุ่ม "ได้ไม่ครบ?" บน L-4) ทำยังไง?** มติไม่ได้พูดถึง · ระบบบังคับ "รับ = ส่งของขั้นก่อน" ที่ security/QA ผ่านแล้ว
- **A. ตัดปุ่มออกรอบแรก — จำนวนไม่ตรง = ไม่กดรับ · ให้ผู้ส่งยกเลิกส่วนแล้วส่งใหม่ (มติ ข3) หรือแจ้งออฟฟิศ** (แนะนำ: ไม่แตะโซ่จำนวน · ไม่ต้องสร้างกติกาใหม่)
- B. ปุ่ม "แจ้งไม่ตรง" ส่งธงให้ออฟฟิศ ไม่แก้ตัวเลขเอง
- C. รับตามจริง + ส่วนต่างเป็น "หายระหว่างส่งต่อ" (ต้องออกแบบกติกาใหม่ ชนโซ่จำนวน)

**Q6. QR ร้านใบเดียวใช้ทั้ง "เปิดงานใหม่" และ "คิวงานของฉัน" ได้ไหม?** มติ ก3 = QR "เปิดงานใหม่" 1 จุด · ช1 = คิวงานช่างเปิดจาก QR (ไม่ระบุว่า QR ไหน) · ของจริงไม่มีทางเข้าที่ไม่ผูกใบ (X1)
- **A. QR ร้านใบเดียว → ชื่อ + PIN → เลือก "คิวงานของฉัน" หรือ "เปิดงานใหม่" (เฉพาะคนติ๊กสิทธิ์ ก2)** (แนะนำ: QR น้อยที่สุด · ใช้ PIN เดียว)
- B. แยก 2 QR (เปิดงานใหม่ / คิวงาน) — ป้ายแปะ 2 จุด แต่คนไม่มีสิทธิ์เปิดงานไม่เห็นเมนูเปิดงานเลย
- C. คิวงานเข้าจากการสแกน QR ใบงานใบใดก็ได้ (ต้องมีใบในมือก่อน — วันไม่มีงานค้างเข้าไม่ได้)
- ถ้าตอบ A: QR ที่พิมพ์ต้องเปลี่ยนป้ายจาก "เปิดงานใหม่" เป็น "QR ร้าน"

**Q7. [เงิน] ต้นทุนแบบ "คำนวณจากสเปค" (ก้อนยาง/แฟลสก์/ค่าแบบ) เข้าสต็อกเป็นงวดแล้วคิดยังไง?** ของจริง `ProductionDoneDialog` ต้นทุนต่อชิ้นของสินค้าแบบสเปคขยับตามจำนวนชิ้นที่ผลิต (คอมเมนต์ในไฟล์ระบุว่าจำนวนชิ้นน้อยลง = ต้นทุนต่อชิ้นสูงขึ้น เพราะก้อนยาง/แฟลสก์/ค่าแบบหารด้วยจำนวนชิ้น) — งวดแรก 34 ชิ้นจะหารก้อนค่าใช้จ่ายด้วย 34 · workflow แบ่งล็อตไม่ได้พูดถึง
- **A. หารด้วย "เริ่มผลิต" ของใบ (ทั้งใบ) ใช้ต้นทุนต่อชิ้นเท่ากันทุกงวด ต่างกันเฉพาะราคาเงินของวันที่เข้า** (แนะนำ: ต้นทุนต่อชิ้นไม่ผันตามวิธีแบ่งงวด)

### จุดที่ต้อง validate กับผู้ใช้จริง (design จับ usability ไม่ได้ทั้งหมด)

1. ช่างอ่านคำ "ส่วนที่ n" และ "ส่วนหลัก" แล้วรู้ว่าหมายถึงถุงไหนหรือไม่ — ลองกับช่างฝัง/ช่าง QC 1 คน (workflow แผน L0)
2. ช่างตอนกลางคืนใส่ n ส่งต่อถูกไหม โดยเฉพาะเมื่อมีของเสีย (กล่อง 3 ช่อง เสีย/ส่งไป/ค้าง)
3. ใบแม่ที่ของกระจายหลายขั้นควรอยู่คอลัมน์ไหนในมุมมองตามขั้น (X3) — ให้ออฟฟิศลองใช้จริง 3 วัน
4. หัวหน้าช่างใช้ hub สองปุ่มแล้วสับสนไหม (Q6) · ค่าเริ่ม "ยังไม่กำหนด" ของกำหนดเสร็จ
5. ใบส่งของ: ผู้รับจ้างอ่านน้ำหนัก "ประมาณ" แล้วเข้าใจหรือโต้แย้งหรือไม่ (ผู้รับจ้างอาจชั่งเอง)

### ข้อจำกัดของการรีวิวนี้

- รีวิวจาก mockup + โค้ด/เอกสารที่อ่าน — **ไม่ได้ยิงหน้าจริง ไม่ได้ตรวจ DB สด** (เช่น สัดส่วน SKU ที่มีน้ำหนักต่อชิ้น ในส่วน T10 อ้าง skill ไม่ใช่ข้อมูลสด)
