| P7 | **หน้างานกรอก "น้ำหนัก/ชิ้น" ของทอง แล้วช่างขั้นชั่งจะเห็นไหม?** — มติ N1 ห้ามโชว์น้ำหนักขั้นก่อน/ที่ถือ/ประมาณแก่ช่างทอง | ถ้า `target_piece_g` โผล่บนจอช่าง = ช่างรู้เป้า ชั่งให้ตรง | ไม่ออกแบบให้โชว์ที่ไหนบนจอช่างทอง · ถาม §C.2 Q6 |

| P9 | **"SKU นี้มีใบเปิดอยู่แล้ว" = บล็อกเด็ดขาด** แต่ออฟฟิศเองเปิดหลายใบ SKU เดียวกันได้ (PO-0003/0015 มี spot) | ผู้จัดการอยากเปิดล็อตที่ 2 ไม่ได้ ต้องโทรหาออฟฟิศ | ออกแบบเป็นบล็อกตามบรีฟ + บอกเลขใบที่ชน · ถามว่าควรเป็น "ยืนยันเปิดซ้ำ" ไหม §C.2 Q7 |

- ปุ่มใช้ `aria-disabled="true"` + `aria-describedby` ชี้บรรทัดเหตุผล (ไม่ใช้ `disabled` จริง เพราะ disabled ไม่รับ focus/ไม่ถูกอ่าน — ผู้ใช้คีย์บอร์ดจะไม่รู้ว่าทำไม) · กดตอน aria-disabled = scroll ไปเช็คลิสต์ ไม่เปิด dialog
- ลำดับเหตุผลบรรทัดใต้ปุ่ม (แสดงข้อแรก + "ติดอีก n ข้อ"): ① แก้ไว้ยังไม่บันทึก ② ยังไม่รับทราบ ③ ยังไม่ผูก SKU ④ น้ำหนัก/ชิ้นขาด ⑤ (เดิม) ไม่มีรายการ

| ข้อติด | ข้อความ (บรรทัดใต้ปุ่ม / เช็คลิสต์) | รู้จากอะไร |
|---|---|---|
| แก้ไว้ยังไม่บันทึก | `มีรายการที่แก้ไว้แต่ยังไม่บันทึก — กด "บันทึกรายการ" ก่อน` | state การ์ด (dirty) — **สำคัญ**: DB อ่านค่าที่บันทึกแล้วเท่านั้น ปล่อยผ่าน = ต้นทุนคิดจากค่าเก่าเงียบๆ |
| ยังไม่รับทราบ | `ใบนี้เปิดจากหน้างาน — ต้องกดรับทราบก่อน` | `openedVia='shopfloor' && !acknowledgedAt` |
| ยังไม่ผูก SKU | `ยังไม่ผูก SKU ให้ "{ชื่อแบบ}" — ผูกก่อน ระบบถึงคิดต้นทุนและเข้าสต็อกได้` | item.productId == null |
| น้ำหนักขาด | `ยังไม่ระบุน้ำหนัก/ชิ้นของ {sku} — ต้นทุนโหมดนี้ต้องใช้น้ำหนัก` | cost_type spot/spec + weightG null (ไม่เช็คกับ fixed) |

เหตุผลที่รู้ได้ตอนกดเท่านั้น (ต้องมี preview): **ราคาทองวันนี้ไม่มี** → แสดงใน dialog (§A.7) · ไม่ทำ pre-check ราคาที่หน้า (ถ้า architect ให้ `missing_prices` ใน view ได้ค่อยยกมาเป็นข้อที่ 5 — §C.3 R3)

## A.3 `ProductionItemCard` — 1 การ์ด/รายการ (แทนตารางแถวเดียว)

เลียน `QuoteJobItemCard` ด้วย primitive ร่วม (ตัดสินแล้วใน design §3 ข้อ ค) — **ลำดับช่องเหมือนหน้า OEM**: วัสดุ → ความบริสุทธิ์ → น้ำหนัก → จำนวน → แบบใหม่

กติกาช่อง

| ช่อง | ใช้ | พฤติกรรม |

| วัสดุ | `MetalRadioRows` (radiogroup 3 ตัว ปุ่ม ≥ 44px) | **ช่องแรกของการ์ดเสมอ** (R6 ในดีไซน์) · เปลี่ยนโลหะ → เนื้อรีเซ็ตเป็นค่าเริ่มของโลหะใหม่ (เงิน 92.50 · ทองเหลือง 100.00 · ทอง **ว่าง**) เหมือน OEM (`OEM_DEFAULT_PURITY`) + ข้อความเล็ก `เนื้อรีเซ็ตตามโลหะใหม่` · น้ำหนักที่ "มาจาก SKU" และ SKU เป็นเงิน → เปลี่ยนเป็นทอง/ทองเหลืองแล้ว**ล้างทิ้ง** + `ล้างน้ำหนักจากสินค้าแล้ว (ใช้กับเงินเท่านั้น)` · น้ำหนักที่พิมพ์เอง = คงไว้ |
| ความบริสุทธิ์ (%) | `PurityPctInput` เดิม (ห้ามทำช่องใหม่) | ทอง: ว่างตอนสร้าง + ป้าย `*บังคับกรอก` (เหมือน OEM) · ผิดกติกา (ทศนิยม > 2 · < 37.50 · > 100 · "0.925") = ข้อความของ `purity.ts` เดิม · บันทึกตอนว่าง/ผิด → `forceShow` + focus ช่องนั้น · **ทองเหลือง = ล็อก 100.00 อ่านอย่างเดียว** (ดู §C.2 Q9) · เงิน = แก้ได้ ค่าเริ่ม 92.50 |
| น้ำหนัก/ชิ้น (กรัม) | `<input inputMode="decimal">` ใช้ `inputCls` | ไม่บังคับตอนสร้าง · >0 และ ≤ 10,000 · ทศนิยม ≤ 3 · ข้อความ `น้ำหนักต้องมากกว่า 0 และไม่เกิน 10,000 กรัม (ทศนิยมไม่เกิน 3 ตำแหน่ง)` · **ห้ามเดาจากชื่อ SKU** (`oem-quote-invariants` ข้อ 9) · ค่าว่างจาก SKU (fixed 284 ตัวไม่มีน้ำหนัก) = ช่องว่างจริง ไม่ใส่ 0 · ป้ายใต้ช่อง `จาก SKU` / `แก้ในใบนี้` (เปรียบเทียบกับค่า SKU — แสดงผลอย่างเดียว) |
| จำนวน | เดิม (`min 1 · max 100000 · integer`) | |
| แบบใหม่ | checkbox เดิม | โชว์เฉพาะ SKU โหมด spec (เหมือนเดิม) · รายการไม่มี SKU = ซ่อน (ยังไม่มีโหมดต้นทุน) |
| บันทึกรายการ | `Button` primary sm | enabled เมื่อ dirty · **การ์ดละปุ่ม** · สำเร็จ → toast `บันทึก {sku/ชื่อแบบ} แล้ว` + `router.refresh()` |

**Trade-off: บันทึกต่อการ์ดแบบกดปุ่ม ไม่ใช่ auto-save ตอน blur** (ต่างจาก `MetalPriceCell`) — เหตุผล: เนื้อทอง/น้ำหนักขับต้นทุนทั้งล็อต พิมพ์ผิดแล้ว blur = เขียน DB ทันที · ข้อเสีย: ลืมกดบันทึก → ปิดแก้ด้วยป้าย `ยังไม่บันทึก ●` + ข้อติดในเช็คลิสต์ "แก้ไว้ยังไม่บันทึก" (§A.2) + `beforeunload` เตือนเมื่อมีการ์ด dirty

### A.3.2 โลหะเปลี่ยนไม่ได้ (มีใบงานเดินอยู่)

radiogroup ทั้งกลุ่ม `aria-disabled` + บรรทัด `เปลี่ยนโลหะไม่ได้ — มีใบงาน JB-0031 เดินอยู่ · ยกเลิกใบงานก่อน แล้วแก้โลหะ` · เนื้อ/น้ำหนัก/จำนวนยังแก้ได้ · น้ำหนักที่แก้หลังมีใบงาน **ไม่ไปแก้ `target_piece_g` ของใบงาน** → ข้อความเล็ก `น้ำหนักเป้าของใบงานไม่เปลี่ยนตาม — แก้ที่ใบงานถ้าต้องการ`

### A.3.3 ไม่มี SKU (ออฟฟิศสร้างทางเดียวกับหน้างาน)

```
┌────────────────────────────────────────────────────────────────────────────┐
│ [◇ เงิน] ไม่มี SKU · แหวนทดลองลายใบไม้     [⚑ ยังไม่ผูก SKU]   30 ชิ้น  [🗑] │
│ ต้นทุน: ยังคิดไม่ได้ — ต้องผูก SKU ก่อน                                     │ ← ไม่ใช่ "—" ไม่ใช่ 0
├────────────────────────────────────────────────────────────────────────────┤
│ ชื่อแบบ *   [ แหวนทดลองลายใบไม้______________________ ]  (≤ 60 ตัวอักษร)    │
│ (วัสดุ / ความบริสุทธิ์ / น้ำหนัก / จำนวน — เหมือน A.3.1)                      │
│                                                         [บันทึกรายการ]     │
│ ┌ ผูก SKU ──────────────────────────────────────────────────────────────┐ │
│ │ ผูกแล้วเปลี่ยนไม่ได้ · เนื้อ/น้ำหนักของรายการนี้ไม่เปลี่ยนตาม SKU        │ │
│ │ [ค้นหา SKU หรือชื่อสินค้า ▾________]   [+ สร้างสินค้าใหม่ (SKU)]         │ │
│ │                                                       [ผูก SKU นี้]    │ │
│ └────────────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────────┘
```

- ป้าย `ยังไม่ผูก SKU` = `Badge tone="amber"` + ไอคอน ⚑ (ข้อความเสมอ ไม่พึ่งสี) · **ห้ามโชว์เป็น error แดง** — เป็นสถานะปกติของงานจากหน้างาน
- ช่องค้น SKU = `datalist` เดิมของ `ProductionAddItemForm` (reuse `skuOptions`) · ปุ่ม `+ สร้างสินค้าใหม่ (SKU)` = `CreateSkuDialog` เดิม (ไม่ seed น้ำหนัก/เนื้อ — ตามเดิม) แล้วผูกต่อทันที
- กด `ผูก SKU นี้` → `Modal` ยืนยัน:
  - หัว `ผูก SKU {sku} · {ชื่อ SKU} กับ "{ชื่อแบบ}" ?`
  - ตัวบท `ผูกแล้วแก้กลับไม่ได้ · ใบงานทุกส่วนจะเปลี่ยนไปใช้ SKU นี้ · ช่างยังเห็นชื่อแบบเดิม "{ชื่อแบบ}" บนใบงาน`
  - ถ้า `skuMetalKnown` และโลหะ ≠ โลหะรายการ: กล่องเหลือง `⚠ SKU นี้ระบุเป็น {โลหะ SKU} แต่รายการนี้เป็น {โลหะรายการ} — ผูกได้ ไม่บล็อก ตรวจให้ตรงของจริง`
  - ปุ่ม `ผูก SKU` (primary) / `ยกเลิก`
- หลังผูก: หัวการ์ดเป็น `SKU · ชื่อ SKU` + บรรทัดรอง `ชื่อบนใบงาน: {ชื่อแบบเดิม}` (อ่านอย่างเดียว) · ป้าย ⚑ หาย · ต้นทุนแสดงตามโหมด SKU ปกติ
- ผูกไม่สำเร็จ (error จาก DB): ข้อความใต้ช่องค้น ไม่ปิด modal — ตาราง §A.10
- การแก้ "ชื่อแบบ" ก่อนผูก = ทำได้ (พิมพ์ผิด) · **ต้องขอ RPC รองรับ** (§C.3 R2)

### A.3.4 State ของการ์ด (4 state)

| state | หน้าตา |
|---|---|
| loading | การ์ด skeleton 3 แถว (หัว + 2 แถวช่อง) ตอนหน้าโหลด (`loading.tsx` ของ route) · ตอนกดบันทึก: ปุ่ม `Button loading` + ช่องทั้งการ์ด `disabled` |
| empty | ไม่มีรายการ → `EmptyState` เดิม `ยังไม่มีรายการในใบนี้` + `เพิ่มรายการด้านล่างได้เลย (มี SKU หรือไม่มี SKU ก็ได้)` |
| error | ระดับช่อง: ข้อความแดงใต้ช่อง + focus · ระดับการ์ด: `role="alert"` กล่องแดงบนการ์ด (ข้อความจาก `humanizeProductionError` — ตาราง §A.10) · ข้อมูลที่กรอกคงอยู่ |
| success | toast + `router.refresh()` · การ์ดกลับเป็นไม่ dirty · ใบ done = โหมดอ่านอย่างเดียว (snapshot) |

- โหมด "มี SKU" = พฤติกรรมเดิมทุกอย่าง (datalist · สร้างสินค้าใหม่ · ติ๊กแบบใหม่เฉพาะ spec) + เพิ่มช่องโลหะ/เนื้อ/น้ำหนัก ส่ง**ค่าทั้งสามชัดเจน**ตอนเพิ่ม (client แค่ prefill ให้เห็น — server ตัดสินค่าเริ่มด้วย helper ตัวเดียว)
- โหมด "ไม่มี SKU": ไม่มีช่อง "แบบใหม่" · ไม่มีต้นทุน · หลังเพิ่ม การ์ดมีป้าย ⚑
- empty: `ยังไม่มี SKU ที่เลือกได้ …` (ข้อความเดิม) + ชี้ทางเลือก "ไม่มี SKU"
- error: SKU ซ้ำในใบ → `SKU นี้มีอยู่ในใบผลิตนี้แล้ว — แก้จำนวนที่การ์ดเดิมแทน`
- มือถือ (ออฟฟิศใช้บนแท็บเล็ต/มือถือได้): segmented เต็มกว้าง · ช่องเรียงแนวตั้ง · ปุ่ม "เพิ่มรายการ" เต็มกว้าง ≥ 44px

## A.5 ตัวอย่างหัวการ์ดที่ข้อความยาว / ตัวเลขเยอะ (edge)

- ชื่อแบบ/ชื่อ SKU ยาวไม่มีเว้นวรรค: `break-words [overflow-wrap:anywhere]` ทั้งหัวการ์ด/เช็คลิสต์/dialog — หัวการ์ดตัดเป็น 2 บรรทัดได้ ปุ่ม 🗑 ไม่ถูกดัน (กล่อง `shrink-0`)
- จำนวน 100,000 ชิ้น / น้ำหนัก 10,000.000 g: `tabular-nums` · ช่องกว้างอย่างน้อย 9 ตัวอักษร
- หลายรายการ (>10): การ์ดพับได้เหมือน OEM (`aria-expanded`) — พับแล้วเห็น `[โลหะ] SKU · ชื่อ · n ชิ้น · ป้ายสถานะ` · **การ์ด dirty/ติดข้อ ห้ามพับอัตโนมัติ**

## A.6 ใบ done / cancelled — อ่านอย่างเดียว

การ์ดแสดงค่าที่ล็อก (จาก `production_order_item` ไม่ใช่ SKU ปัจจุบัน): `[โลหะ] SKU · ชื่อ · n ชิ้น` + `เนื้อ 96.50% · น้ำหนัก 3.200 g/ชิ้น` + (ถ้ามาจากหน้างาน) `ชื่อบนใบงาน: …` · การ์ดสเปคต้นทุน (`ProductionSpecCostCard`) ป้าย "เนื้อเงิน" → `เนื้อ{โลหะ}` ตามรายการ · ค่าที่ว่าง (ไม่ระบุน้ำหนัก) แสดง `ไม่ได้ระบุ` ไม่ใช่ 0

## A.8 `/oem/rates` — กรอกราคาทอง/ทองเหลือง (`MetalPriceSection` delta)

หน้านี้เจ้าของ/แอดมินเท่านั้น (เดิม). เปลี่ยนการ์ด **ทอง** และ **ทองเหลือง** เป็นช่องที่มี "หน่วยหน้างานจริง + ค่าที่ระบบใช้" · **เงินไม่เปลี่ยน** (ยังบันทึกตอน blur · 5–500 บาท/กรัม · ปุ่มล็อก)

```
┌ ราคาโลหะ ──────────────────────────────────────────────────────────────────┐
│ ใช้คำนวณต้นทุนเนื้อโลหะ — บันทึกใหม่ทุกวันที่ราคาขยับ (เก็บประวัติ)          │
│                                                                            │
│ ┌ ◇ เงิน ────────┐ ┌ ◆ ทอง ─────────────────────┐ ┌ ▲ ทองเหลือง ─────────┐│
│ │ (ของเดิม)      │ │ ราคาสมาคมฯ ทองคำแท่ง 96.5% │ │ ราคาทองเหลือง        ││
│ │ [ 38.50 ] บาท/g│ │ (บาทละ) [ขายออก/รับซื้อ—   │ │ [ 350.00 ] บาท/กก.   ││
│ │ ณ 20 ต.ค.      │ │ ต้องยืนยัน]                │ │                      ││
│ │ …              │ │ [ 29,420.92 ] บาท/บาททอง   │ │ ระบบใช้ = 0.3500     ││
│ │                │ │ ───────────────────────── │ │ บาท/กรัม (÷ 1,000)   ││
│ │ ระบบใช้ = เท่าที่กรอก│ ระบบแปลงเป็น ทอง 100%     │ │ ช่วงที่รับ 100–1,000 ││
│ │                │ │ = 2,000.00 บาท/กรัม        │ │ บาท/กก.              ││
│ │                │ │ (÷ 15.244 ÷ 0.965)         │ │ [บันทึกราคาทองเหลือง]││
│ │                │ │ ช่วงที่รับ 2,000–8,000     │ │ ณ 25 ส.ค. · ค่าเดิม  ││
│ │                │ │ บาท/กรัม (ทอง 100%)        │ │ ก่อนใช้ช่องนี้       ││
│ │                │ │ [บันทึกราคาทอง]            │ │                      ││
│ │                │ │ ณ 25 ส.ค. · ค่าเดิม …      │ │                      ││
│ └────────────────┘ └────────────────────────────┘ └──────────────────────┘│
└────────────────────────────────────────────────────────────────────────────┘
```
(ตัวอย่างสมมติทั้งหมด · 29,420.92 = ขอบล่างพอดี 2,000.00)

กติกา

- **ทอง/ทองเหลือง = กดปุ่ม "บันทึก" ชัดเจน ไม่บันทึกตอน blur** (ต่างจากเงิน) — เหตุผล: ค่ากรอกกับค่าที่เก็บคนละหน่วย (ผู้ใช้ต้องเห็นค่าแปลงก่อนเขียน) และผิดทีเดียวต้นทุนผิดทุกใบวันนั้น · ข้อเสีย: ขั้นเพิ่ม 1 คลิก/วัน (ยอมรับ — กรอกวันละครั้ง)
- ช่อง = `type="text" inputMode="decimal"` (ไม่ใช่ `type=number` เพราะต้องรับ `41,250.50` ที่วางมาจากเว็บสมาคม) · ตัด `,` ก่อน parse · ทศนิยม ≤ 2 ตำแหน่ง · ตัวเลขกำกับ `tabular-nums`
- แถวค่าแปลง `role="status" aria-live="polite"` (อัปเดตเมื่อหยุดพิมพ์ ~400ms ไม่อ่านทุกตัวอักษร) · ว่าง = `ค่าแปลงจะขึ้นที่นี่` · ป้าย `ค่าที่ระบบจะบันทึก` (preview) → หลังบันทึกเปลี่ยนเป็น `บันทึกแล้ว` + **ค่าที่ server ส่งกลับ**
- วันที่ = **วันนี้ (เวลาไทย) เท่านั้น** ไม่มีตัวเลือกย้อนวัน (ด่านใบผลิตใช้ "ราคาของวันนี้") — ข้อความใต้ปุ่ม `บันทึกเป็นราคาของวันนี้ ({d ต.ค.})`
- แถวเดิม: `ณ 25 ส.ค. · ค่าเดิม ก่อนใช้ช่องราคาสมาคม` + แสดงเป็น "ต่อกรัม ทอง 100%" ตามที่เก็บ **ไม่แปลงกลับเป็นราคาสมาคม** (P6) · มีแถว "วันนี้ยังไม่มี" → ป้ายเหลือง `⚠ ยังไม่มีราคาของวันนี้ — ใบผลิตทอง/ทองเหลืองปิดไม่ได้` (ตอนนี้มีเฉพาะเงิน — ขยายให้ทอง/ทองเหลืองด้วย)
- ⚠️ ถ้าแถวเดิมอยู่นอกช่วงใหม่: ขึ้นป้าย `ค่าเดิมอยู่นอกช่วงที่รับ — กรอกใหม่` [ยังไม่ได้ตรวจ DB — ต้องให้ backend ตรวจ §C.3 R5]

- **ทองเหลือง**: เนื้อ `100.00` อ่านอย่างเดียว (`readOnly` + ข้อความ `ทองเหลืองไม่ต้องระบุเนื้อ`)

- `แก้` → **แผ่นเต็มจอ (sheet)** ที่มี `MetalSpecFields size="lg"` ชุดเดียวกับ W-2b + ปุ่ม `ใช้ค่านี้` / `ยกเลิก` (กลับไม่เปลี่ยนอะไร) — เหตุผลที่ไม่ inline: ฟอร์ม W-3 ยาวแล้ว · การแก้โลหะเป็นเหตุการณ์ไม่บ่อย · trade-off: เพิ่ม 1 ชั้นของ UI เทียบกับหน้าที่ยาวขึ้น 3 ช่อง
- **ถ้า SKU ไม่มีข้อมูลที่ต้องใช้** (เช่น โลหะ = ทอง แต่เนื้อว่าง): บล็อกขึ้นสถานะ `ต้องใส่เนื้อ` (warn) + ปุ่ม `ถัดไป` กด → เปิด sheet อัตโนมัติ focus ช่องเนื้อ · ไม่ปล่อยให้ผ่านไปรอ error จากเซิร์ฟเวอร์
- **เปลี่ยนโลหะต่างจาก SKU**:
  - `skuMetalKnown` และ ≠ → กล่อง warn ในบล็อก + ใน sheet: `⚠ สินค้านี้ในระบบเป็น {เงิน} — คุณเลือก {ทอง} · เปิดงานได้ ออฟฟิศจะเห็นคำเตือนนี้ ตรวจให้ตรงของจริง` (ไม่บล็อก)

- น้ำหนักมาจาก SKU (เงินเท่านั้น) → เปลี่ยนเป็นโลหะอื่นแล้วล้างพร้อมบอก (เหมือน §A.3.1)
- สินค้าไม่มี SKU: ไม่มีบล็อกนี้ (เพราะทำใน W-2b แล้ว) — แทนด้วยบล็อกสรุปอ่านอย่างเดียวขนาดเล็ก `ทำจาก ◆ ทอง · 96.50%` + `แก้` (กลับ W-2b)
- **W-3 ไม่มีตัวเลขเงิน** · ไม่มีช่องราคา

| loading | บล็อก "ทำจาก" skeleton ถ้ายังดึงค่าเริ่มจาก SKU ไม่เสร็จ (ปุ่มถัดไป disabled `กำลังโหลดข้อมูลสินค้า…`) |

```
│ [ประวัติ ▾]  แก้โลหะ/เนื้อ/น้ำหนักที่การ์ดรายการด้านล่าง   [ ✓ รับทราบ · ทอง 96.50% ] │ ← read-back อยู่ในปุ่ม
└───────────────────────────────────────────────────────────────────────────┘
```

- **โลหะ/เนื้อ/น้ำหนัก = ส่วนที่เด่นที่สุดของการ์ด** (บรีฟ) · ค่าว่าง (ยังไม่ระบุน้ำหนัก) = `ไม่ได้ระบุ`
- ปุ่ม `รับทราบ` = ปุ่มหลักเดียวของการ์ด · ข้อความปุ่ม: เงิน `รับทราบ · เงิน 92.50%` · ทอง `รับทราบ · ทอง 96.50%` · ทองเหลือง `รับทราบ · ทองเหลือง` — เป็น read-back ของค่าที่หน้างานกรอก (P8) ไม่เพิ่ม checkbox
- ปุ่ม aria-disabled เมื่อ dirty (ค่าที่โชว์ในการ์ด = ค่าที่บันทึกแล้ว ไม่ใช่ที่กำลังพิมพ์)
- ไม่มีการแก้ค่าในการ์ดนี้ (แก้ที่การ์ดรายการ — แหล่งแก้เดียว) · **โลหะแก้ไม่ได้เมื่อมีใบงาน** → ข้อความ `ผิดโลหะ? ยกเลิกใบงานแล้วเปิดใหม่ (โลหะล็อกพร้อมใบงาน)` ในส่วน ประวัติ/ช่วยเหลือ
- ประวัติ (`<details>`): รายการ `เวลา · ใคร · อะไรเปลี่ยน` จาก event `intake_open`/`edit` (ตามที่เจ้าของวาด) · ว่าง = `ยังไม่มีการแก้`
- หลังรับทราบ: แถบ `รับทราบแล้วโดย {ชื่อ} · {วันที่}` + `ประวัติ ▾` เท่านั้น

| state | หน้าตา |
|---|---|
| loading | ปุ่มรับทราบ `Button loading` `กำลังบันทึก…` |
| empty | (ไม่มี — ใบจากหน้างานมีรายการเสมอ) · ประวัติว่างตามข้างบน |
| error | `role="alert"` ในการ์ด: `รับทราบไม่สำเร็จ — ลองอีกครั้ง` · ถ้าใบถูกยกเลิก/ปิดไปแล้ว `ใบนี้ไม่ได้เปิดอยู่แล้ว — โหลดหน้าใหม่` + `โหลดใหม่` |
| success | toast `รับทราบ {PO} แล้ว` + การ์ดหดเป็นแถบ + ข้อติด "ยังไม่รับทราบ" หายจากเช็คลิสต์ |

### B.10.2 `/production` (รายการ) — ป้าย + ตัวกรอง

- แถวตาราง: ต่อจากเลขที่ใบ เพิ่มป้าย (ซ้อนบรรทัดเล็ก ไม่เพิ่มคอลัมน์): `จากหน้างาน` (`bg-primary-100 text-primary-700` ตาม brand-tint) · `รอรับทราบ` (amber) หรือ `ค้าง 3 วัน` (แดง · ≥ 3 วันนับจากวันที่เปิด เวลาไทย — [ต้องยืนยัน: นับตามวันปฏิทินหรือ 72 ชม. §C.2 Q10]) · `ยังไม่ผูก SKU n` (amber + ⚑)
- ตัวกรอง: แถบสถานะเดิม (ทั้งหมด/กำลังผลิต/…) คงไว้ + **กลุ่มที่สอง "ต้องจัดการ"** ปุ่ม toggle `aria-pressed` 2 อัน: `รอรับทราบ ({n})` · `ยังไม่ผูก SKU ({n})` — ทำงานแบบ AND กับแถบสถานะ · ตัวนับนับเฉพาะใบ open · n = 0 → ปุ่มยังอยู่ (สม่ำเสมอ) สีจาง
- empty: เปิดตัวกรองแล้วไม่เหลือ → `ไม่มีใบที่รอรับทราบ` / `ไม่มีรายการที่ยังไม่ผูก SKU` + `ล้างตัวกรอง`
- ตาราง min-w 720 เดิม (เลื่อนแนวนอนบนมือถือ — ของเดิม ไม่แก้รอบนี้)

### B.10.3 `/jobs` บอร์ด — tile + ป้ายการ์ด

- `SummaryTiles` เพิ่ม tile ที่ 5 `รอรับทราบ` (Signal ใหม่ `unacked` · tone amber เมื่อ n>0 · แดงถ้ามีใบค้างเกิน 3 วัน) · grid เดิม `grid-cols-2 sm:grid-cols-4` → `grid-cols-2 sm:grid-cols-3 lg:grid-cols-5` (ไม่ซ่อน tile เมื่อ n=0 — ไม่ให้เลย์เอาต์กระโดด)
- การ์ด/แถวใบงาน: ป้าย `จากหน้างาน` + `ยังไม่ผูก SKU` (flag) + (ถ้า known≠ต่าง) ป้ายเล็ก `โลหะต่างจาก SKU` · `statusSignals` เพิ่มข้อ "รอรับทราบ" (rank อยู่ระหว่าง เลยกำหนด กับ ครบใน 3 วัน — ให้ architect/frontend ตัดสินเลข rank) · ตัวกรอง `describeFilters` เติม `รอรับทราบ`
- tile เป็นปุ่มกรอง (เดิม) — `aria-pressed` + ตัวนับในข้อความเสมอ

### B.10.4 `/jobs/workers` — สิทธิ์ + การ์ด QR ร้าน

**สิทธิ์ในกล่อง "แก้ไข" ของช่าง (`EditDialog`)** — เพิ่ม `<fieldset>` ใต้ "ขั้นที่ช่างทำ":

```
สิทธิ์เพิ่มเติม
 ☐ เปิดงานได้
    สร้างใบผลิต + ใบงานจากมือถือ (สแกน QR ร้าน) · ออฟฟิศต้องกดรับทราบก่อนปิดใบ
 ☐ ดูแลงานนอกร้าน
    ชี้แจงส่วนต่าง / ส่งออก / รับกลับ / ยกเลิกการส่งออกของคนอื่นได้
```
- checkbox ≥ 44px แถวเดียวต่อสิทธิ์ + บรรทัดอธิบาย 14px · บันทึกพร้อมปุ่ม `บันทึก` เดิม (ไม่ใช่สวิตช์ทันที — สิทธิ์สร้างข้อมูลจริง ต้องมีจังหวะยืนยัน)
- ผู้จัดการ = ช่างปกติที่มี `stage_codes` + ติ๊ก `เปิดงานได้` (ไม่ต้องมี stage ถ้าไม่ผลิตเลยก็ได้? — ปัจจุบัน "เลือกอย่างน้อย 1 ขั้น" บังคับ [ต้องยืนยัน — ผู้จัดการที่ไม่ผลิตต้องถูกบังคับเลือกขั้นไหม §C.2 Q11])
- แถวช่าง (`WorkerItem`): ป้าย `เปิดงานได้` (บน brand-tint) และ `ดูแลงานนอกร้าน` (info) ต่อท้ายชื่อ · ช่างปิดใช้งาน → ไม่โชว์ป้ายสิทธิ์
- ปิดใช้งานช่างที่ถือสิทธิ์: ข้อความยืนยันเดิม + บรรทัด `ช่างคนนี้เปิดงานจากมือถือไม่ได้อีก` (ไม่บล็อก)

**การ์ด QR ร้าน (บนสุดของหน้า ใต้หัว "ทะเบียนช่าง" · เจ้าของ/แอดมินเท่านั้น — เหมือนหน้าเดิม)**

```
┌ QR ร้าน — ให้ช่างเปิดงานใหม่จากมือถือ ────────────────────────────────────┐
│ [ใช้งานอยู่]  ออกเมื่อ 20 ต.ค. 09:12 โดย {ชื่อ}                             │
│ ติดไว้ที่หน้าร้าน/โต๊ะผู้จัดการ · ช่างสแกน → เลือกชื่อ → ใส่ PIN → เปิดงาน    │
│ ดู QR ซ้ำไม่ได้ (ระบบเก็บเฉพาะรหัสเข้ารหัส) — ถ้าทำหาย ให้ออกใหม่              │
│                                       [ออกใหม่ (เปลี่ยน QR)]  [เพิกถอน]     │
└───────────────────────────────────────────────────────────────────────────┘
```

| สภาพการ์ด | เนื้อหา |
|---|---|
| ยังไม่เคยออก (empty) | `ยังไม่มี QR ร้าน — ช่างยังเปิดงานจากมือถือไม่ได้` + ปุ่มหลัก `ออก QR ร้าน` |
| ใช้งานอยู่ | ตามกรอบข้างบน · ปุ่ม `ออกใหม่` รอง · `เพิกถอน` รอง (ตัวแดง/ขอบแดง) |
| ถูกเพิกถอน | `ถูกเพิกถอนเมื่อ {วันที่} — ช่างเปิดงานจากมือถือไม่ได้` + `ออก QR ร้าน` |
| loading | skeleton กรอบ + ปุ่ม `loading` ระหว่างออก/เพิกถอน |
| error | `ออก QR ไม่สำเร็จ — ลองอีกครั้ง` (`role=alert`) · ไม่ทิ้งสถานะครึ่งๆ (ออกไม่ผ่านต้องไม่เพิกถอนของเก่า — ให้ architect ทำเป็น transaction เดียว) |

- **ออก/ออกใหม่ → Modal "QR ร้านใหม่" (แสดง raw ครั้งเดียว)**:
```
┌ QR ร้านใหม่ ───────────────────────────┐
│        ┌──────────────┐               │
│        │   QR  240px  │               │ role=img aria-label "QR ร้าน"
│        └──────────────┘               │
│ ⚠ แสดงครั้งเดียว — ปิดกล่องนี้แล้วดูซ้ำไม่ได้ │
│ ถ้าออกใหม่ QR เดิมที่ติดอยู่ใช้ไม่ได้ทันที   │
│ พิมพ์แล้วติดแทนของเดิมเลย                   │
│ [พิมพ์โปสเตอร์ QR]        [จดแล้ว ปิด]      │
└────────────────────────────────────────┘
```
  - ก่อนออกใหม่ (เมื่อมี QR เดิม) ยืนยัน: `ออก QR ใหม่? QR เดิมที่ติดอยู่จะใช้ไม่ได้ทันที — พร้อมพิมพ์และเปลี่ยนที่ติดแล้วใช่ไหม` [ออก QR ใหม่ แล้วพิมพ์] [ยกเลิก]
  - ปุ่ม `จดแล้ว ปิด` ถ้ายังไม่เคยกด `พิมพ์` → ยืนยันเบาๆ `ยังไม่ได้พิมพ์ — ปิดแล้วต้องออกใหม่ ปิดเลยไหม` (ข้ามได้) · pattern เดียวกับ `ShownPinDialog` (แสดงครั้งเดียวของ PIN)
  - **โปสเตอร์พิมพ์ (A4 แนวตั้ง · `print:`)**: โลโก้ 3J ซ้ายบน (`assets/3j-logo-crop.png` ตาม handoff §5) · หัว `เปิดงานใหม่` ตัวใหญ่ · QR 12 ซม. · ขั้น 1-2-3 `สแกน → เลือกชื่อ → ใส่ PIN` · ท้าย `สำหรับช่างที่ได้รับสิทธิ์เท่านั้น` · **ไม่พิมพ์ URL/ตัวเลขใดๆ** · ไม่มีส่วนที่ซ่อนด้วย `print:hidden` ที่มีข้อมูลภายใน
- เพิกถอน → `Modal` ยืนยัน: `เพิกถอน QR ร้าน? ช่างทุกคนจะเปิดงานจากมือถือไม่ได้ทันที จนกว่าจะออก QR ใหม่ · ใบงานและ QR ใบงานที่เปิดไปแล้วไม่ได้รับผลกระทบ` [เพิกถอน] [ยกเลิก] — [ต้องยืนยันกับ architect ว่าเพิกถอนร้านไม่แตะ token ใบงาน]

## C.0 Design decision + trade-off (สรุป)

| การตัดสินใจ | ทำไม | ไม่เลือก |
|---|---|---|
| โลหะเป็น radio แสดงทุกตัวเลือก + MetalTag สี (ไม่ใช่ `<select>` แบบ OEM) | R6: ผิดโลหะแล้วด่านทองหาย · ต้องเห็นตัวเลือกและสีตลอด · เหมาะนิ้วบนมือถือ | `<select>` (เหมือน OEM เป๊ะ — แต่ซ่อนโลหะที่เลือกไว้หลังเมนู) |
| ใบผลิต: บันทึกต่อการ์ดด้วยปุ่ม | เนื้อ/น้ำหนักขับต้นทุนทั้งล็อต · พิมพ์ผิดแล้วไม่เขียนทันที | auto-save ตอน blur (เร็วกว่า แต่ผิดแล้วลงทันที) |
| ราคาทอง/ทองเหลือง: ปุ่มบันทึกชัดเจน + โชว์ค่าแปลง | ค่าที่กรอก ≠ ค่าที่เก็บ ต้องเห็นก่อนเขียน | blur-save เหมือนเงิน |

## C.1 จุดที่ต้อง validate กับผู้ใช้จริง (design จับ usability ไม่ได้)

ผู้จัดการ/ช่าง ≥ 3 คน (1 คนสายตาไม่ดี) · ออฟฟิศ 1–2 คน · ไม่อธิบายก่อน · มือถือของตัวเอง
- **V1** (หน้างาน) ให้เปิดใบ "แหวนทองเนื้อ 90%" ที่ไม่มีรหัส — วัด: เลือกทองถูกไหม · กรอกเนื้อถูกไหม · เห็นป้ายทองบนจอทวนไหม · มีใครเผลอปล่อยเป็นเงินไหม (R6 — **ตัวชี้วัดสำคัญสุดของชุด B**)
- **V2** เปิดใบสินค้ามี SKU เงินแล้วถามว่า "ใบนี้ทำจากอะไร" โดยไม่ดูหน้าจอ → ตอบได้ไหม (บล็อก "ทำจาก" เด่นพอไหม)
- **V3** หลังเปิดสำเร็จ ให้ปิดหน้าไปโดยไม่บอกอะไร แล้วถามว่าถ้าช่างยังไม่ได้สแกนจะทำอย่างไร (ข้อความ "แสดงครั้งเดียว" ถูกอ่านไหม)
- **V4** MetalTag ทอง/ทองเหลือง/ป้าย "ยังไม่ผูก SKU" แยกออกไหม (รวมคนตาบอดสีแดง-เขียว/เหลือง-ส้ม)
- **V5** (ออฟฟิศ) ใบจากหน้างาน: หาตรงที่ต้องตรวจเนื้อ/น้ำหนักเจอใน 5 วินาทีไหม · เข้าใจเหตุผลที่ปุ่ม "ผลิตเสร็จ" กดไม่ได้ไหมโดยไม่ถาม
- **V6** (ออฟฟิศ) กรอกราคาทอง: ให้ลอกราคาจากเว็บสมาคมจริง — กรอกถูกฝั่ง (ขายออก/รับซื้อ) ไหม · อ่านค่าแปลงเข้าใจไหม · ลองพิมพ์ราคาต่อกรัมผิด → ข้อความ error พอไหม
- **V7** ผู้จัดการพิมพ์เนื้อทองเอง — พิมพ์ "96.5" แล้ว (ช่องรับ) · พิมพ์ "0.965"/"965" ได้ข้อความที่เข้าใจไหม · ไม่ทำ shortcut K รอบนี้ (96.50 / 90.00 / 75.00 …) เพราะชุดค่าที่ร้านใช้จริงต้องเจ้าของยืนยัน — ถ้า V7 พบพิมพ์ผิดบ่อย ค่อยเพิ่มชิป
