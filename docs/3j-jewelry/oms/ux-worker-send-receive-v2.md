## 1. ทำไมจอตอนนี้งง (วิเคราะห์จากโค้ด HEAD 35226ce)

จอส่งตอนนี้ ไล่จากบนลงล่าง มี **ตัวเลขโผล่ ~10 ที่ ใหญ่ 3 ขนาดแข่งกัน** และตัวที่ใหญ่สุดคือตัวที่ "ไม่ใช่คำตอบ"

| ลำดับอ่าน | อะไร | ขนาด | ปัญหา |
|---|---|---|---|
| 1 | หัวจอ WorkerApp "คุณถืออยู่ **50** ชิ้น · ขั้น X" | 36px | เลขชุดที่ 1 — แต่ยังไม่รู้ว่าต้องทำอะไรกับมัน |
| 2 | "ส่งต่อกี่ชิ้น **จาก 50**" + ปุ่ม "ทั้งหมด **50**" | 18px | เลข 50 ซ้ำ 2 ที่ — และ "ทั้งหมด" = ถือ − เสีย จึง **ไม่เท่า** "จาก 50" เมื่อมีของเสีย |
| 3 | stepper − **40** + | 30px | **ตัวที่ต้องตัดสิน** แต่เล็กกว่าเลขหัวจอ |
| 4 | กล่อง 3 ช่อง เสีย **0** / ส่งไป **40** / ค้างกับคุณ **13** | 24px ×3 | "ส่งไป" ซ้ำกับ stepper · 3 กล่องหน้าตาเท่ากัน ตาไม่รู้ว่าอันไหนสำคัญ |
| 5 | ข้อความ "40 ชิ้นที่ส่งจะแยกเป็นส่วนใหม่ · QR เดิมใบเดียว" | 18px | ศัพท์ระบบ ("ส่วนใหม่") ช่างไม่ได้ถาม |
| 6 | ตัวนับของเสีย **0** + ปุ่ม −10 −5 +5 +10 | **48px** | 🔴 เลขใหญ่สุดบนจอคือ "ของเสีย" ซึ่ง 90% เป็น 0 — ดึงสายตาผิดที่ |
| 7 | ปุ่ม "ส่งต่อ 40 จาก 53 ชิ้น" | 20px | ตัวเลขที่ 3 ที่ขึ้นต้นด้วย "จาก" — ไม่บอกผลลัพธ์ว่า "เหลือกับฉันเท่าไร" |

ต้นตอ 4 ข้อ
1. **เลขเยอะเกิน + ขนาดสวนกับความสำคัญ** (ข้อ 1, 6 ใหญ่กว่าข้อ 3)
2. **ศัพท์ 3 ชุดแทนสิ่งเดียวกัน**: ส่งต่อ / ส่งไป / ส่งออก · ถืออยู่ / ค้างกับคุณ / ที่เหลือ · ส่วนหลัก / ส่วนใหม่
3. **ตัวเลขผลลัพธ์ไม่มีภาพ** — "ส่ง 40 เหลือ 13" ต้องคำนวณในหัวจากกล่องตัวเลข ไม่มีอะไรให้ "เห็น" ว่าก้อนหนึ่งออกไปอีกก้อนอยู่
4. **ลำดับกลับด้าน**: ของเสียอยู่ใต้ผลสรุปที่มันเปลี่ยนค่า — กดเสียแล้วเลขข้างบนขยับ ไกลจากนิ้ว

จอรับมีโรคเดียวกันในขนาดเล็ก: หัวจอ "รอคุณรับ **50**" + บล็อก "รับเข้า **50** จาก 50" + stepper **50** = เลขเดียวกัน 3 ที่ ไม่มีภาพบอกว่า "ขาด"

## 2. หลักออกแบบ v2 (5 ข้อ)

1. **ตัวเลขที่ต้องตัดสินมีตัวเดียว** = จำนวนที่ส่ง (จอส่ง) / จำนวนที่ได้รับ (จอรับ) — ใหญ่สุดบนจอ 48px อยู่กลางจอ ขนาบด้วยปุ่ม − + 56px
2. **ผลลัพธ์เป็นภาพ**: แถบเดียวแบ่งก้อน — ตัวเลขใต้แถบเป็น "คำบรรยายภาพ" (24px) ไม่ใช่ input
3. **สีบอกว่าของอยู่กับใคร** ใช้ชุดเดียวทุกจอ (ตามหลัก §3.1 ของ handoff เดิม + ข้อความกำกับทุกครั้ง ไม่พึ่งสีอย่างเดียว)

   | ความหมาย | สี | Tailwind (token เดิมของแอป) | คำ |
   |---|---|---|---|
   | ออกจากมือฉันแล้ว | info น้ำเงิน | แถบ `bg-sky-700` · การ์ด `bg-sky-50 text-sky-950` | **ส่งไป** |
   | อยู่กับฉัน (ยังต้องทำ) | warn อำพัน | แถบ `bg-amber-600` · การ์ด `bg-amber-50 text-amber-950` | **เหลือกับฉัน** / **ได้รับ** (จอรับ) |
   | เสีย / ขาด | danger แดง | แถบ `bg-red-700` · การ์ด `bg-red-50 text-red-900` | **เสีย** / **ขาด** |
   | สำเร็จ | success เขียว | ไอคอน ✓ `text-green-700` เท่านั้น | (เครื่องหมายถูกบนจอสำเร็จ) |
   | ปุ่มหลัก | brand | `bg-primary-600` (= `#a2191d` ตาม BigButton เดิม) | — |

   เขียวไม่ถูกใช้เป็นสีของก้อนตัวเลข (กันสับสนกับ "เสร็จ/ผ่าน QC" ในแถบ 100 ชิ้นของบอร์ด)
4. **ศัพท์ชุดเดียว**: การกระทำ = **ส่ง** · ผลลัพธ์ = **ส่งไป** · ที่เหลือ = **เหลือกับฉัน** (ประโยคที่ระบบพูดกับช่างบนจอสำเร็จ = "เหลือกับคุณ") · ไม่ใช้ "ส่งต่อ/ส่งออก/ค้าง/ถืออยู่/ส่วนใหม่" บนจอส่ง-รับ
   - เปลี่ยน "ค้าง" → "เหลือ": "ค้าง" ในระบบนี้แปลว่า "ค้างชำระ/ค้างนอกร้าน/เลยกำหนด" (เชิงลบ) — ช่างที่ส่งไป 40 เหลือ 13 ไม่ได้ทำอะไรผิด
   - "ส่วนที่ n" เหลือเฉพาะบรรทัดรองสีเทาบนจอสำเร็จ (ให้ตรงกับใบย่อยของออฟฟิศ) ไม่ใช่หัวข้อ
5. **ปุ่มหลักพูดผลลัพธ์** — อ่านปุ่มอย่างเดียวต้องรู้ว่ากดแล้วเกิดอะไร (ข้อ 4.4)

Trade-off หลัก: เลือก "แถบ + ตัวเลขใต้แถบ" แทน "กล่องตัวเลข 3 ช่อง" เดิม · ข้อดี ตาเห็นสัดส่วนก่อนอ่านเลข · ข้อเสีย แถบกินที่แนวตั้ง ~24px + ต้องมีคำกำกับสำหรับคนมองสีไม่ชัด (จึงเก็บ legend ไว้) · ไม่เลือก "ซ่อนผลลัพธ์ไว้ให้ปุ่มบอกอย่างเดียว" เพราะเจ้าของถามชัดว่า "ดูยังไง" = ต้องมีที่ให้ดู

## 3. User flow

```
ช่างสแกน QR ใบงาน → ใส่ PIN → (WorkerApp)
 ├─ nextAction = send ──► จอส่ง (§4)
 │     ├─ ส่งหมด (ค่าเริ่ม) ─────────► จอสำเร็จ "ส่งแล้ว N ชิ้น" ✓ 2 วิ → โหลดใหม่ (ใบจบขั้น)
 │     ├─ ส่งบางส่วน ────────────────► จอหลังส่ง (§6): ส่งไป n · เหลือกับคุณ k · QR · [เสร็จแล้ว] / ยกเลิกการส่ง
 │     ├─ ใส่ของเสีย (ทางเลือก) ─────► แถบมีก้อนแดง · ปุ่มบอก "เสีย s"
 │     └─ error: ข้อมูลเก่า (stage_changed ฯลฯ) → ข้อความ + [โหลดใหม่] · ส่งเกิน/ว่าง → ปุ่มปิด + บอกเหตุผล
 └─ nextAction = receive ─► จอรับ (§5)
       ├─ ครบ (ค่าเริ่ม) ───────────► ✓ "รับงานแล้ว — N ชิ้น"
       ├─ ได้น้อยกว่า ──────────────► แถบมีก้อนแดง "ขาด m" → ยืนยัน → ✓ "รับ r ชิ้น — ขาด m แจ้งกลับขั้นก่อนแล้ว"
       └─ ขั้นก่อนยังไม่ส่ง/ถือโดยคนอื่น → ข้อความเดิม (ไม่เปลี่ยน)
```

## 4. จอส่ง (SendPanel) — spec

### 4.1 ลำดับบนจอ (บน→ล่าง) · จอ 390×~740 ที่เห็นจริง

1. หัว WorkerApp (เลขใบ · ชื่องาน) — **เอา holdLine ออก** (เลขซ้ำ) ดู §8
2. `h2` "ส่งงาน: {ขั้นนี้}" + บรรทัดรอง "ถัดไป: {ขั้นถัดไป}" (ถ้ามี)
3. `sendNote` เดิม (ถ้ามี — ขั้นไม่ต้องชั่ง ฯลฯ)
4. **การ์ดตัดสินใจ** (ข้อ 4.2) ← ทุกอย่างที่ต้องตัดสินอยู่ในการ์ดเดียว
5. ช่องน้ำหนัก (เฉพาะที่ขั้นนี้ต้องกรอก — 4.5)
6. แถวของเสีย (พับ) 4.3
7. เศษโลหะ / + เติมโลหะ (เดิม ตามเงื่อนไขเดิม)
8. error (ถ้ามี) อยู่เหนือปุ่ม
9. **ปุ่มหลักติดล่าง** (StickyAction เดิม)

กรณีเงิน ไม่ต้องกรอกน้ำหนัก ไม่มีของเสีย: ข้อ 2→4→6→9 พอดีหนึ่งจอ ไม่ต้องเลื่อน

กติกาการ์ด
- **ตัวเลขใหญ่ตัวเดียว** = ช่องกลางของ stepper (48px / `text-5xl`) · เลขอื่นในการ์ดทั้งหมด ≤ 24px
- chip "ส่งหมด {allCount}" = toggle `aria-pressed`: ตอน n = allCount พื้นดำ (`bg-zinc-900 text-white`) · ไม่เท่า = ขอบเทา · กดแล้ว n = allCount (และกลับสู่โหมด "ตามสด" ของเดิม: ของเสียเปลี่ยน → n ตาม)
- `allCount` = ถือ − ของเสีย · ชิปแสดงเลขนี้ (ไม่ใช่ถือ) เพื่อให้เลขบนชิปเท่ากับเลขที่จะขึ้นในช่องเสมอ
- "ในมือฉัน H ชิ้น" = คำกำกับแถบ (รวมทุกก้อน = H เสมอ — ผลรวมก้อนต้องเท่า H เหมือนหลัก "แถบ 100 ชิ้น")
- แถบ: ความกว้างก้อน = qty/H · ก้อนที่ qty>0 กว้างไม่ต่ำกว่า 8px · transition 150ms (`motion-reduce:transition-none`)
- แถบเป็น `role="img"` + `aria-label` "ในมือ 53 ชิ้น ส่งไป 40 เหลือกับฉัน 13" · legend เป็น `role="status" aria-live="polite"` (ตัวเดียว)
- ซ่อนคำอธิบาย "แยกเป็นส่วนใหม่ · QR เดิมใบเดียว" ออกจากจอนี้ (ย้ายไปจอหลังส่ง §6)

### 4.3 ของเสีย — พับ ไม่แย่งสายตา

- ปัจจุบัน `ScrapStepper` เลข 48px + 5 ปุ่ม ตั้งตระหง่านทุกครั้ง → **พับเป็นแถวเดียว** 56px (`border-dashed`, เหมือนปุ่ม "+ แจ้งของเสียในขั้นนี้" เดิม) · ขั้นที่ถามชิ้นเสีย (`scrapQtyAsk` ไม่ใช่ false/ใบเดิม) = ข้อความ "ของเสียขั้นนี้ · **ไม่มี**" ขวา "+ แจ้ง" · ขั้นที่ไม่ถาม = "+ แจ้งของเสียในขั้นนี้" (เดิม)
- กดแถว → ขยาย `ScrapStepper` (เลขลดเป็น 30px, ปุ่ม ±1 ±5 ±10 เดิม, ชิปเหตุผลเดิม) · **เปิดค้างเมื่อ s > 0** (เหตุผลบังคับ ต้องเห็น) · ปิดได้เมื่อ s = 0
- s > 0: แถบมีก้อนแดงท้ายแถบ · legend เป็น 3 ช่อง (grid-cols-3, label 16px) · ปุ่มหลักต่อท้าย "· เสีย s"
- เพิ่ม s แล้ว n เกิน allCount → **clamp n = allCount อัตโนมัติ** (เดิมขึ้น error แดง) เพราะช่างไม่ได้ผิด · ลด s → n ไม่ขยับเอง ยกเว้นอยู่โหมด "ส่งหมด"
- Trade-off: พับทำให้ "ลืมแจ้งของเสีย" ง่ายขึ้นถ้าช่างไม่อ่านแถว — แก้ด้วยแถวมีค่า "ไม่มี" ชัด (คำตอบที่เห็นอยู่เสมอ ไม่ใช่ช่องว่าง) · **ต้อง validate กับช่างจริง** (§11)

### 4.4 ปุ่มหลัก — พูดผลลัพธ์

| สถานะ | ข้อความปุ่ม |
|---|---|
| ส่งหมด · ไม่มีเสีย | `ส่งหมด 53 ชิ้น` |
| ส่งหมด · เสีย 2 | `ส่ง 51 ชิ้น · เสีย 2` |
| ส่งบางส่วน | `ส่ง 40 ชิ้น · เหลือกับฉัน 13` |
| ส่งบางส่วน · เสีย 2 | `ส่ง 40 ชิ้น · เสีย 2 · เหลือกับฉัน 11` (ยาวได้ 2 บรรทัด ปุ่มสูงขึ้นเองด้วย `min-h-14`) |
| ช่อง n ว่าง/0 | ปิดปุ่ม · `ใส่จำนวนที่ส่ง` |
| n > allCount | ปิดปุ่ม · `ส่งได้ไม่เกิน 53 ชิ้น` + ข้อความแดงใต้ stepper (เดิม) |
| ของเสียหมดทั้งก้อน (allCount = 0) | `แจ้งเสียหมด 53 ชิ้น` — ดูคำถามค้าง Q2 |
| กำลังส่ง | `กำลังส่ง…` + spinner (BigButton `loading` เดิม) · stepper/ชิป/แถวของเสียถูก disabled |
| ใบชิ้นเดียว | `ส่ง 1 ชิ้น` |

ปิดปุ่ม + บอกเหตุผลบนปุ่ม ตามกติกา §4 ของ handoff · **ด่านจริงยังอยู่ที่ DB** (UI แค่กันกดผิดก่อน)

### 4.5 ช่องน้ำหนัก — วางตรงไหนไม่ให้รก

ช่อง "น้ำหนัก" มี **ช่องเดียวต่อจอ** (ไม่เคยมีสองช่องพร้อมกัน — โค้ดเดิม `showWeight = … && !partial` กับ `partial && goldWeigh` ไม่ซ้อนกันอยู่แล้ว) วางเป็น **การ์ดแยกใต้การ์ดตัดสินใจ** ก่อนแถวของเสีย:

| กรณี | ช่องที่ขึ้น | ป้าย |
|---|---|---|
| ส่งหมด · ขั้นที่ต้องชั่ง (ทอง/เงิน) | น้ำหนักออก | `น้ำหนักออก (กรัม) — ต้องใส่` |
| ทอง · ขั้นชั่ง · **ส่งบางส่วน** | น้ำหนักส่วนที่ส่ง | `น้ำหนัก 40 ชิ้นที่ส่ง (กรัม) — ต้องใส่` + hint `ชั่งเฉพาะ 40 ชิ้นที่ส่ง ไม่ต้องชั่งที่เหลือ` |
| เงิน · ส่งบางส่วน | ไม่มีช่อง | บรรทัด 18px ใต้ legend: `ส่งบางส่วนนับจำนวนอย่างเดียว ไม่ต้องชั่ง` |
| ขั้นไม่ต้องชั่ง | ไม่มีช่อง | `sendNote` เดิม |

```
 ┌────────────────────────────────────┐ ขอบ amber-400 เมื่อ "ต้องใส่" และยังว่าง
 │ น้ำหนัก 40 ชิ้นที่ส่ง (กรัม) ต้องใส่ │ 18px bold (เลข 40 ตาม n สด)
 │ ┌────────────────────────────────┐ │
 │ │              0.000             │ │ ช่อง 56px · เลข 24px (ไม่ใช่ 36px — ไม่แย่ง n)
 │ └────────────────────────────────┘ │
 │ ชั่งเฉพาะ 40 ชิ้นที่ส่ง             │ 18px
 └────────────────────────────────────┘
```

- `WeightField` เพิ่ม prop `size="md"` (ช่อง `min-h-14 text-2xl`) ใช้บนจอส่ง/รับ · ค่าเริ่ม `lg` เดิมสำหรับที่อื่น
- ทอง: **ห้ามโชว์น้ำหนักขั้นก่อน/น้ำหนักที่ถือ/น้ำหนักประมาณ** (มติ N1 เดิม) · แถบมีแต่จำนวนชิ้น ไม่มีกรัม
- กด "ปุ่มหลัก" แล้วช่องน้ำหนักว่าง: `scrollIntoView` + focus ช่องนั้น + ข้อความแดงใต้ช่อง (เดิมข้อความไปอยู่นอกจอได้เมื่อปุ่ม sticky) · ไม่ปิดปุ่มด้วยเหตุผลน้ำหนัก (ปุ่มต้องคงข้อความผลลัพธ์ไว้)
- แป้นพิมพ์: ช่องจำนวนและน้ำหนัก `onFocus` = select ทั้งช่อง (พิมพ์ทับได้เลย ไม่ต้องลบ 53 ทีละตัว)

### 5.3 กติกาจอรับ

- ข้อความสำเร็จ: ครบ `รับงานแล้ว — 50 ชิ้น` · ขาด `รับ 47 ชิ้นแล้ว — ขาด 3 ชิ้น แจ้งขั้นก่อนแล้ว` (เดิมเหมือนกัน เติมจำนวนในกรณีครบ)
- เตือนน้ำหนักเบี่ยง >20% (เดิม) ยังข้ามเมื่อรับไม่ครบ ตามเดิม

## 7. State ครบ 4 (จอส่ง + รับ)

| State | จอส่ง | จอรับ |
|---|---|---|
| **loading** | `PanelSkeleton` เดิมตอน `!ready \|\| waiting` (ปุ่มไม่ติดก่อน hydrate) · เพิ่มรูปร่าง skeleton = การ์ด 1 ใบ + แถบ (ไม่ใช่ 3 แถบสุ่ม) | เหมือนกัน |

| **success** | §6 | ✓ เต็มจอ 2 วิ (`already` โดยคนอื่น = ไอคอนเหลือง 4 วิ + ตกลง เดิม) |

Edge case ที่ออกแบบแล้ว
- เลขหลักพัน (ถือ 1,200): ช่องกลาง `min-w-0 flex-1` เลข 4 หลัก 48px ≈ 110px พอใน 320px · เกิน 5 หลักไม่รองรับ (ข้อมูลจริงไม่ถึง)
- จอแคบ 320px: ปุ่ม − + 56 ×2 + gap 24 = 136 · ช่องกลางเหลือ ~140 ✓ · legend 3 ช่อง (มีเสีย) label ตัดบรรทัดได้ ไม่ตัดคำกลางตัวเลข · ปุ่มหลักขึ้น 2 บรรทัดได้
- ข้อความชื่อขั้น/ชื่อ ผู้รับยาว: `break-words` ทุกที่ที่มีชื่อ
- ช่องจำนวนว่างระหว่างพิมพ์: แถบเป็นสีเทา (`bg-zinc-300`) · legend `—` · ปุ่มปิด `ใส่จำนวนที่ส่ง`
- สิทธิ์ไม่พอ/ไม่ใช่ขั้นของคุณ/พักใบ: ข้อความ `INFO` เดิมใน WorkerApp ไม่เปลี่ยน

- ถือ 53 · เสีย 2 · โหมดส่งหมด → send 51 · keep 0 · `ส่ง 51 ชิ้น · เสีย 2`
- ถือ 53 · เสีย 2 · n=40 → keep 11 · ผลรวม 40+11+2 = 53 (ทดสอบเลขคี่)
- n พิมพ์ 60 > allCount → state `over` · ปุ่มปิด · ข้อความ `ส่งได้ไม่เกิน 53 ชิ้น`
- เพิ่มเสียจน allCount < n (n แตะเองแล้ว) → n clamp = allCount
- n ว่าง/"0"/"abc" → `empty` ปุ่มปิด
- ถือ 1 → ไม่มี stepper/แถบ · ปุ่ม `ส่ง 1 ชิ้น`
- allCount 0 (เสียหมด) → ปุ่มไม่เป็น `ส่ง 0 ชิ้น`
- รับ: E=50 r=47 → `รับ 47 ชิ้น · ขาด 3` · r=50 → `รับ 50 ชิ้น` + legend `ครบ 50 ชิ้น` · r>E ปิดปุ่ม

ต้องไม่พัง (component)
- ส่งหมดเรียก `workerSendStage` **ไม่มี** `qtySend` · ส่งบางส่วนมี `qtySend=n` + `qtyHold` · `weightMoveG` เฉพาะทอง+ขั้นชั่ง+บางส่วน
- รับครบเรียกแบบเดิม (ไม่ส่ง `qtyReceived`) · รับน้อยกว่า → `qtyReceived=r`
- ใบเดิม (ไม่มี `hasProfile`) ยังเห็นช่องน้ำหนัก/ของเสียครบ · ใบหลายส่วนส่ง `lotJobId` ทุกครั้ง
- ทองไม่เห็นน้ำหนักขั้นก่อน/น้ำหนักที่ถือที่ใดบนจอ (grep DOM)
- กด "ส่งหมด" ซ้ำ/กดปุ่มหลักรัว ๆ → เรียก server ครั้งเดียว

## 10. Design decision + trade-off

| การตัดสินใจ | ทำไม | ไม่เลือก |
|---|---|---|
| แถบ + legend แทนกล่อง 3 ช่อง | เห็นสัดส่วนก่อนอ่านเลข ลดเลขต่อจอ | กล่อง 3 ช่องเดิม (ตัวเลข 3 ตัวหน้าตาเท่ากัน) |
| เลขตัดสินใจตัวเดียว 48px | เจ้าของ UAT: "ไม่รู้ดูตรงไหน" | เลขหัวจอ 36px (แข่งกับ stepper) |
| ของเสียพับเป็นแถว | 90% เป็น 0 ไม่ควรกินจอ/สายตา | เปิดตลอด (เดิม) — เสี่ยงน้อยกว่าเรื่อง "ลืมแจ้ง" แต่จอรก |
| "ส่งหมด" เป็น toggle chip | ให้ภาพว่ากำลังอยู่โหมดไหน (ตามสด vs เลขเอง) | ปุ่มธรรมดา (กดแล้วไม่รู้ว่าติดโหมดอยู่) |
| "เหลือ" แทน "ค้าง" | ค้าง = เชิงลบ + ชนความหมาย "ค้างชำระ" | ตามคำเจ้าของ "ค้างกับฉัน" — **ถ้าเจ้าของอยากใช้ "ค้าง" เปลี่ยนได้จุดเดียว (ตาราง §2) แต่ต้องเปลี่ยนทุกจอพร้อมกัน** |
| ปุ่มบอกผลลัพธ์ ไม่เปลี่ยนเป็น "ยืนยัน" | ช่างอ่านปุ่มก็รู้ผล · ลด dialog | dialog ยืนยันทุกครั้ง (เพิ่มขั้นให้ช่างทุกชิ้นงาน) |
| จอรับขาด → คง ConfirmBox | ย้อนยาก สร้างงานให้คนอื่น | เอาออกเพราะมีภาพแล้ว |

## 11. ต้อง validate กับช่างจริง (design จับ usability ไม่ได้ทั้งหมด)

ให้ช่าง 3 คน (อย่างน้อย 1 คนอายุมาก/ตาไม่ดี) ถือมือถือของตัวเอง ไม่อธิบายก่อน:
1. "ใบนี้คุณถือ 53 ชิ้น ส่งให้ช่างถัดไป 40 ชิ้น" → วัด: กดจบกี่วิ · ถามกลับ "เหลือกับคุณกี่ชิ้น" ตอบถูกไหม โดยไม่ดูปุ่ม
2. "ในนี้เสีย 2 ชิ้นเพราะตะไบเกิน" → หาแถวของเสียเจอไหม · ลืมแจ้งไหม (เสี่ยงข้อ 4.3)
3. จอรับ "ได้มา 47 จาก 50" → บอกได้ไหมว่าขาดเท่าไร และใครจะถูกถามต่อ
4. คนตาบอดสีแดง-เขียว: แยก "เหลือกับฉัน/ส่งไป/เสีย" ได้จากคำไหม (ไม่ใช่จากสี)
5. คำ "เหลือกับฉัน/เหลือกับคุณ" เข้าใจตรงกันไหม

## 12. คำถามค้าง / จุดที่ตัดสินเองไม่ได้ (ไม่เดา)

- **Q1** ผู้ส่งชื่อ+เวลา บนจอรับ ("จากช่าง ข · 08:20" ตาม L-4) — `WorkerAction` ไม่มี field นี้ · ไม่ใส่ใน v2 · ต้องการไหม? ถ้าใช่ต้องขอ DB ส่งเพิ่ม (งานแยก)
- **Q2** ของเสียหมดทั้งก้อน (allCount = 0): โค้ดตอนนี้ปล่อยผ่านไป DB (`job_core_send` หักเสียเอง) — DB ยอมไหม? ถ้ายอม ปุ่ม `แจ้งเสียหมด N ชิ้น` ถูกต้อง · ถ้าไม่ยอมต้องปิดปุ่มและบอกให้แจ้งออฟฟิศ — **frontend/backend โปรดยืนยันก่อนทำ**
- **Q3** "ไม่ได้รับเลยสักชิ้น" (r = 0) — stepper min 1 ตามเดิม · เคสนี้ช่างต้องทำอย่างไร? ไม่ได้ออกแบบ (นอก scope · ถ้ามีจริงต้องมีปุ่มแยก)
- **Q4** ใบที่ยังใช้ "เหลือกับฉัน" ในหน้า Queue/ใบงานแม่ (L-1) ใช้คำ "ค้างกับคุณ" ของเดิมอยู่ไหม — ถ้าเปลี่ยนต้องเปลี่ยนให้ตรงกันทุกหน้า (ไม่อยู่ใน scope นี้)
- **Q5** เจ้าของเห็นด้วยกับ "เหลือ" แทน "ค้าง" หรือไม่ (§10)
