## 0. ปัญหาของโจทย์ที่ต้องพูดก่อน (อ่านก่อนลงมือ)

1. **คำว่า "แบบ" ชนกัน (สำคัญสุด)** — หน้าปัจจุบันเรียกพลอยอันดับ 1/2/3 ว่า "แบบ 1/2/3" (การ์ด · LINE · `sameAs`) พอมี "แบบแหวน" 7 แบบ ลูกค้าจะงงว่า "แบบ 2" คือแหวนหรือพลอย และข้อความ LINE `แบบ: X · แบบ 2` อ่านไม่ออก
   - **เสนอ: ชุดพลอย 1/2/3 = "ชุด 1/2/3"** (การ์ด: "ชุด 1 · อันดับ 1 จากแบบทดสอบ") · "แบบ" ใช้กับแหวนอย่างเดียว
   - กระทบสตริงที่ shipped แล้ว: `GemSetPicker` (hardcode "แบบ {n}") · `line-message.ts` · `sameAs` · tests (QA11/d11) — Yoda/Luke ต้องรู้ก่อนเขียน test
   - ทางเลือกที่ไม่แตะของเดิม: เรียกแหวนว่า "ทรง" แต่เจ้าของสั่งใช้ "แบบ" — ไม่เลือกทางนี้
2. **"ห้ามโชว์รายละเอียดเชิงเทคนิค" ต้องนิยามให้ชัด** (ไม่งั้น Luke ตีความเอง) —
   - **แสดงได้**: ชื่อแบบ + จำนวนเม็ดที่อยู่ในชื่อ · บทบาท หลัก/เสริม · ตำแหน่ง กลาง/ข้าง/บน/ล่าง · ช่วงไซซ์
   - **ห้ามแสดง**: ขนาดพลอย (มม.) · วิธีฝัง/ตัวเรือน · น้ำหนัก · วัสดุตัวเรือน · ต้นทุน
   - ข้อสังเกต: ชื่อ "ฝังล็อค" เป็นศัพท์ช่างเอง ลูกค้าอาจไม่เข้าใจ → ชื่อชั่วคราวอยู่แล้ว ให้เจ้าของพิจารณาตอนตั้งชื่อจริง (pictogram ใน §2.2 ช่วยให้ไม่ต้องพึ่งชื่อ)
3. **ราคา 800 → 890** — ค่าเดียวใน `SHOWCASE_PRICE_THB` แล้ว tests/สตริงที่ hardcode "800" ต้องไล่แก้ · ราคาเดียวทุกแบบ **อย่าทำ per-design price** (ไม่มีใครขอ) · `pageDescription`/metadata ต้องไม่มีเลขราคา
4. **ไม่มีรูปจริง 6 จาก 7 แบบ** — ปัจจุบัน stage ใช้รูปจริงเป็น fallback (โหลด/ไม่รองรับ 3D/context lost) ถ้าไม่แก้ แบบอื่นจะโชว์รูปแหวนไขว้ = ผิดคำสั่ง "ห้ามใช้รูปแบบอื่นแทน" → §6
5. **ก้นหอย 6 เม็ด ไม่รู้ว่าอะไรคือ "เม็ดกลาง"** (เกลียวไม่มีกลางชัด) · กฎ "เม็ดคู่ → 2 เม็ดกลาง" ใช้กับก้นหอยด้วยไหม → คำถามข้อ 1

```

เข้าตรง ────────→ /ring-builder                  (ไขว้ 2 เม็ด + CZ ขาว)
        │
        ▼
 ① เลือกแบบแหวน (7)  ← ใหม่ · ค่าเริ่มต้น = ไขว้ · ภาพ stage เปลี่ยนทันที
        ▼
 ② เลือกพลอย: แนะนำ (ชุด 1/2/3 + เรื่อง) | เลือกเอง (หลัก/เสริม)   ← พลอยที่เลือกค้างข้ามแบบแหวน
        ▼
 ③ เลือกไซซ์ (ช่วงตามแบบ) หรือไม่เลือก → แอดมินช่วยเช็ก
        ▼
 ④ ดูของจริง (เฉพาะแบบที่มีรูป)
        ▼
 ⑤ สรุป → [ส่งให้แอดมินทาง LINE] / [คัดลอกข้อความ]
```

edge path
- เปลี่ยนแบบแหวนหลังเลือกพลอย/ไซซ์ → พลอยคงเดิม · ไซซ์: ถ้านอกช่วงใหม่ = ถือว่าไม่ได้เลือก (ไม่ลบค่า ดู §5)

- ลิงก์เก่าที่ไม่มี `r` = ไขว้ → ลิงก์ที่แชร์ไปแล้วยังได้ของเดิมเป๊ะ
- กลับจาก /ring-size ได้แบบแหวนเดิม (เขียน `r` ผ่าน `buildShowcaseUrl` เหมือน key อื่น)

## 2. Layout

### 2.1 ลำดับจอ (มือถือ) และเหตุผล

```
[stage sticky 40dvh]                     (เดิม ไม่แตะ)
-- scroll --
A  header: "3J · JEWELRY" · h1 · "890 บาท ทุกแบบ · พรีออเดอร์ ทำภายใน 21 วัน"
B  เลือกแบบแหวน   ← ใหม่ วางเหนือสวิตช์โหมด
C  [ แบบแนะนำ | เลือกพลอยเอง ]
D  แผงพลอย (บรรทัดอธิบายตำแหน่ง หลัก/เสริม ของแบบที่เลือก อยู่หัวแผง)
E  เลือกไซซ์ (ช่วงตามแบบ)
F  ดูของจริง  (มีรูป = สไลด์ · ไม่มีรูป = การ์ดบอกตรงๆ)
G  สรุป · LINE · disclaimer
```
**ทำไม B อยู่ก่อน C:** (1) บทบาท/ตำแหน่งพลอย ป้ายใน D และไซซ์ใน E ล้วนขึ้นกับแบบแหวน — เลือกต้นน้ำก่อนปลายน้ำ (2) เจ้าของอยากให้ลูกค้า "เลือกแบบ → พลอย → ไซซ์" ตามลำดับพูด (3) ผลเปลี่ยนที่ stage ทันที เห็นได้โดยไม่ scroll
**ไม่ทำ:** วางไว้ใต้พลอย (ลูกค้าเลือกพลอยแล้วเจอว่าแบบที่ชอบมีตำแหน่งต่าง = ต้องย้อนกลับ) · วางเป็น tab บน stage (แย่งพื้นที่ภาพ + ซ้อน interaction กับลากหมุน)

**h1:** เปลี่ยนจากชื่อแบบ (ตายตัว) เป็นหัวหน้าเพจคงที่ `แหวนพลอยของ 3J Jewelry` `[ต้องยืนยัน: ถ้อยคำ]` — ชื่อแบบที่เลือกอยู่ในตัวเลือกแล้ว ไม่ซ้ำ ประหยัด ~0 บรรทัด (ยังบรรทัดเดียว)

### 2.2 รูปแบบตัวเลือกแบบแหวน — ตัดสินใจ: **radiogroup แนวนอน เลื่อนได้ (chip + pictogram) บนมือถือ · grid บนเดสก์ท็อป**

โครง chip (กว้าง ≥ 104 × สูง 72px · gap 8 · เลื่อน snap-x · เห็นใบที่ 4 โผล่ครึ่งใบ = บอกว่าเลื่อนได้)
```
 ┌───────────┐
 │  ◦ ● ◦    │  pictogram 48×32 (SVG · aria-hidden) ● = พลอยหลัก  ◦ = พลอยเสริม
 │ ไขว้ 2 เม็ด│  ชื่อ 14px (ไม่ตัดคำ · 1 บรรทัด)
 └───────────┘
```
- pictogram = ภาพประกอบ "ตำแหน่งเม็ด" แบบ schematic (เม็ดหลักทึบ · เม็ดเสริมกลวง → ไม่พึ่งสีอย่างเดียว) — ไม่ใช่ภาพถ่าย ไม่มีสีพลอย ไม่ใช่ภาพ 3D
- เหตุผลที่มี pictogram: ชื่อชั่วคราวและเป็นศัพท์ช่าง ("ฝังล็อค" "เตย") — ลูกค้าแยกฝังล็อค 4 / 6 / แถวเล็ก 7 ไม่ออกจากชื่อ · และ pictogram สอน "หลัก/เสริม" ไปในตัว ก่อนอ่านคำอธิบาย
- **ต้นทุน:** พิกัดจุด 2D ต่อแบบ (`points: {x,y,role}[]` ใน design config) เขียนมือ/ฉายจากข้อมูล 3D · **ถ้าไม่ทันให้ตกเป็น chip ข้อความล้วนได้ (P2)** — ฟังก์ชันครบเท่าเดิม แค่แยกแบบยากขึ้น · ต้องให้ Sabé/เจ้าของตรวจว่า pictogram ตรงกับของจริง `[ต้องยืนยัน]`
- เลือกแล้ว = ขอบ 2px burgundy + พื้น `--gq-burgundy-soft` + เครื่องหมายถูกมุมขวาบน (pattern เดียวกับ `OwnGemPicker`)

**ทำไมไม่ใช้แบบอื่น (trade-off)**
| ทางเลือก | ผล | ตัดสิน |
|---|---|---|
| grid 2 คอลัมน์ 7 ใบ (4 แถว × 72) | สูง ~310px → สวิตช์โหมด/พลอยตกใต้ fold บน 375×667 (พื้นที่เลื่อนเหลือ ~384px) | ไม่เอา |
| พับเป็น "แบบ: X · เปลี่ยน" (pattern IntentionPicker) | ประหยัดสุด แต่ **ลูกค้าไม่รู้ว่ามี 7 แบบ** — นี่คือ feature ใหม่หลักที่เจ้าของอยากให้เห็น | ไม่เอา |
| `<select>` | ไม่เห็นรูปร่าง เลือก 7 ตัวเลือกด้วยชื่อชั่วคราวอย่างเดียวไม่ไหว · ไม่สอดคล้องกับ pattern radio ทั้งหน้า | ไม่เอา |
| การ์ดรูปย่อใหญ่ (รูปจริง/3D thumbnail) | ไม่มีรูปจริง 6/7 · render 3D 7 ใบ = หนักเกินและเสี่ยงโชว์ผิด | ไม่เอา |
| **chip เลื่อนแนวนอน + pictogram** | สูง ~100px รวมหัวข้อ · เห็น 3.3 ใบ + ใบที่ 4 โผล่ · แลก: ใบที่ 5–7 ต้องปัด | **เลือก** |

ข้อแลกที่ยอมรับ: ลูกค้าที่ไม่ปัดอาจไม่เห็น เตย/แถวเล็ก → ลดด้วย (ก) ใบที่ 4 โผล่ครึ่ง (ข) คำใต้หัวข้อ "ปัดดูทั้ง 7 แบบ" (มือถือเท่านั้น) · **วัดจริง:** สัดส่วนคนเลือกแบบที่ 5–7 (ถ้าต่ำมาก ลองเปลี่ยนเป็น grid)

**งบความสูง 375×667** (stage 40dvh ≈ 267 + padding ≈ 283 → พื้นที่เลื่อน ≈ 384)
header ~90 → gap 20 → หัวข้อ+chip ~104 → gap 20 → สวิตช์โหมด 48 = **282** → แถวเรื่อง (IntentionPicker 48 + gap 20) สิ้นสุด ~350 < 384 ✓ ยังเห็นโดยไม่ scroll (เดิม ~226 → ดันลง ~124px — ยอมรับ แลกกับ feature ใหม่)

## 3. คำอธิบายตำแหน่งพลอย (ตอบข้อ 2)

### 3.1 แนวคิด
- **คำเดียวกันทุกแบบ = "พลอยหลัก / พลอยเสริม"** (ตรงกับที่ quiz/GEM_QUIZ_PAIRS ใช้) · **ตำแหน่ง = วงเล็บ ตามแบบ** — ลูกค้าสลับแบบแล้วไม่ต้องเรียนศัพท์ใหม่ มีแค่คำในวงเล็บเปลี่ยน
- รูปแบบป้าย: `พลอยหลัก (เม็ดกลาง)` · `พลอยเสริม (เม็ดข้าง)` · ไขว้: `พลอยหลัก (เม็ดบน)` · `พลอยเสริม (เม็ดล่าง)`
  (เปลี่ยนจากเดิม "พลอยบน (เม็ดหลัก)" — ลำดับกลับ: บทบาทนำ ตำแหน่งตาม)

- ประโยค "CZ เล็ก 2 เม็ดมาพร้อมแหวน" และ `czNote` ท้ายหน้า: **แสดงเฉพาะแบบที่มีฟิลด์ `extraCz` ** (ไขว้ = 2 · แบบอื่น `[ต้องยืนยัน]` — ถ้าไม่ระบุ = ไม่แสดง ห้ามเดา)
- ตำแหน่งบนบรรทัดอธิบาย **อยู่หัวแผงพลอย (ใต้สวิตช์โหมด)** ไม่ใช่ใต้ชุดพลอย (เดิมอยู่ใน live region ท้ายการ์ด → ลูกค้าเห็นช้า) · โหมดเลือกเองใช้ป้ายแถวด้วย
- หัวข้อแถวโหมดเลือกเอง: `พลอยหลัก (เม็ดกลาง)` / `พลอยเสริม (เม็ดข้าง)` · hint ว่าง: "แตะพลอยหลักก่อน ระบบใส่ชนิดเดียวกันให้พลอยเสริม แล้วเปลี่ยนได้"
- การ์ดชุดพลอย (โหมดแนะนำ): บรรทัด 2 = `{หลัก} + {เสริม}` เดิม (ลำดับ = หลักก่อน ตรงกับไอคอนใหญ่/เล็กเดิม) · ไม่ต้องใส่ตำแหน่งซ้ำ (บรรทัดอธิบายอยู่เหนือแล้ว)
- `sameAs`: "คู่เดียวกับชุด n — สลับว่าเม็ดไหนเป็นพลอยหลัก" (เดิม "…เม็ดไหนอยู่บน" ใช้ไม่ได้กับแบบแถว)
- `ownBothSame`: "{ชื่อ} ทุกเม็ด" (เดิม "ทั้ง 2 เม็ด" **ผิดสำหรับแบบ 3–7 เม็ด** — ต้องแก้)
- สรุป/LINE: `พลอยหลัก (เม็ดกลาง): {ชื่อ}` · `พลอยเสริม (เม็ดข้าง): {ชื่อ}` · `stageAria` ใช้สตริงเดียวกัน (เดิมมี "พลอยบน/พลอยล่าง/CZ เล็ก 2 เม็ด" hardcode)

## 4. ไซซ์ (ตอบข้อ 3)

ช่วงไซซ์เป็นฟิลด์ต่อแบบ: ไขว้ 55–58 · แบบใหม่ 50–60 (11 ปุ่ม) · `SHOWCASE_SIZES` ที่เดียวต้องกลายเป็น `design.sizes` (ด่าน `isShowcaseSize`/`fitsDesignRange` รับ design)
- layout ปุ่ม: `grid grid-cols-6 gap-2` ปุ่ม ≥48 (343−5×8)/6 ≈ 50px ✓ → 11 ปุ่ม = 2 แถว (6+5) · ไขว้ = 1 แถว · หัวข้อต่อท้าย "(ช่วง 50–60)" ให้รู้ขอบเขต

### เมื่อเปลี่ยนแบบแล้วไซซ์ที่เลือกอยู่นอกช่วง — **ตัดสิน: "ถือว่ายังไม่ได้เลือก + บอกตรงนั้นทันที" โดยไม่ลบค่าที่ผู้ใช้เลือก**
- state เก็บ `size` ดิบไว้ · ใช้ `effectiveSize = size อยู่ในช่วงของแบบปัจจุบัน ? size : null` ทั้งปุ่ม/สรุป/LINE
- ในส่วนไซซ์ แสดงแถบ (มีไอคอน ไม่พึ่งสี · `role=status`) ตราบที่ยังนอกช่วง:
  > "ไซซ์ 52 ใช้กับแบบนี้ไม่ได้ (แบบนี้มีไซซ์ 55–58) · เลือกไซซ์ใหม่ หรือส่งข้อความแล้วแจ้งไซซ์กับแอดมินทาง LINE ได้"
- สลับกลับไปแบบที่ไซซ์ 52 ใช้ได้ → ไซซ์กลับมาเลือกอยู่เอง แถบหาย (ลูกค้าเปรียบเทียบหลายแบบได้ ไม่ต้องเลือกซ้ำ)
- ผู้ใช้กดไซซ์ใหม่ → ทับค่าเดิม (ทิ้งของเก่า)
- ประกาศ SR ตอนเปลี่ยนแบบ: "เลือกแบบ {ชื่อ} แล้ว · ไซซ์ที่เลือกไว้ใช้กับแบบนี้ไม่ได้" (ต่อท้ายเฉพาะกรณีนอกช่วง)

**ทำไมไม่ล้างทิ้ง:** ลูกค้ากดดูหลายแบบเป็นพฤติกรรมปกติของหน้านี้ — ล้างเงียบ = ต้องเลือกซ้ำและไม่รู้ว่าทำไมหาย · **ทำไมไม่แค่เตือนแล้วคงค่าส่งต่อ:** ไซซ์ที่ส่งเข้า LINE ต้องใช้ได้จริงกับแบบนั้น ไม่งั้นแอดมินรับค่าที่ผิดช่วง
- ผลวัดล่าสุดจาก /ring-size: เทียบกับช่วงของ "แบบที่เลือกอยู่" · นอกช่วง = "ไซซ์นี้อยู่นอกช่วงของแบบนี้ ทักแอดมินทาง LINE ได้" (เดิมมีอยู่ ใช้ต่อได้ — ข้อความไม่ต้องแก้)
- ปุ่มส่ง LINE ยังไม่ disabled เมื่อไม่มีไซซ์ (หลักการ D1 เดิม) · แถบเหลือง "ยังไม่ได้เลือกไซซ์ — ส่งได้เลย…" ใช้ต่อ

## 5. ดูของจริง + stage เมื่อไม่มีรูปจริง (ตอบข้อ 4)

## 8. Accessibility

- radiogroup แบบแหวน: `aria-labelledby` ชี้หัวข้อ · แต่ละ chip `role=radio` `aria-checked` · `aria-label` = ชื่อเต็ม · roving tabindex (tab stop = ใบที่เลือก) · ←→/↑↓ ผ่าน `handleRadioKeyDown` + `scrollIntoView({inline:"nearest", block:"nearest"})` เมื่อ focus ย้าย (กัน chip ที่เลื่อนอยู่นอกจอ)
- touch target: chip ≥104×72 · ปุ่มไซซ์ ≥48 · ปุ่ม "ลองอีกครั้ง" ≥44
- การเลือกไม่พึ่งสี: ขอบ 2px + เครื่องหมายถูก · pictogram หลัก/เสริม = ทึบ/กลวง · `aria-hidden` (ข้อมูลเดียวกันอยู่ใน `placementNote`)
- แถว chip เลื่อนแนวนอน: `touch-action: pan-x pan-y` (ไม่ block การเลื่อนหน้า) · `overscroll-x-contain` · แถบเลื่อนซ่อนได้แต่ต้องมี peek (ไม่ใช้ fade ที่บัง chip ที่ 4 จนอ่านไม่ออก)
- `prefers-reduced-motion`: ไม่ใช้ smooth scroll/ไม่มี transition ของ crossfade ภาพเก่า→ใหม่
- contrast ≥ 4.5:1 ทุกข้อความใหม่ใช้ token เดิม · ข้อความนอกช่วงไซซ์มีไอคอน ไม่ใช้สีอย่างเดียว
- `role=status` เดียวสำหรับประกาศเปลี่ยนแบบ (ใช้ `announce` เดิม ขยายให้รับ design) · ข้อความ stage `role=status` เดิม

## 10. Trade-off หลัก (สรุป)
1. chip เลื่อน (ไม่ใช่ grid) = ไม่ดันจอ แลกกับ 3 แบบท้ายต้องปัด → วัดอัตราเลือก
2. ไม่ล้างไซซ์เมื่อสลับ = เปรียบเทียบแบบได้ลื่น แลกกับ state ซับซ้อนขึ้น 1 ตัว (`effectiveSize`)
3. ไม่โชว์รูปแบบอื่นแทน = ซื่อตรง แลกกับหน้าจอ "ว่าง" ใน 6 แบบ (ช่วยด้วย pictogram + ข้อความตรงๆ)
4. เปลี่ยน "แบบ n" → "ชุด n" = กระทบ test เดิมแต่กันสับสนถาวร
5. บรรทัดตำแหน่งย้ายขึ้นหัวแผง = เห็นก่อนเลือก แลกกับดันการ์ดชุดพลอยลง ~40px (อยู่ใต้ fold อยู่แล้ว)

## 11. ต้อง validate กับผู้ใช้จริง
1. ลูกค้าเห็นว่ามี 7 แบบโดยไม่ปัดไหม (ใบที่ 4 โผล่ครึ่งพอไหม) · สัดส่วนเลือกแบบ 5–7
2. pictogram ทึบ/กลวง เข้าใจเป็น "หลัก/เสริม" ไหม (ถามหลังเลือกพลอย: "เม็ดไหนคือพลอยหลัก")
3. ชื่อ "ฝังล็อค" "เตย" "ก้นหอย" ลูกค้านึกภาพออกไหม (ก่อนตั้งชื่อจริง)
4. สลับแบบแล้วภาพเก่าจาง ~60% ไม่ทำให้เข้าใจผิดว่าเป็นแบบใหม่
5. ที่ 360px ชื่อ "TRINITY 3 เม็ด" 14px ไม่ตัดคำ · ปุ่มไซซ์ 6 คอลัมน์ไม่แน่น
6. ปุ่ม LINE ใน in-app browser (ค้างจาก D1) — ไม่เกี่ยวกับงานนี้แต่ยังไม่ปิด

## 12. คำถามเจ้าของ (ห้ามเดา)
1. **ก้นหอย 6 เม็ด**: เม็ดไหนเป็น "เม็ดกลาง" — ใช้กฎ 2 เม็ดกลางเหมือนฝังล็อค หรือ 1 เม็ด หรือกำหนดเอง?
2. **ลำดับ 7 แบบ**: ใช้ตามที่สั่ง (ไขว้ · TRINITY · ก้นหอย 6 · ฝังล็อค 4 · ฝังล็อค 6 · เตย · แถวเล็ก) หรือเรียงตามจำนวนเม็ด/ยอดนิยม?
3. **เรียกชุดพลอยว่า "ชุด 1/2/3"** แทน "แบบ 1/2/3" ตามข้อ 0.1 — เห็นด้วยไหม?
4. **"CZ เล็ก 2 เม็ด"** ติดมากับแบบอื่นด้วยไหม (แบบไหนกี่เม็ด) · ถ้าไม่มี จะไม่แสดงประโยคนี้
5. **พลอยสีในแบบใหม่เป็นวัสดุอะไร** (CZ สี / พลอยแท้) — เพื่อเขียนหมายเหตุให้ตรง (ร้านต้องบอกชัดว่าชิ้นไหน CZ ชิ้นไหนแท้ · ห้ามให้เข้าใจว่า CZ เป็นเพชร) · ถ้ายังไม่ตอบ ใช้ disclaimer เดิม ไม่ขยาย
6. **แบบที่ยังไม่มีรูปจริง**: แอดมินส่งรูป/ภาพตัวอย่างให้ทาง LINE ได้ไหม (ถ้าได้จะเพิ่มลิงก์ขอดูรูป)
7. **พรีออเดอร์ 21 วัน** ใช้กับทั้ง 7 แบบไหม · **ไซซ์ 50–60** ใช้กับทุกแบบใหม่เหมือนกันหมดไหม (เช่น แถวเล็กอาจต่าง)
8. **h1 หน้า** "แหวนพลอยของ 3J Jewelry" ใช้ได้ไหม (เดิมเป็นชื่อแบบเดียว)
9. **ตั้งชื่อจริง** ของทุกแบบเมื่อไร (ชื่อใน chip/LINE/alt เปลี่ยนที่ config ที่เดียว)

## 13. ข้อจำกัด
- ไม่ได้เห็นโค้ด 3D/gl-renderer/design data ของ Yoda — spec นี้สมมติว่า geometry โหลดแยกต่อแบบได้ (ถ้าโหลดรวมก้อนเดียว §6 ส่วน "ระหว่างสลับ" จะเรียบง่ายลง)
- ไม่ได้ตรวจ `GEM_QUIZ_PAIRS` ทีละคู่ว่ามีคำว่า บน/ล่าง ในข้อความไหม (grep ในไฟล์ UI/lib ไม่พบ — QA ต้อง grep config ของ quiz ซ้ำ)
- pictogram ต้องผ่านตาเจ้าของ/Sabé ก่อนขึ้น (กันภาพประกอบไม่ตรงของจริง)

# D1.2a เลือกรายเม็ด (18 พ.ย.)

ผู้เขียน: Padmé · มติเจ้าของ 18 พ.ย. 69 (ดูจอจริงบน preview): แบบแถว 3–7 เม็ด ในโหมด "เลือกพลอยเอง" = **เลือกสีทีละเม็ด** · ไขว้ 2 เม็ดคงเดิม (บน/ล่าง) · โหมด "แบบแนะนำ" คงเดิม (เม็ดกลาง=หลัก ที่เหลือ=เสริม) · ราคาเท่าเดิมไม่ว่ากี่สี
**แทนที่:** §3 ส่วน "โหมดเลือกเอง" + ข้อความ `ownBothSame` ของแบบแถว · **ไม่แตะ** ที่เหลือของ D1.2
อ้างอิงระบบเดิมของเจ้าของ (handoff B2): แถบตำแหน่ง 1..N ซ้าย→ขวา (จุดสี+เลข) → แตะเม็ด → เลือกพลอยของเม็ดนั้น · ปุ่ม "ใส่ X ทุกเม็ด" · ตัดทิ้ง: ราคา/เม็ด · ล้างเป็น CZ ขาว · สลับตำแหน่ง · ลากสลับ (ไม่มีใครขอ + ราคาเดียว)

## A0. ประเด็นที่ต้องพูดก่อน
1. **ไม่มีคำว่า "หลัก/เสริม" ในโหมดรายเม็ด** — ทุกเม็ดเท่ากัน ใช้ "เม็ดที่ N" อย่างเดียว (กัน test Z10 ใหม่: ห้ามโผล่ "พลอยหลัก/พลอยเสริม" ใน own+แถว) · ไขว้ยังใช้หลัก/เสริม (บน/ล่าง)
2. **3D ลากหมุนได้ → "ซ้าย→ขวา" ใช้ได้เฉพาะมุมหน้าตรง** (มุมเริ่มต้น) · หมุนหลังแหวนแล้วเลขจะดูกลับด้าน — ใส่คำกำกับใต้แถบ ไม่ทำ relabel ตามมุมกล้อง (ต้อง hook กล้อง = ผิดคำสั่งเดิม "ห้ามแตะกล้อง")
3. **เก็บ invariant เดิม "ครบทุกเม็ดหรือไม่มีเลย"** → ไม่มีเม็ด "ว่าง" ครึ่งๆ · แตะพลอยครั้งแรกตอนยังไม่เคยเลือก = ใส่ทุกเม็ดด้วยพลอยนั้น (เหมือนที่ pickTop ทำอยู่) แล้วค่อยแก้รายเม็ด → LINE/URL/สรุปไม่ต้องมี state "บางเม็ดว่าง"

## A5. สลับแบบแหวนขณะอยู่โหมดเลือกเอง (ตอบข้อ 3)
**ตัดสินใจ: จำสีไว้ "ต่อจำนวนเม็ด" + แมปแบบกึ่งกลาง · ไม่ล้างเงียบ** (pattern เดียวกับ effectiveSize ของไซซ์)
- เก็บ `ownByCount: { 2?, 3?, 4?, 6?, 7? } → code[]` — แบบที่จำนวนเท่ากัน (ฝังล็อค 6 / ก้นหอย 6 · เตย 7 / แถวเล็ก 7) **ใช้ชุดสีเดียวกัน** สลับไปมาไม่เสียอะไร · กลับไปจำนวนเดิม = สีเดิมกลับมาเป๊ะ
- ไปจำนวนที่ยังไม่เคยแก้: สร้างจากจำนวนที่ดูอยู่โดย **จัดกึ่งกลางให้ตรงกัน** (`oldIdx = clamp(i + floor((old−new)/2), 0, old−1)`) → เม็ดเกินตัดจากขอบ เม็ดขาดเติมด้วยสีเม็ดริม · ตัวอย่าง 7→3 เก็บเม็ด 3–5 (กลางไว้) · 7→4 เก็บเม็ด 2–5 · 3→7 = `[1,1,1,2,3,3,3]`
- **จาก/ไป ไขว้ (2 เม็ด):** ไขว้→แถว = เม็ดกลางเป็นสี "บน" ที่เหลือเป็นสี "ล่าง" (ตรงความหมายหลัก/เสริมที่ลูกค้าเห็นอยู่) · แถว→ไขว้ = บน = สีเม็ดกลาง (เม็ดกลางตัวแรก) · ล่าง = สีเม็ดที่ 1
- ประกาศ (`role=status`, ต่อท้ายข้อความเปลี่ยนแบบ): จำนวนเปลี่ยน → "เปลี่ยนเป็น{ชื่อแบบ}แล้ว · ปรับพลอยให้พอดี {N} เม็ด กลับไปแบบเดิมสีเดิมจะกลับมา" · จำนวนเท่าเดิม → ไม่ต่อท้าย
- เม็ดที่แก้อยู่ (index) เกินจำนวนใหม่ → ขยับไปเม็ดสุดท้าย
- ทางที่ไม่เลือก: ตัดเหลือ N เม็ดแรก (7→3 เสียเม็ดกลางทั้งหมด ผิดความรู้สึก) · ล้างเป็น seed ใหม่ (ลูกค้าที่กดเปรียบเทียบหลายแบบเสียงานทุกครั้ง)

## A6. คำอธิบายพลอย (GEM_QUIZ_PAIRS) ในโหมดรายเม็ด (ตอบข้อ 5)
กติกาเรียบ 3 ข้อ ข้อความมาจาก config เท่านั้น (Y4 · ไม่แต่งความหมายเอง):
| ชนิดที่ใช้ | แสดง |
|---|---|
| 1 ชนิด | `{ชื่อ} ทุกเม็ด` + keywords (kind "same" เดิม) |
| พอดี 2 ชนิด | ข้อความคู่จาก `findExactPair(a,b)` (ไม่สนลำดับ/จำนวนเม็ด ✓ ตรวจแล้วใน sets.ts) → title + th + "เหมาะกับ" · ถ้าไม่มีคู่ใน config → แบบข้างล่าง |
| ≥3 ชนิด (หรือ 2 ชนิดที่ไม่มีคู่) | รายการ "ชื่อ · keywords" ต่อชนิดที่ใช้ (≤5 บรรทัด ตามลำดับซ้าย→ขวาที่เจอก่อน) + `ownNoPairNote` เดิม |
- ไม่เรียก "เม็ดไหนคือหลัก" ใน copy คู่ — ถ้าข้อความคู่ใน config มีคำว่า บน/ล่าง/หลัก/เสริม ให้ QA grep (ข้อจำกัด §13 เดิมยังค้าง)

## A7. สรุป + LINE (ตอบข้อ 4) — helper เดียว `formatOwnSlots(codes)` ใช้ทั้ง OrderSummary · LINE · stageAria
**จับกลุ่มช่วงติดกัน** (ซ้าย→ขวา) แล้วเลือกรูปตามจำนวนช่วง:
- ช่วง ≤ 4 → 1 บรรทัดต่อช่วง (แอดมินก๊อปไปใส่ใบสั่งได้ตรงๆ)
```
พลอย: เลือกพลอยเอง (รายเม็ด · ซ้ายไปขวา มองตรงหน้าแหวน)
เม็ด 1–2: โกเมน
เม็ด 3: อเมทิสต์
เม็ด 4–7: ซิทริน
```
- ทุกเม็ดสีเดียว → `เม็ด 1–7: โกเมน (ทุกเม็ด)`
- ช่วง > 4 (สลับสีถี่) → บรรทัดเดียวเรียงทีละเม็ด: `เม็ด 1–7 (ซ้ายไปขวา): โกเมน · อเมทิสต์ · โกเมน · อเมทิสต์ · โกเมน · อเมทิสต์ · โกเมน`
- ไขว้ own: ข้อความเดิม `พลอยหลัก (เม็ดบน): X · พลอยเสริม (เม็ดล่าง): Y` · rec ทุกแบบ: เดิม
- เหตุผลที่จับกลุ่ม: รูปแบบ "เม็ด 1–7: ก · ก · ข …" ของโจทย์ซ้ำชื่อ 7 ครั้งอ่านยากสุดตอนสีซ้ำติดกัน ซึ่งเป็นเคสส่วนใหญ่ (ใช้ "ทุกเม็ด" + แก้ 1–3) · ช่วงถี่ใช้รูปแบบเรียงเม็ดตามโจทย์
- `line-message.ts` ตรวจ: จำนวน code = จำนวนเม็ดของแบบ + code ทุกตัว whitelist · ไม่ครบ = null (ไม่ fallback — เหมือน Z5) · ไม่มี "ชุด n" ในโหมดนี้ · ไม่มีตัวเลขราคานอก 890 · ไม่มี "เพชร"
- OrderSummary: แถวพลอยแสดงข้อความเดียวกับ LINE + แถบ swatch 1..N เล็ก (decor `aria-hidden` — ข้อความคือข้อมูลจริง)

## A8. URL `c` (Yoda เคาะ — ผมเสนอ)
`c` = รหัสพลอย 1 ตัวอักษรต่อเม็ด ซ้าย→ขวา คั่น `.` ยาว = จำนวนเม็ดของ `r` (ไขว้ยังเป็น `c=g.a` = ไม่เปลี่ยน byte)
- ยาว ≠ จำนวนเม็ดของแบบ → **ยกเว้น 1 เคส:** ยาว 2 + แบบแถว (ลิงก์ preview ก่อนหน้านี้) = ขยายแบบ กลาง=ตัวแรก ที่เหลือ=ตัวที่สอง · อย่างอื่นทิ้ง `c` เงียบ
- URL เขียนเฉพาะชุดของจำนวนเม็ดปัจจุบัน (ชุดที่จำไว้ของจำนวนอื่นไม่ลง URL · reload = เสียส่วนนั้น ยอมรับ)

## A12. ห้ามผ่าน / ต้องไม่พัง (ให้ QA)
ห้ามผ่าน (ตกที่ด่านไหน): `c` ยาว 1/4/8 บน trinity · code นอก whitelist · `c` ครบแต่ `r` ผิด → parser ทิ้ง · LINE/สรุปมี "พลอยหลัก/พลอยเสริม/ชุด n" ในโหมด own+แถว · มีเม็ดว่างไป LINE (ต้องครบ N หรือ null) · ตัวเลขบาท ≠ 890 / ราคาต่อเม็ด · "เพชร" · ช่อง < 44px ที่ 360 · สลับแบบแล้วจำนวน code ≠ จำนวนเม็ดของแบบ (วนทุกคู่แบบ 7×7)
ต้องไม่พัง: ไขว้ own 2 แถวเดิม + URL byte เดิม · rec ทุกแบบเดิม · ลิงก์ `c=g.a` + `r=bar7` ขยายได้ · สลับ 7→4→7 สีกลับมาเดิม · bar7↔small7 ไม่เสียสี · เปิดเลือกเองครั้งแรกจากชุดแนะนำ = กลาง/ข้างตรงกับที่เห็น · ไม่มี WebGL ส่ง LINE ได้ · localStorage บล็อก

## A13. Trade-off + validate
1. แถบเดียวไม่ใส่ชื่อ = จอเตี้ย เห็นภาพพร้อมแก้ แลกกับต้องอ่านชื่อจากหัว/สรุป · **วัด:** คนแก้เม็ดผิดแล้วแก้ซ้ำ (แตะเม็ดเดิม >2 ครั้ง) = ช่องแยกยาก
2. ไม่เลื่อนเม็ดอัตโนมัติ = ควบคุมได้ แลกแตะเยอะ · 3. ใส่ทุกเม็ดมี "เลิกทำ" แทน confirm dialog = ไม่ขวางคนส่วนใหญ่ · 4. จำสีต่อจำนวนเม็ด = เปรียบเทียบแบบได้ลื่น แลก state +1 ก้อน
validate กับผู้ใช้จริง: (ก) เห็นเลข 1–7 แล้วรู้ว่าเม็ดไหนบนภาพไหม โดยเฉพาะหลังลากหมุน (ข) เข้าใจ "นับซ้ายไปขวา" ไหม (ค) ลูกค้าหา "ใส่ทุกเม็ด" เจอไหม (ง) แอดมินอ่านข้อความ LINE แบบจับกลุ่มแล้วถามกลับไหม

## A14. คำถามเจ้าของ (ข้อเดียวที่ต้องตอบ ที่เหลือตัดสินให้แล้ว)
1. **ก้นหอย 6 / ฝังล็อค: เม็ด 1…N ซ้าย→ขวา ตรงกับที่เห็นจากหน้าตรงจริงไหม** (ผมสมมติจาก `layout.kind="row"` ว่าเรียงแถวตรงตามแนวนิ้ว · ถ้าก้นหอยเรียงเป็นเกลียวที่ซ้ายขวาไม่ใช่ลำดับ — ต้องเปลี่ยนการนับ ก่อนขึ้นจริง)
2. (ไม่บังคับ) ต้องการชื่อพลอยในช่องแถบไหม — ต้องตั้งชื่อย่อ 5 ชื่อ
