## 2. หัวหน้าจอรูปแบบเดียวกัน

### 2.1 หลักการ (ตัดสินแล้ว)

1. **ซ้ายบน = ถอยหนึ่งขั้นเสมอ** (ไอคอนลูกศร 44×44 · `aria-label="ย้อนกลับ"`) · ขั้นแรกของ flow ไม่มีขั้นให้ถอย → ช่องเดียวกันนี้เปลี่ยนเป็นข้อความ `← เครื่องมือ 3J` (ลิงก์ hub) — **ซ้ายบนไม่เคยเป็น "เริ่มใหม่"/"ปิด"**
2. **ขวาบน = ออกไปหน้ารวม** ข้อความ `เครื่องมือ 3J` + ไอคอนบ้านเล็ก (ลิงก์ hub) ทุกจอที่มีขั้นถอยได้ · ใช้คำเดียวกับลิงก์เดิม (ไม่ใช้ "หน้าหลัก" ตรงๆ เพราะใน LINE มี "หน้าหลัก" ของ OA/ร้านอยู่แล้ว — ลูกค้าจะเข้าใจผิดว่าออกไปที่อื่น `[ต้องยืนยัน Q1]`)
3. **กลางบน = ตัวนับขั้น** เดิม (quiz `01 / 05` · ring-size `01 / 03`) — ไม่แตะ
4. ความหมายต่างกันชัดด้วย **รูปร่าง + ข้อความ**: ลูกศรเปล่า = ถอย · ไอคอนบ้าน+ข้อความ = ออกหน้ารวม (ไม่พึ่งสีอย่างเดียว)

### 2.2 ข้อกำหนดภาพ (ใช้ token เดิม ไม่คิดค่าใหม่)

## 3. ขั้นเบาๆ ในหน้าแหวน

### 3.1 ตัดสิน: **ปุ่ม "แก้" ในกล่องสรุป → เลื่อนไปหัวข้อนั้น + ย้ายโฟกัส** (scroll-to-section จากจุดที่ผู้ใช้อ่านสรุปอยู่)

กล่องสรุป (`OrderSummary` — อยู่ท้ายหน้า ติดปุ่ม LINE) มีแถว แบบแหวน · ชุดพลอย · ไซซ์ อยู่แล้ว → เติมปุ่ม `แก้` ท้ายแถวเหล่านี้ (ไม่แถวราคา):

| แถว | `แก้` พาไป | หมายเหตุ |
|---|---|---|
| แบบแหวน | หัวข้อ "เลือกแบบแหวน" (`DesignPicker`) | |
| ชุดพลอย | โหมดแนะนำ → หัวข้อ "เรื่องที่อยากเสริม" (`IntentionPicker`) · โหมดเลือกเอง → หัวข้อของ `OwnGemPicker` | เรื่อง = ต้นน้ำของชุดแนะนำ จึงพาไปที่เรื่องก่อน ชุด 1–3 อยู่ใต้ลงมาเห็นพร้อมกัน |
| ไซซ์ | หัวข้อ "เลือกไซซ์" (`SizePicker`) | |

กติกา: **ไม่รีเซ็ตอะไรทั้งสิ้น** (ไซซ์ · พลอยเลือกเอง · เรื่อง ค้างตามเดิม — `RingShowcaseClient` ถือ state เหล่านี้ไว้อยู่แล้ว การกด "แก้" แค่เปลี่ยนตำแหน่งจอ) · `scrollIntoView` เคารพ `prefers-reduced-motion` (ใช้แนวเดียวกับ `focusStone` ของ quiz) · คอนเทนเนอร์มี `scroll-pt-[46dvh]` (มือถือ) อยู่แล้ว หัวข้อจึงไม่โดน stage ที่ติดบนทับ · แล้ว `focus()` ที่ `<h2 tabIndex={-1}>` ของหัวข้อนั้น (screen reader/คีย์บอร์ดตามไปด้วย) · `role="status"` เดิมประกาศ "ไปที่ …" 1 บรรทัด

### 3.2 ทำไมเลือกทางนี้ ไม่ใช่ sticky stepper / chips

| ทางเลือก | ข้อดี | ข้อเสีย | ตัดสิน |
|---|---|---|---|

## 4. ประวัติเบราว์เซอร์ (ปุ่ม Back ของมือถือ/LINE ต้องตรงกับปุ่มบนจอ)

### 4.1 กติกา

1. **ขั้นใน flow = history entry** (ring-size ทำอยู่แล้ว · **gem-quiz ต้องเพิ่ม**) · หน้าแหวนไม่เพิ่ม entry (`replaceState` เหมือนเดิม)
2. ปุ่มถอยบนจอ: ถ้า entry ก่อนหน้าคือปลายทางที่ต้องไปจริง → `history.back()` (ไม่สะสม entry) · ไม่ใช่ → `pushState` ไปปลายทาง — **นี่คือตรรกะ `goBack` ของ ring-size อยู่แล้ว ใช้เป็นต้นแบบ** (รวมแฟลก `backPendingRef` กันกดรัว = back ซ้ำ = หลุดหน้า)
3. 🔴 **ปุ่มบนจอห้ามเรียก `history.back()` เมื่อ entry ก่อนหน้าไม่ใช่จอในแอปที่รู้จัก** (เปิดลิงก์ตรงจาก LINE = ไม่มี entry ก่อนหน้า หรือ entry ก่อนหน้าคือแชต LINE/เว็บอื่น → ออกนอกเว็บ) · ที่ขั้นแรก ปุ่มคือ `<a href={HUB_URL}>` เสมอ ไม่ผ่าน history
4. Back ของเครื่องที่ขั้นแรก = ออกจากหน้า (พฤติกรรมปกติของเบราว์เซอร์ ผู้ใช้คาดอยู่แล้ว) · ปุ่มบนจอไม่ทำให้เข้าใจผิดเพราะที่ขั้นแรกมันเป็นลิงก์ hub ที่มีข้อความชัด
5. 🔴 **ห้ามเขียนทับ `history.state` ทั้งก้อน** — ต้องคง `__NA` ของ Next (บทเรียน QA-3 ใน `RingSizeClient`: ไม่งั้น Back ทุกจอ = reload ค่าหาย) · ใช้ pattern `nextHistoryState` เดิม · แนะนำแยกเป็น `lib/nav/screen-history.ts` (ฟังก์ชัน pure รับ key: `rs` / `gq`) ให้ 2 เครื่องมือใช้ร่วม — ring-size ย้ายมาใช้ทีหลังเมื่อเทสต์เขียวเท่านั้น (ห้ามรื้อพร้อมกัน)
6. รีโหลดกลางทาง: `history.state` ค้างจอเก่า แต่ค่าใน memory หาย → **กลับจอเริ่มต้นเสมอ** (quiz → Landing · ring-size → R0 ตามเดิม) + guard เหมือน `resolveScreen`: popstate ไป Q3/Result โดยไม่มีคำตอบ = replace ไป Landing (ไม่ค้างจอว่าง)

### 4.2 ลำดับ entry ของ quiz (เสนอ)

```
Landing(0) → Q1(1) → Q2(2) → Q3(3) → Q4(4) → Q5(5) → Loading(6, push) ── timer ──▶ replaceState → Result(6)
```
- Loading ถูก **replace** เป็น Result (ไม่เหลือ entry ของ Loading) → Back จาก Result ไป Q5 ไม่เจอ loading วนซ้ำ · Back ระหว่าง Loading ไป Q5 (timer ถูกเคลียร์โดย cleanup เดิม)

- 🔴 **สถิติส่ง (submit) ต้องไม่เบี้ยว:** ตอนนี้ส่ง 1 ครั้งต่อรอบด้วย `submittedRef` และ reset แค่ใน `restart()` · เมื่อ Result ถอยกลับแก้คำตอบได้ → กติกา: **ส่งซ้ำเฉพาะเมื่อคำตอบ/พลอยที่ชอบ ต่างจากที่ส่งไปแล้ว** (เทียบ JSON) และส่งเป็น `retake=true` (ใช้ `sentThisSessionRef` เดิม) · คำตอบเหมือนเดิม = ไม่ส่งซ้ำ · **ให้ Yoda/เจ้าของ ยืนยันว่านับ "แก้แล้วดูผลใหม่" เป็นรอบ retake ได้** `[ต้องยืนยัน Q5]`

## 8. State ครบ 4 (เฉพาะส่วนใหม่)

| ส่วน | Loading | Empty | Error | Success |
|---|---|---|---|---|
| ปุ่มถอย/ลิงก์ hub | ไม่มี async | quiz ขั้นแรก/R0 ไม่มีตัวนับ · ไม่มีปุ่มขวา | `history` API ใช้ไม่ได้ (sandbox/LINE) → ปุ่มบนจอยัง navigate ด้วย state ได้ · เสียแค่ Back ของเครื่อง (เหมือน `navigate` ของ ring-size) · ลิงก์ hub เป็น `<a>` ทำงานแม้ JS ไม่โหลด | กดแล้วไปขั้นก่อน/hub |
| LeaveSheet | — | — | เปิดไม่ขึ้น (JS พัง) → ลิงก์ hub ทำงานโดยไม่ถาม | เลือก "อยู่ต่อ" = กลับจอเดิมโฟกัสที่ปุ่มที่กด · "ออก" = ไป hub |

## 9. Accessibility

- ทุกปุ่ม/ลิงก์ใหม่ `min-h-11` (44) · ปุ่มถอยเป็น `<button>` (ไม่ใช่ลิงก์) เพราะทำ history · ลิงก์ hub เป็น `<a href>` · ไม่มี `role="button"` ปลอม
- ลำดับ Tab = ลำดับภาพ: ถอย → ตัวนับ(ไม่โฟกัส) → เครื่องมือ 3J → เนื้อหา · LeaveSheet: focus trap, โฟกัสเริ่ม "อยู่ต่อ", Esc = อยู่ต่อ, คืนโฟกัสไปปุ่มที่เปิด
- "แก้": `aria-label="แก้แบบแหวน"` / `"แก้ชุดพลอย"` / `"แก้ไซซ์"` (ชื่อบอกแถว ไม่ใช่ "แก้" ซ้ำ 3 ครั้ง) · หลังเลื่อน โฟกัสที่ `<h2 tabIndex={-1}>` · ประกาศผ่าน `role="status"` เดิม
- เปลี่ยนจอ quiz ผ่าน Back: โฟกัสไปเนื้อหาจอใหม่ (เหมือน ring-size ที่ `root.focus()` อยู่แล้ว)
- Contrast: ข้อความขวา `--gq-text-muted` บน ivory ≈ 4.9:1 (ผ่าน AA · ตรวจจริงตอน implement) · ไอคอนไม่ใช่ตัวส่งความหมายเดียว
- `prefers-reduced-motion`: เลื่อนแบบ `auto` · ไม่มี animation ใหม่
- ไม่ใช้สีเป็นตัวบอกความต่าง "ถอย" กับ "ออก" (รูปร่าง+ข้อความ)

## 13. Trade-off หลัก + จุดที่ต้อง validate

1. **ปุ่ม hub ทุกจอ + ยืนยันเมื่อมีงานค้าง** แทน "ไม่ใส่กลางทาง" — ได้ปุ่มที่เจ้าของขอ แลกด้วย 1 ด่านถามในบางจอ · ถ้า validate แล้วคนกดพลาดบ่อย → ย้ายไปหลังขั้นที่ 2
2. **ไอคอนถอยเปล่า + ลิงก์ขวามีข้อความ** — แลกความชัดของข้อความถอยกับความแน่นของแถบ 335px
3. **"แก้" ในสรุป** แทน stepper/chips — แลกกับการที่คนอยู่กลางหน้าต้องเลื่อนเอง
4. **history ต่อจอ + replace loading** — เพิ่มความซับซ้อน state machine ของ quiz (ต้นแบบมีแล้ว) แลกกับ Back ที่ไม่หลุด
5. **ไม่กู้ผล quiz ใน P1** — ผู้ใช้ที่ Back จาก ring-builder ไป quiz จะเจอ Landing เปล่า (ต้องทำใหม่ ~1 นาที)

**ต้อง validate กับผู้ใช้จริง:** (ก) Back ใน LINE iOS/Android เดินทีละขั้น quiz/ring-size จริงไหม · (ข) คนกด "เครื่องมือ 3J" กลาง flow แล้วงงว่า "ไปไหน" ไหม (ถ้าสำคัญ ลอง "รวมเครื่องมือ") · (ค) ลูกค้าเห็นปุ่ม "แก้" ในสรุปไหม/กดไหม · (ง) ลูกค้าที่วัดไซซ์เสร็จกด "ดูแหวนด้วยเบอร์ N" หรือ LINE ก่อน

## 14. คำถามเจ้าของ (ถ้ายังไม่รู้ = `[ต้องยืนยัน]` ห้ามเดา)

- **Q1** ถ้อยคำปุ่มออกหน้ารวม: `เครื่องมือ 3J` (ใช้อยู่แล้ว · แนะนำ) หรือ `หน้าหลัก` (ใน LINE อาจสับสนกับหน้าหลักของ OA)?
- **Q2** ยอมรับว่ากลางทาง quiz/วัดไซซ์ มีปุ่มออกไป hub ได้แล้ว (เขียนทับมติ 18 พ.ย. ที่ว่าไม่ใส่กลางทาง) โดยมีด่านถามเฉพาะเมื่อมีงานค้างใช่ไหม?
- **Q3** quiz Result: เอาไอคอน "เริ่มใหม่" ซ้ายบนออก (เหลือปุ่ม "ทำแบบทดสอบใหม่" ท้ายหน้าตัวเดียว) ใช่ไหม?
- **Q4** R6 มีปุ่มเยอะเกินไป — ยังต้องการ "แชร์" และ "ลิงก์ร้าน" ทั้งคู่ไหม? (ไม่ลบจนกว่าจะตอบ)
- **Q5** quiz: ถอยจากผลไปแก้คำตอบแล้วดูผลใหม่ — นับเป็นรอบ "ทำซ้ำ" ในสถิติได้ไหม (ส่งซ้ำเฉพาะเมื่อคำตอบเปลี่ยน)? ให้ Yoda ยืนยันผลต่อ `/api/gem-quiz/submit` ด้วย
- **Q6** (P2) ยอมให้เก็บคำตอบ quiz ใน `sessionStorage` (หายเมื่อปิดแท็บ) เพื่อกู้ผลตอน Back ไหม? (ไม่ระบุตัวตน แต่เป็นข้อมูลความตั้งใจส่วนตัว — ux-tools-hub §3 เคยเลี่ยง)
- **Q7** หน้าแหวนมีการวัดคลิกปุ่ม "แก้"/ลิงก์ใหม่ไหม (ปัจจุบันไม่มี track บนหน้านี้ — ไม่เพิ่มเองถ้าไม่สั่ง)

## 15. ข้อจำกัดของ spec นี้ (สิ่งที่ผมไม่ได้ยืนยัน)

- ไม่ได้เปิด `G3Sheet` · `G2` · `RingStage` · screen R1–R5 ทีละไฟล์ — ตำแหน่ง overlay บน stage (pill hub P2) และโครง sheet ให้ frontend ตรวจกับของจริงก่อน
- ไม่ได้ทดสอบ Back ใน LINE in-app บนเครื่องจริง — ข้อ 4 เป็นการออกแบบจากพฤติกรรมเบราว์เซอร์มาตรฐาน + โค้ด ring-size ที่ผ่าน QA แล้ว
- การย้าย `nextHistoryState` เป็น lib ร่วมไม่บังคับใน P1 (ลดความเสี่ยงต่อ ring-size)

## 16. มติเจ้าของ 24 พ.ย. 69 (เขียนทับ §14)

- **Q1** ปุ่มขวาบน = `เครื่องมือ 3J`

- **Q3** ✅ เอาไอคอน "เริ่มใหม่" ซ้ายบนของผล quiz ออก เหลือปุ่ม "ทำแบบทดสอบใหม่" ท้ายหน้าอันเดียว
