# UX spec: หน้าสรุปสถิติไซส์แหวนสำหรับเจ้าของ `/marketing/ring-size`

> ux-ui (Padmé) · 25 ต.ค. 69 · UX spec ก่อน frontend — ไม่มีโค้ด · ข้อมูลที่ใช้ = สิ่งที่ RPC `analytics.ring_size_stats` คืนตาม `design-ring-size-analytics.md` §3.4 + §12.1 (retention 180 วัน)
> หน้าเทียบที่ลอก pattern: `app/(dashboard)/marketing/gem-quiz/page.tsx` · `components/domain/marketing/GemQuizStats.tsx` · chip filter: `components/domain/marketing/ChannelRoasFilter.tsx`
> ตัวเลขในภาพ wireframe เป็น **ตัวอย่างวาง layout เท่านั้น ไม่ใช่ข้อมูลจริง** · ค่าที่ต้องมาจากเจ้าของ = `[ต้องยืนยัน]`

## 0. TL;DR

- เรียงหน้าตามคำถามเจ้าของ: (1) สรุป 3 ตัวเลข → (2) ส่วนใหญ่ไซส์อะไร → (3) วัดด้วยวิธีไหน/กระดาษมีปัญหาแค่ไหน → (4) คนเลิกที่ขั้นไหน → (5) มาจากช่องทางไหน → (6) จุดที่คนติด → (7) รายวัน → (8) วิธีนับ/ข้อจำกัด · คอลัมน์เดียวทุกขนาดจอ (ไม่ขยาย `max-w-6xl`) · ตาราง + แท่ง CSS ไม่มี chart library
- **เรียก "ครั้งที่เปิดใช้" ไม่ใช่ "คน"** — session ตายเมื่อปิดแท็บ คนเดียวกลับมาเปิดใหม่นับใหม่ · ตัวเลข "กด LINE" ติดป้าย "ขั้นต่ำ"
- **% โชว์เมื่อฐานหาร >= 30 เท่านั้น** (ต่อทุกค่า ไม่ใช่แค่ยอดรวม) ฐานต่ำกว่า 30 โชว์ "3 จาก 8" แทน — กันตัวเลข % ที่แกว่งทำให้เจ้าของสรุปผิด (เรื่องกระดาษจะเจอตัวอย่างน้อยอีกนานแน่)
- ช่วงวันที่: chip 7/30/90/180 วัน (**relative ใน URL** → bookmark "7 วันล่าสุด" ไม่แข็งเป็นวันเก่า) + กำหนดเอง · ไม่เกิน 180 วัน บังคับที่ server ไม่ใช่แค่ `max` ของ input
- 🔴 **พบ 4 ช่องใน design/RPC ที่กระทบโจทย์ "กระดาษคลาดเคลื่อน" ต้องตัดสินก่อนเขียน migration 0193** (§13) — สำคัญสุด: `method` เป็น "ค่าล่าสุดทับ" ทำให้คนที่ลองกระดาษแล้วเปลี่ยนไปแหวนเดิมหายจากสถิติกระดาษ · และ "ก้ำกึ่ง" ไม่ใช่ตัวชี้วัดความแม่น (§7.3)

## 2. ผู้ใช้ + งานที่ต้องทำ

**ผู้ใช้**: เจ้าของ/แอดมิน (staff ไม่เห็น) · เปิดทุกสัปดาห์ · คอมกับมือถือพอๆ กัน · ชอบตาราง + ตัวเลขจริง · ไม่ใช่นักสถิติ

**งาน 5 อย่าง (เรียงตามความถี่)**
1. "สัปดาห์นี้มีคนใช้เท่าไร วัดได้กี่ครั้ง" (5 วินาที)
2. "ส่วนใหญ่ไซส์อะไร อยู่ในช่วงที่ร้านทำไหม"
3. "คนใช้วิธีไหน — กระดาษมีปัญหาจริงไหม" (โจทย์พิเศษจากเจ้าของ 25 ต.ค.)
4. "คนเลิกกลางทางที่ขั้นไหน" (ไว้ตัดสินใจแก้เครื่องมือ)
5. "มาจากช่องทางไหน" (ไว้ตัดสินใจแปะลิงก์ที่ไหน)

### User flow

```
เปิดหน้า (bookmark / เมนู การตลาด > เพิ่มเติม > ไซส์แหวน)
  ├─ staff ─────────────────────────▶ EmptyState "จำกัดสิทธิ์" (จบ)
  ├─ env ตั้งค่าไม่ครบ ─────────────▶ ErrorState (จบ — ไม่มีแถบกรอง เพราะโหลดอะไรไม่ได้)
  └─ owner/admin
       ├─ โหลด (loading.tsx) ──▶ skeleton ทรงเดียวกับหน้าจริง
       ├─ RPC ล้ม ─────────────▶ แถบกรอง + ErrorState (+ปุ่ม "โหลดใหม่") ── เปลี่ยนช่วง/ช่องทางได้
       ├─ 0 ครั้ง ─────────────▶ แถบกรอง + EmptyState 3 แบบ (§9) ── ปุ่มขยายช่วง/ดูทุกช่องทาง
       └─ มีข้อมูล
            อ่านจากบนลงล่าง ── (ต้องการเจาะ) ──▶ กดช่วงวัน/ช่องทาง ──▶ URL เปลี่ยน ──▶ เนื้อหาจาง + "กำลังอัปเดต" ──▶ ข้อมูลใหม่
            ท้ายหน้า: "อ่านก่อนตีความ" (วิธีนับ + ข้อจำกัด)

edge: URL พิมพ์เอง (วันที่ผิดรูป/ย้อน >180 วัน/อนาคต/from>to/src แปลก)
      → server ปรับเข้าค่าที่ถูกต้อง + แถบบอกว่า "ปรับช่วงวันที่ให้อยู่ในขอบเขต" (ไม่ error เงียบ ไม่ปล่อย 22023 ถึงจอ)
```

## 4. ตัวกรอง + URL (bookmarkable)

```
/marketing/ring-size                          = 30 วันล่าสุด · ทุกช่องทาง (URL สะอาด ไม่มี param)
/marketing/ring-size?range=7d                 = 7 วันล่าสุด (relative — bookmark ได้ ไม่แข็ง)
/marketing/ring-size?range=90d&src=line
/marketing/ring-size?from=2026-09-26&to=2026-10-25&src=fb     (กำหนดเอง — absolute)
```

| param | ค่า | ตรวจที่ server (`parseRingSizeFilters` pure + test) |
|---|---|---|
| `range` | `7d` `30d` `90d` `180d` | นอกชุด = ใช้ default · `to` = วันนี้ (Asia/Bangkok) · `from` = to − (n−1) |
| `from` `to` | `YYYY-MM-DD` | ถ้ามีทั้งคู่และถูกต้อง → ชนะ `range` · รูปผิด/วันที่ไม่มีจริง (30 ก.พ.) = ทิ้งทั้งคู่ · `to` > วันนี้ → วันนี้ · `from` > `to` → ใช้ default · ช่วง > 180 วัน (นับรวมปลาย) → ตัด `from` ให้เหลือ 180 วัน |
| `src` | `^[a-z][a-z0-9_]{0,15}$` | ไม่ผ่าน regex = ทิ้ง (ทุกช่องทาง) + แจ้ง · ผ่าน regex แต่ RPC ไม่รู้จัก (22023) → ErrorState ข้อความ "ไม่พบช่องทางนี้" + ปุ่ม "ดูทุกช่องทาง" |

- **180 วัน = ขอบที่ cron ลบ (180d)** · UI เลือกได้ไม่เกิน today−179 ถึง today · ข้อความใต้แถบกรอง "ระบบเก็บข้อมูลย้อนหลัง 180 วัน"
- ตอนปรับค่าให้เอง ต้องมีแถบ `role="status"` สีกลาง บอกว่าปรับอะไร (เช่น "ปรับช่วงวันที่ให้ไม่เกิน 180 วัน") — **ห้ามปรับเงียบ**
- ตัวเลือกช่องทางมาจาก lookup `ring_size_src` (active) ไม่ hardcode ใน client (§13 A3) · fallback ถ้าไม่มี label = โชว์รหัสดิบ (ตัดความยาวด้วย `truncate` + `title`)

**ควบคุม**
| ตัวควบคุม | ชนิด | ขนาด/พฤติกรรม |
|---|---|---|
| ช่วงเวลา 7/30/90/180 | chip (`button aria-pressed`) — pattern เดียวกับ `ChannelRoasFilter` | `min-h-11 rounded-full px-3` · active = `bg-primary-100 text-primary-700` · กดแล้ว push ทันที |
| กำหนดเอง | chip ตัวที่ 5 เปิดแถวข้างล่าง: date "ตั้งแต่" · date "ถึง" · ปุ่ม **"ดูข้อมูล"** (Button primary md) | input `min-h-11` · `min`=today−179 `max`=today · ผูก `from<=to` · กดปุ่มถึง push (ไม่ push ตอน onChange — U5) |
| ช่องทาง | `<select>` เนทีฟ "ทุกช่องทาง / …" | `min-h-11` · เนทีฟ = picker มือถือดีกว่า chip 7 ตัวที่ล้นหลายแถวที่ 360px · onChange push ทันที |
| สรุปสิ่งที่กำลังดู | บรรทัดข้อความ | "แสดง 26 ก.ย. 2569 – 25 ต.ค. 2569 · LINE OA · มีข้อมูลตั้งแต่ 14 ต.ค. 2569" (`data_since` §13 A4) |

เมื่อกำลังโหลด (push ค้าง): `useTransition` → เนื้อหา `opacity-60` + `aria-busy="true"` + ข้อความ `role="status"` "กำลังอัปเดต…" ข้างสรุปช่วง — **ห้ามพึ่ง `loading.tsx`** (Next ไม่แสดง fallback เมื่อเปลี่ยนแค่ searchParams ของ segment เดิม — frontend ต้องทดสอบจริง)

### 7.1 แถบสรุป 3 ตัว

| tile | ค่า | sub | tone |
|---|---|---|---|
| เปิดใช้ (ครั้ง) | `sessions` | "เคยใช้ในเครื่องนี้มาก่อน {returning} ครั้ง" | brand |
| วัดได้เบอร์ | `measured` | "{%} ของที่เปิด" (ตามกฎ MIN_N) | neutral |
| กดปุ่ม LINE | `cta.line` | "ขั้นต่ำ — อาจนับขาดบางครั้ง" (ไม่โชว์ %) | neutral |

- ใต้ tile: บรรทัดเดียว "หลังเห็นผล (ขั้นต่ำเช่นกัน): แชร์ผล {cta.share} · ดูหน้าร้าน {cta.shop} · เกมพลอย {cta.gem_quiz}"
- **ไม่โชว์ % ของ "กด LINE"** — ปุ่ม LINE อาจโผล่ที่หน้าช่วยเหลือ (G2/G4) ด้วย ไม่ใช่เฉพาะหน้าผลลัพธ์ ฐาน `measured` อาจให้เกิน 100% · ถ้า backend ยืนยันว่านับเฉพาะหน้าผลลัพธ์ ค่อยเพิ่ม % (§13 A4)
- "กดปุ่ม LINE" = กดปุ่ม ไม่ใช่ทักจริง — ใส่ใน "อ่านก่อนตีความ" · **ไม่ทำอะไรที่จับคู่รายคนกับแชท LINE** (design §7)
- StatCard ไม่มี loading/disabled state ในตัว → loading ใช้ skeleton ระดับหน้า

### 7.2 ส่วนใหญ่ไซส์อะไร

1. **พบมากสุด 3 อันดับ** — ชิป 3 อัน: "เบอร์ N" ตัวใหญ่ (`text-xl font-bold`) + "{count} ครั้ง" + % (MIN_N) · เรียง count มาก→น้อย เสมอกันให้เบอร์เล็กก่อน · เอาจาก `result_sizes` ทุกเบอร์ (รวมนอก 45–68) · ถ้านอกช่วงร้าน ติด Badge slate "นอกช่วงที่ร้านทำ" · มีน้อยกว่า 3 เบอร์ → โชว์เท่าที่มี
2. **ช่วงที่ร้านทำ** — 3 แถว (ต่ำกว่า / ในช่วง / สูงกว่า) จาก `size_summary` · แท่ง + จำนวน + % · ป้าย "45–68" **อ่านจาก RPC** (`shop_range` §13 A4) ไม่ hardcode · ในช่วง = แท่ง primary · นอกช่วง = แท่ง amber (`bg-amber-500`) + ตัวอักษรกำกับ ไม่พึ่งสีอย่างเดียว
3. **ตารางเบอร์** — `<table>` แถว = เบอร์ 45–68 ครบ **รวมเบอร์ที่เป็น 0** (ไม่ซ่อน เพื่อให้เห็นรูปการกระจายจริง) · เรียงตามเบอร์ขึ้นไป (เป็นสเกล ไม่ใช่อันดับ) · คอลัมน์: เบอร์ | แท่ง (flex-1) | ครั้ง | % · แท่งคิดความยาวเทียบ **ค่ามากสุดของตารางนี้** (ให้รูปชัด) แต่ % ที่โชว์ฐาน = `measured` · แถวที่เป็น 3 อันดับบน ตัวหนา + Badge "อันดับ 1/2/3" (ไม่ใช้สีอย่างเดียว) · แถวละ ~28px ไม่ใช่ปุ่ม จึงไม่ติดเกณฑ์ 44px
4. หมายเหตุ: "ผลก้ำกึ่งของวิธีกระดาษนับอยู่ในเบอร์ที่ระบบแนะนำ (เบอร์ใหญ่กว่า) แล้ว ไม่ได้นับซ้ำ"
5. ทำไมแนวนอน (ไม่ใช่กราฟแท่งตั้ง): 24 แท่งตั้งที่ 300px = แท่งละ ~10px ป้ายเบอร์ไม่พอ/อ่านด้วย screen reader ไม่ได้ · แนวนอนยาว ~700px แต่ไล่ตัวเลขได้ครบ (เจ้าของชอบตัวเลขจริง) — trade-off ยอมรับความยาวบนมือถือ

### 7.3 วัดด้วยอะไร — **ส่วนที่ตอบโจทย์ "กระดาษคลาดเคลื่อน"**

ตารางเทียบ 2 คอลัมน์ (แหวนวงเดิม | พันกระดาษรอบนิ้ว) · แถว ฐานหาร และข้อมูลที่ต้องการ (🔶 = ต้องขอเพิ่มจาก RPC §13 A1):

| แถว | ค่า | ฐาน % | ที่มา |
|---|---|---|---|
| เลือกวิธีนี้ (ครั้ง) | picked | ผลรวม 2 วิธี | `method` |
| วัดได้เบอร์ | measured | picked ของวิธีนั้น | 🔶 |
| เลิกที่หน้าวัด | abandoned_at_measure (max_stage = 6) | picked ของวิธีนั้น | 🔶 |
| ค่าวัดผิดปกติ | invalid sessions (G4) | picked ของวิธีนั้น | 🔶 |
| วัดซ้ำ 2 ครั้งขึ้นไป | measure_count >= 2 | measured ของวิธีนั้น | 🔶 |
| ผลก้ำกึ่งระหว่างเบอร์ | between | measured ของวิธีกระดาษ | `size_summary.between_count` + 🔶 ฐาน · คอลัมน์แหวน = "—" |
| ลองกระดาษแล้วเปลี่ยนมาแหวนเดิม | used_b และ method=A | measured | 🔶 A2 (ถ้าไม่มี = ตัดแถวนี้ทั้งแถว ไม่ใช่โชว์ 0) |

**การตีความที่ต้องไม่หลอกเจ้าของ (บังคับขึ้นจอใต้ตาราง — ข้อความ "ข้อสังเกต")**
- ตัวเลขทั้งหมด = สัญญาณ "ยาก/ไม่มั่นใจ" **ไม่ใช่ความแม่นยำ** — ระบบไม่มีทางรู้ว่าเบอร์ที่ได้ตรงนิ้วจริงไหม (ต้องดูจากการเปลี่ยน/คืนสินค้าแยกต่างหาก)
- **"ก้ำกึ่ง" ไม่ใช่ตัวชี้วัดความคลาดเคลื่อน**: เป็นผลตามกติกาของวิธีกระดาษ (`ceil(c−0.25)` + ระหว่างเบอร์) ส่วนแหวนวงเดิมปัดใกล้สุดจึงไม่มีทางก้ำกึ่ง → เทียบ A กับ B ไม่ได้ · ใช้ดู "กี่ครั้งที่ลูกค้าต้องได้ยินว่าอยู่ระหว่างเบอร์" เท่านั้น · จึงวางแถวนี้ **ท้ายตาราง** แยกจากแถวสัญญาณ
- สัญญาณที่เทียบ A กับ B ได้จริง = เลิกที่หน้าวัด · ค่าผิดปกติ · วัดซ้ำ · (ถ้ามี) เปลี่ยนวิธี
- "วัดซ้ำ" อาจมาจากการลองเล่น ไม่ใช่วัดไม่ได้ — ป้าย: "นับเมื่อได้ผลตั้งแต่ 2 ครั้ง"
- **ไม่ไฮไลต์สี/ไม่ตั้งเกณฑ์ "สูง/ต่ำ"** เพราะเกณฑ์ที่ถูกต้องต้องมาจากเจ้าของ `[ต้องยืนยัน]` (คำถาม Q3)

ตาราง 2x2 "เทียบหน้าจอด้วย x วิธีวัด": แถว = แหวนวงเดิม/กระดาษ · คอลัมน์ = เหรียญ 10 บาท/บัตร/รวม · จาก `method_x_ref` + `ref` · ตัวเลขล้วน (ไม่มี %) เพราะฐานเล็ก ใช้ดูว่า "ส่วนใหญ่เทียบด้วยอะไร"

**Fallback ถ้า architect ไม่เพิ่ม A1**: เหลือแถว "เลือกวิธีนี้" + ก้ำกึ่ง (ฐาน = `method.B` ซึ่งอาจรวมคนที่ยังไม่ได้ผล → % ต่ำเกินจริง ต้องติดป้ายเตือน) + วัดซ้ำรวมทั้งสองวิธีใน section จุดที่คนติด — **ตอบโจทย์กระดาษได้ไม่ครบ ไม่แนะนำ**

### 7.4 คนเลิกกลางทางที่ไหน (funnel)

ชื่อขั้นภาษาคน (ตรงกับ stage 0–7 ใน design §3.2 ซึ่งเป็น `as const` ชุดเดียว — `ring-size-labels.ts` ต้องมี test ว่ามี label ครบทุก stage):

| stage | ชื่อ "ไปถึงขั้นนี้" | ความหมายของ "เลิกที่ขั้นนี้" (max_stage = k) |
|---|---|---|
| 0 | เปิดหน้า | เปิดแล้วยังไม่กดเริ่ม |
| 1 | กดเริ่มวัด | กดเริ่มแล้วไม่เลือกของที่ใช้เทียบจอ |
| 2 | เลือกเหรียญหรือบัตรไว้เทียบหน้าจอ | เลือกแล้วไม่ปรับวงกลม |
| 3 | ปรับวงกลมให้เท่าของจริง | ปรับไม่เสร็จ |
| 4 | เทียบหน้าจอเสร็จ | เทียบเสร็จแล้วไม่เลือกวิธีวัด |
| 5 | เลือกวิธีวัด (แหวนวงเดิม/กระดาษ) | เลือกวิธีแล้วไม่เข้าหน้าวัด |
| 6 | เข้าหน้าวัด | อยู่หน้าวัดแล้วไม่ได้ผล |
| 7 | ถึงหน้าผลลัพธ์ | — (จบ ไม่นับเป็นเลิก) |

- ตารางมี **ฐานเดียว = เปิดใช้ (sessions)** ทั้งสองคอลัมน์ ("ไปถึง" cumulative และ "เลิก" รวมกับ "จบ" = 100%) — ยอมไม่ให้ "% เลิกต่อคนที่มาถึงขั้นนั้น" (ซึ่งชี้ขั้นที่ยากจริง) เพราะผสมสองฐานในตารางเดียวทำให้อ่านผิด · ตัวเลขดิบ `funnel` ให้เจ้าของคำนวณเองไม่ได้ จึงเป็น trade-off (§14 D6)
- **เลขขั้นบนจอ = stage + 1 (1–8)** ให้คนอ่านนับจาก 1 · ค่าใน RPC/โค้ดยังเป็น stage 0–7 (อย่าให้เลขสองระบบหลุดข้ามกัน — ใส่ใน `ring-size-labels.ts` ที่เดียว)
- **Badge "หยุดมากสุด"**: ขั้นที่ `abandon_at` มากสุดในกลุ่ม stage 1–6 (= กดเริ่มแล้วเลิก) · stage 0 "เปิดแล้วไม่กดเริ่ม" มากสุดเสมอและไม่ใช่ปัญหาของขั้นตอน จึงแสดงแถวเดียวกันแต่ไม่เข้าการเลือก Badge · เสมอ = ติดทุกขั้นที่เสมอ · ฐานเปิดใช้ < 30 หรือค่า = 0 → ไม่ติด · เลือกค่ามากสุดจากข้อมูล ไม่คำนวณใหม่
- แถวสุดท้ายมีบรรทัดรอง: "ได้เบอร์ {measured} · ที่เหลือคือหน้า 'ค่าวัดผิดปกติ'" (U8)
- หมายเหตุใต้ตาราง: คนที่เคยเทียบจอไว้ในเครื่องเดิมข้ามขั้น 3–5 บนจอ (stage 2–4) ไปเลย จึงนับว่าผ่านแล้ว · "เลิก" = ปิดหน้า/ออกไปโดยไม่ไปต่อ ถ้ากลับมาใหม่นับเป็นครั้งใหม่
- **โครง DOM: `<ol>` + `<li>` ทุกขนาดจอ** — ลำดับขั้นคือรายการเรียงลำดับ ไม่ใช่ตารางเปรียบเทียบหลายมิติ · แต่ละ `<li>` เป็น grid 2 บรรทัด (ชื่อขั้น + ตัวเลข "ไปถึง" / แท่ง + "เลิกที่ขั้นนี้") ที่ 360px และขยายเป็นแถวเดียวที่ `md:` · ตารางจริง (`<table>`) ใช้กับ 7.2 / 7.3 / 7.5 / 7.6 ที่เป็นหลายมิติ
- ผลกระทบต่อ wireframe §5: ภาพวาดเป็นแถวเดียวต่อขั้นแบบตาราง — เป็นรูปแบบการจัดวางของ `<li>` ที่ `md:` ไม่ใช่ `<table>`

### 7.5 ช่องทาง

- 2 ตาราง: **ลิงก์ที่ร้านแปะ (src)** ← `by_src` (label จาก lookup §13 A3) · **เปิดในแอปอะไร (in_app)** ← `by_in_app` · คอลัมน์: ชื่อ | ครั้ง | % ของเปิดใช้ · เรียงมาก→น้อย
- in_app label: LINE · TikTok · Facebook · Instagram · เบราว์เซอร์ทั่วไป · ไม่ทราบ — ติดป้ายหัวตารางว่า "ประมาณการจากชนิดแอป อาจจัดผิดกลุ่มได้" (UA bucket พลาดได้ — design §11 ข้อ 7)
- **TikTok**: แถว "TikTok" ในตาราง in_app + ข้อความ "ดูจากแอปที่เปิดหน้านี้ ไม่ใช่ลิงก์ที่ร้านวาง" · **ห้ามมี CTA/ข้อความแนะนำให้แปะลิงก์ใน TikTok** (นโยบายแพลตฟอร์ม — memory `tiktok-offplatform-policy`)
- **ไม่มี matrix src x in_app** (RPC ไม่ได้ให้ crosstab — ไม่ออกแบบสิ่งที่ข้อมูลไม่มี)
- เมื่อกรองช่องทางอยู่ → ตาราง src มีแถวเดียว: ใส่แถบ "กำลังกรอง: LINE OA" + ปุ่ม "ดูทุกช่องทาง" แทนที่จะโชว์ตารางแถวเดียวเงียบๆ

### 7.6 จุดที่คนติด

ฐาน = **กดเริ่ม (`funnel[1]`)** ฐานเดียวทั้งตาราง (เหตุการณ์ทั้งหมดเกิดหลังกดเริ่ม · เทียบกันได้) · แถวละหนึ่งปัญหา ภาษาคน + (ข้อความรองอธิบาย 1 บรรทัด):

| key (RPC `friction`) | ชื่อบนจอ | อธิบายรอง |
|---|---|---|
| G1 `zoom_blocked` | ซูมหน้าจออยู่ เทียบขนาดไม่ได้ | ต้องเลิกซูมก่อนถึงจะไปต่อได้ |
| G3 `calib_warn` | ค่าเทียบจอผิดปกติ | ขนาดที่ปรับไว้ไม่ตรงกับที่จอทั่วไปเป็น |
| G4 `invalid` | ค่าวัดผิดปกติ | เล็กหรือใหญ่เกินช่วงที่เครื่องมือวัดได้ |
| G5 `stale_recalib` | ค่าเทียบเก่าอาจไม่ตรงเครื่องนี้ | ใช้ค่าที่เคยเทียบไว้ แต่ขนาดจอเปลี่ยน |

- **ชื่อ key ใน RPC ยังไม่ได้ระบุใน design §3.4 (`friction{...}`) → ขอให้ระบุ (A4)** · key ที่ไม่รู้จัก = ไม่โชว์ ไม่ crash
- ไม่มีรหัส G1–G5 บนจอ (เป็นศัพท์ dev) — ใส่ใน `title`/test id เท่านั้น
- "วัดซ้ำ" ไม่อยู่ที่นี่ (อยู่ในตาราง 7.3 ที่แยกตามวิธี — ไม่ให้ซ้ำและคนละฐาน)

### 7.7 รายวัน

- แถว = วันที่ไทย (`thaiDate` แบบสั้น) | แท่ง (เทียบวันที่มากสุดในช่วง) | "{sessions} เปิด · {measured} ได้เบอร์" · **ใหม่→เก่า** (เจ้าของดูสัปดาห์ล่าสุดก่อน — ต่างจาก gem quiz ที่เรียงเก่า→ใหม่)
- แสดง 14 วันล่าสุดของช่วง + ปุ่ม "แสดงทั้งหมด {n} วัน" (`min-h-11`, toggle `aria-expanded`) — ช่วง 180 วัน = 180 แถว ไม่ควรยาวเป็นค่าเริ่มต้น · ไม่ซ่อนด้วย conditional render ซ้ำซ้อน (ใช้ slice เฉยๆ ไม่มี state ฟอร์มที่ต้องรักษา)
- ไม่เติมวันที่ว่างเอง — ถ้า RPC ไม่คืนวันที่ 0 ครั้ง จะมีรู ขอให้ RPC คืนครบทุกวัน (A4) ไม่งั้นแท่งหลอกว่าต่อเนื่อง
- วันเริ่มมีข้อมูล: ถ้า `data_since` > `from` แทรกแถวคั่น "— ก่อนวันนี้ยังไม่ได้เก็บข้อมูล —" ท้ายรายการ
- ไม่มีเวลาระดับนาที/ชั่วโมง (design §7: ลดความเสี่ยงจับคู่รายคน)

### 7.8 การกระจายเส้นรอบวง (มม.) — พับ

`CollapsibleSection` (ปิดเป็นค่าเริ่มต้น) · ตาราง มม. (ช่วง 1 มม.) | ครั้ง | แท่ง · `overflow-x-auto` · ใช้ตรวจว่าค่ากองอยู่ติดเส้นปัดเบอร์หรือไม่ (ช่าง/ทีม ไม่ใช่เจ้าของทุกสัปดาห์) · **เสนอตัดทิ้งใน v1** ถ้าเจ้าของไม่ตอบรับตอนทดลอง (§14 D10, §15)

## 8. ลำดับโฟกัส / การอ่านด้วยคีย์บอร์ด

h1 → แถบกรอง (chips → กำหนดเอง → select) → [แถบ notice] → StatCard 3 ใบ (ไม่ใช่ลิงก์ จึงไม่รับโฟกัส) → h2 ต่อ section ตามลำดับภาพ → ปุ่มขยายรายวัน → CollapsibleSection → อ่านก่อนตีความ · ไม่มี tabindex บวก · หลัง push เสร็จ ไม่ย้ายโฟกัสหนี (ผู้ใช้อยู่ที่ chip เดิม) · `aria-live="polite"` ที่ข้อความ "กำลังอัปเดต…/อัปเดตแล้ว" (ไม่ประกาศตัวเลขทั้งหน้า)

## 9. State ครบ

| State | เงื่อนไข | หน้าตา |
|---|---|---|
| **staff** | `getEffectiveRole()==="staff"` | `EmptyState` icon `Lock` "หน้านี้จำกัดสิทธิ์" / "เฉพาะเจ้าของร้าน/แอดมินเท่านั้นที่ดูสถิติไซส์แหวนได้" (ลอก gem quiz) · ไม่เรียก RPC · เมนูยังเห็นเหมือนแบบทดสอบพลอย (consistent) |
| **ตั้งค่าไม่ครบ** | `getDevShopId()` throw | `ErrorState` ข้อความจาก error (เหมือน gem quiz) — ไม่มีแถบกรอง |
| **loading (เข้าหน้า)** | server await | `loading.tsx`: `role="status" aria-label="กำลังโหลดสถิติไซส์แหวน"` · Skeleton: หัว (h-6 w-48 + h-4 w-72) · แถบ chip (h-11 w-full) · 3 tile (`grid-cols-3` h-20) · 2 การ์ด h-48 · ทรงเดียวกับหน้าจริง กัน layout shift |
| **loading (เปลี่ยนกรอง)** | `useTransition` pending | เนื้อหา `opacity-60` + `aria-busy` + "กำลังอัปเดต…" (ไม่ปิดการกดซ้ำ — กดอันใหม่ทับได้) |
| **error (RPC ล้ม)** | catch | แถบกรองยังอยู่ + `ErrorState` "โหลดสถิติไม่สำเร็จ ลองใหม่อีกครั้ง" + ปุ่ม "ลองใหม่" (`router.refresh()` ผ่าน client shell) · log แค่ `readErrorCode` (ห้ามก้อน error — memory supabase-error-logging-trap) |
| **error (กรองผิด 22023)** | src ไม่รู้จัก / ช่วงผิด | ข้อความเฉพาะ ("ไม่พบช่องทางนี้" / "ช่วงวันที่ไม่ถูกต้อง") + ปุ่ม "ใช้ค่าเริ่มต้น" (ล้าง param) · ไม่มีปุ่มลองใหม่ (ซ้ำก็พังเหมือนเดิม) |
| **empty ก (ไม่เคยมีข้อมูล)** | `sessions=0` และ `data_since=null` | แถบกรอง + `EmptyState` "ยังไม่มีคนใช้เครื่องมือวัดไซส์" / "สถิติจะขึ้นเมื่อมีคนเริ่มใช้ — ถ้ารอนานผิดปกติ แจ้งทีมพัฒนาให้ตรวจว่าเปิดเก็บสถิติแล้วหรือยัง" |
| **empty ข (ช่วงอยู่ก่อนเริ่มเก็บ)** | `sessions=0` และ `data_since > to` | "ช่วงนี้อยู่ก่อนวันที่เริ่มเก็บข้อมูล (เริ่ม {วันที่})" + ปุ่ม "ดูตั้งแต่ {วันที่}" |
| **empty ค (ช่วง/ช่องทางนี้ว่าง)** | อื่นๆ ที่ `sessions=0` | "ไม่มีการใช้งานในช่วง/ช่องทางที่เลือก" + ปุ่ม "ขยายเป็น 90 วัน" และ (ถ้ากรองช่องทาง) "ดูทุกช่องทาง" · ไม่ซ่อนแถบกรอง (บทเรียน S3) |
| **ข้อมูลน้อย** | `sessions` 1–29 | แถบ amber `role="status"` (ใต้แถบกรอง) + Badge amber "ข้อมูลยังน้อย" ที่การ์ดที่ฐาน <30 · ตัวเลขโชว์ครบเป็น "จำนวน" ส่วน % ตามกฎ MIN_N (§7.0) |
| **success** | `sessions >= 30` | หน้าเต็ม §5 |
| **section ว่างบางส่วน** | ฟิลด์ของ RPC ว่าง/ไม่มี key | section นั้นโชว์ "ยังไม่มีข้อมูล" (`text-zinc-500` ไม่ใช่ 400) — ห้ามหาย/ห้าม crash · ห้ามพูดถึง migration ในข้อความ (ศัพท์ dev ไม่ขึ้นจอเจ้าของ) |
| **ข้อมูลบางช่วง** | `data_since > from` และ `sessions>0` | บรรทัด notice สีกลาง "เริ่มมีข้อมูลตั้งแต่ {วันที่} — ก่อนหน้านั้นยังไม่ได้เก็บ" (กันเจ้าของเห็นกราฟรายวันเงียบแล้วคิดว่าตก) |
| **ปรับ URL ให้เอง** | parse ปรับค่า | notice `role="status"` บอกว่าปรับอะไร |

**Edge จริง**: ชื่อช่องทางยาว → `break-words min-w-0` ไม่ล้นการ์ด · ตัวเลข 5–6 หลัก → tile ไม่ล้น (`text-2xl` ที่ ~76px ต้องทดสอบ 360px ที่ "12,345") · ช่องทางเดียว 100% · ฐาน 0 ทุกแถว (กันหารศูนย์ → "—") · เบอร์นอก 45–68 ใน top 3 · ไม่มีเบอร์ใดๆ (measured=0 แต่ sessions>0) → section 1 = "ยังไม่มีใครวัดได้เบอร์ในช่วงนี้" ไม่ใช่ตารางศูนย์ 24 แถว · label จาก DB เป็นข้อความธรรมดา (React escape เอง ห้าม `dangerouslySetInnerHTML`)

## 11. Accessibility checklist

- contrast: เนื้อ `zinc-700/800/900` · ข้อความรอง `zinc-600` (เนื้อที่ต้องอ่าน) / `zinc-500` (ป้ายประกอบ) · **ห้าม `zinc-400` กับข้อความ** (U3) · amber banner `bg-amber-50 border-amber-300 text-amber-900` · Badge amber/slate จาก `Badge` เดิม (ผ่าน) · แท่ง `bg-primary-600` บน `bg-zinc-200` (non-text 3:1 — frontend วัดจริงกับ token brand #a2191d)
- ไม่พึ่งสีอย่างเดียว: อันดับ = Badge ข้อความ · "นอกช่วง" = ข้อความ + แท่ง amber · "หยุดมากสุด" = Badge ข้อความ
- โครง: 1 `h1` · แต่ละ section `<section aria-labelledby>` + `h2` (gem quiz ข้ามไป `h3` — ไม่ลอก) · ตารางมี `<caption class="sr-only">` + `<th scope>` · แท่ง `aria-hidden` (ไม่ใช้ `role=progressbar` ซ้ำ 40+ ตัวให้ screen reader อ่านรก)
- touch target >= 44px: chip · select · date input · ปุ่ม "ดูข้อมูล" · "แสดงทั้งหมด" · "ลองใหม่" (`ErrorState` ใช้ Button `size="sm"` = 36px — ที่หน้านี้ใช้ปุ่ม `md` ในกล่อง error ของเราเอง หรือ wrap ให้ `min-h-11`)
- focus: ใช้ `focus-visible:ring-2 ring-primary-600` ของ Button เดิม · chip ใส่ class เดียวกัน (ChannelRoasFilter ปัจจุบันไม่มี focus ring — หนี้เดิม ห้ามลอก)
- เคารพ `prefers-reduced-motion`: ไม่ใส่ animation เอง · skeleton `animate-pulse` ของเดิมคงไว้
- ซูมตัวอักษร 200% / Safari aA 115%: ไม่ fix ความสูง · ข้อความห่อได้ทุกเซลล์

| # | ตัดสินใจ | ไม่ทำแบบไหน | ทำไม / ราคาที่จ่าย |
|---|---|---|---|
| D1 | คอลัมน์เดียว `max-w-3xl` | ขยาย wide 2 คอลัมน์ (แก้ `nav.ts`+`isWideMarketingPath`) | ตารางทุกอันพอใน 768px · ไม่แตะ shell/nav test · ราคา: บนจอกว้างมีที่ว่างขวาเหลือ |
| D2 | ตาราง + แท่ง CSS | chart lib / กราฟแท่งตั้ง 24 แท่ง | เจ้าของชอบตัวเลข · 10px/แท่งที่ 360px ป้ายไม่พอ · ราคา: หน้ายาวกว่า (~24 แถว) |
| D3 | ใช้ "ครั้ง" | ใช้ "คน" (เหมือน gem quiz) | session ตายตามแท็บ — เรียกคนจะเกินจริงและเจ้าของเอาไปคูณกับจำนวนลูกค้า · ราคา: ไม่ตรงภาษาที่เจ้าของพูด → ใส่ลง §15 ให้ validate |
| D4 | % เมื่อฐาน >= 30 ต่อค่า | โชว์ % ทุกค่า / ซ่อนทั้งหน้าเมื่อรวม <30 | ฐานย่อยของกระดาษจะเล็กนานที่สุด — "3 จาก 8" ซื่อสัตย์กว่า "38%" · ราคา: ช่วงแรกหลายเซลล์ไม่มี % |

## 15. จุดที่ต้อง validate กับผู้ใช้จริง (design จับไม่ได้)

1. **งาน 30 วินาทีบนมือถือ**: ให้เจ้าของตอบ "ส่วนใหญ่ไซส์อะไร" / "คนเลิกขั้นไหนมากสุด" / "กระดาษมีปัญหาไหม" จากหน้าโดยไม่ถาม — ดูว่าใช้เวลา/เลื่อนหน้ากี่ครั้ง และเจอ section 2 เองไหม
2. **"ครั้ง" vs "คน"** — เจ้าของเข้าใจป้าย "ครั้งที่เปิดใช้" ไหม หรือสับสนกับจำนวนลูกค้า
3. **"3 จาก 8" แทน %** — เจ้าของรู้สึกว่าข้อมูลขาดหรือเข้าใจว่า "ยังน้อยเกินสรุป" · ถ้ารำคาญ ลองเกณฑ์อื่นหลังคุยกัน
4. **ตารางเบอร์ 24 แถวบนมือถือ** — ยาวเกินไหม หรือ top 3 + ช่วงร้านพอแล้ว (ถ้าพอ ซ่อนตารางไว้ใน CollapsibleSection ได้)
5. **ข้อสังเกตเรื่อง "ก้ำกึ่ง"** — อ่านแล้วเข้าใจว่าทำไมเทียบกับแหวนไม่ได้ หรือยังตีความเป็น "กระดาษพลาด"
6. **ชื่อขั้น funnel** — ภาษาตรงกับสิ่งที่เจ้าของเห็นบนหน้าเครื่องมือ (ให้เทียบกับหน้า `/ring-size` จริง)
7. **ค่าเริ่มต้น 30 วัน** — ตรงกับรอบดูรายสัปดาห์ไหม (Q2)
8. **เครื่องจริง**: iPhone SE 360px (tile 3 ใบกับ "12,345") · Safari aA 115% · Android Chrome (date input native) · คอมที่ 768/1024/1440
